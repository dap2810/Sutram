# Sutram ROUND-122 WS2 — proposal review: kosh names, meaning, collision and behavior

**Pinned main:** `61d5f7b70e30e6711cc2171e57744de2dede70a1`; compiler v253, changelog v374. Sanskrit-only development until v1.0. The brief calls these **nine words** but supplies only **eight rows**: `push`, `pop`, `cap`, `clear`, `empty`, `peek`, `dequeue`, `enqueue`. The actual ninth existing builtin is **`kosh_len`**, included at the end below. This is a **review**, not an approved rename or grammar certification.

## Verified current behavior (not inferred from names)

The canonical [`docs/reports/KOSH-BUILTINS.md`](../docs/reports/KOSH-BUILTINS.md) and active compiler builtin table `src/sutram_compiler.asm:562-570` show the exact nine current names. `kosh_push` and `kosh_enqueue` **both append and return new length**; `kosh_pop` removes the **last** element; `kosh_dequeue` removes the **first** element (FIFO, O(n)); `kosh_peek` views the **last** without removing it. `kosh_cap` reports current allocated capacity, whereas `kosh_len` reports logical length. `kosh_clear` sets logical length to zero **without zeroing old storage**; `kosh_empty` is a read-only predicate returning 1 iff length is zero. All three empty pop/peek/dequeue operations can abort without an ok channel. These distinctions decide naming, not a loose word analogy.

## Verdict on the eight proposed words, plus missing ninth

| Actual builtin | Sarvam proposal | Assessment | Recommendation / reason |
|---|---|---|---|
| `kosh_push` | **`kshep` (क्षेप)** | **Plausible but not first choice** | `kṣepa` is a noun for casting/throwing and may denote an additive quantity; current `chay_khip`, `suchi_khip` already use the closer **`khip`** insert/push action. Prefer **`kosh_khip`** for consistency, subject to owner/grammar review. |
| `kosh_pop` | **`uddhar` (उद्धार)** | **Plausible with qualification** | `uddhāra` means taking/drawing out, but not inherently *last* element. A `kosh_uddhar` operation must explicitly preserve LIFO semantics. `chay_apanay` is the project's analogous stack-pop action. No automatic approval. |
| `kosh_cap` | **`dharita` (धारिता)** | **REJECT as present wording** | `dhārita` means *held/borne/supported*, not automatically **maximum allocated capacity**. Prefer **`kshamata` (क्षमता)** or an explicitly reviewed capacity term; distinguish `kosh_kshamata` from `kosh_aayam` logical length. |
| `kosh_clear` | **`shodh` (शोध)** | **REJECT unless clarified** | This sounds like cleansing/purifying, whereas clear **does not wipe storage** (only length→0). Calling it `shodh` encourages a security false assumption; instead consider a phrase meaning **make logically empty**, e.g. **`kosh_rikta_kuru`**, with a contract that old values remain in backing cells. |
| `kosh_empty` | **`rikt` (रिक्त)** | **Meaning right, spelling/API ambiguity** | `rikta` is a good adjective for empty; the current project already uses `suchi_rikta` / `rakh_rikta` for **clear**, so bare `kosh_rikta` may look like a mutator. Prefer predicate-shaped **`kosh_asti_rikta`** (to be linguistically reviewed) and teach returns 1/0 without mutation. |
| `kosh_peek` | **`iksh` (ईक्ष्)** | **Meaning plausible** | Root `īkṣ` genuinely means see/look, but it doesn't specify last element. Project's **`chay_avalok`** and **`avali_avalok`** are better established non-removing peek analogues. Prefer **`kosh_avalok`** for API family coherence; do not claim this is mandated classical morphology. |
| `kosh_dequeue` | **`apanay` (अपनय)** | **Too generic** | Means taking/removing away; `suchi_apanay` and `chay_apanay` already remove elements in other structures. A queue must remove **first/oldest**; the existing `avali_nishkas` has this FIFO role. Prefer **`kosh_nishkas`**, with exact O(n) and empty-aborts behavior documented. |
| `kosh_enqueue` | **`yuj` (युज्)** | **Lexically good, API-specificity weak** | `yuj` means join/add, but `kosh_enqueue` appends at the back and aliases `kosh_push`; project queue API already uses **`avali_pravesh`**. Prefer **`kosh_pravesh`** if preserving queue-shaped naming. |
| **`kosh_len`** (missing from brief) | **none supplied** | **RECOMMEND a separately approved ninth word** | `vartani_aayam` is the now-established length/extent builtin. Thus **`kosh_aayam`** is consistent for *logical number of elements* (not capacity). This is a naming proposal, NOT an existing function. |

**Scope warning:** The owner has approved a **direction**, not these nine replacements. These recommendations are NOT source changes and MUST NOT be added to working code until the owner signs off the final vocabulary, compatibility strategy, and Sanskrit form. Existing `kosh_` builtins remain the only proven callable spellings.

## Keyword and name collision check: exact names vs semantic confusion

**Direct table read:** `src/sutram_compiler.asm:684-715` contains **32 core ASCII keyword spellings**; `lang/sanskrit.lang` has **58 native mapping rows** including core words, builtin aliases and abbreviation forms. The brief mentions "38 keywords", but the current table extraction has 32 core ASCII `kw_* db "name"` definitions; this number difference **does not authorize inventing or deleting keywords**. Need exact-head parser table acceptance to settle which additional aliases are counted as keywords. Every proposed bare stem (`kshep`, `uddhar`, `dharita`, `shodh`, `rikt`, `iksh`, `apanay`, `yuj`, and the added `aayam`) has **zero exact equalities** with those 32 core ASCII keywords or native pack words, and the full proposed `kosh_*` spellings have **no current builtin table entry**. Current `kosh` alone **is** a keyword, but the compiler's proven whole-token lexer permits longer identifiers with that prefix.

**Semantic collisions, despite zero lexical collisions:** `shodh` risks suggesting erased memory; `rikta` can mean a clear mutator or empty predicate in existing families; `yuj` can be mathematical addition or collection union; `apanay` is nonspecific about FIFO vs stack removal; `kshep` and `khip` differ in morphological type and teaching consistency. No syntax error from a keyword collision implies no semantic ambiguity.
