## Decisions first

1. **HOLD release qualification for the affected compiler.** A reported ordinary terminating loop that becomes infinite is a semantic-correctness blocker, even if every accessed address is mapped. Do not ship v1.0 from this candidate on the existing gate totals alone.
2. **The missing obligation is preservation of live source values and control flow across emitted operations.** Memory-boundary testing and unchanged-output comparisons on other inputs do not establish it. A golden test containing this reproducer with an independent expected result and a timeout could detect it; the mechanism is not intrinsically incapable of doing so.
3. **Add a production-mode builtin state-preservation gate.** The pinned compiler has **44 distinct builtin IDs**, including **43 returning operations and one terminating operation**, represented by **45 rows in `bn_table`** because `kosh_enqueue` aliases `kosh_push`. This is not the 305-function library count. Proposed first matrix: **519 template instances per applicable build profile**, before operation-specific branches and overloads.
4. **K0 cannot repair incorrect code generation.** Keep its source-language scope separate from backend correctness. Do not turn a temporary compiler defect into a permanent rule banning allocation in loops. Until a verified repair, withhold the affected compiler/profile or explicitly disable the affected lowering under a tested fallback; do not advertise the future block as safe.
5. **Additional source-confirmed gate weakness:** `tools/guard_page.py` discards subprocess exit codes and derives suite success from selected text totals. This must fail closed or explicitly classify approved exclusions. It is not established as the cause of the loop bug escaping, but it weakens the reliability of the aggregate green signal.

## Evidence boundary

R142/v420 report that the supplied `yavat` program prints `i=0` repeatedly, that the branch-only and allocation-before-loop controls work, and that moving allocation after increment also changes behavior incorrectly. That is the symptom evidence. I have **not** reproduced it, identified the exact corrupted register, or verified a repair. In particular, a live-value symptom does not prove that the defect is specifically an emitted-machine register clobber rather than a bad stack slot, compiler-side state corruption, branch patch or another lowering mistake. [R1,R2]

The report's assertion that no existing test holds a variable across an allocation is **not an independently reconstructed whole-tree coverage census in this review**. The supported narrower conclusion is that the reported successful gates did not expose this particular allocation/control-flow/live-state interaction. Counts alone cannot tell which interactions or allocator branches were exercised.

The source explicitly separates compiler procedures, generated byte templates and target modes. `src/sutram_compiler.asm` states a compiler calling convention; `.ge_call_nirm` evaluates the argument and invokes `emit_nirmmita_from_rax`. `r65_arena.inc` supplies persistent/reservation/fallback emission and disables the arena under `GUARD_PAGES`. Treat host-compiler register preservation and generated-program preservation as **two different obligations**, not one ABI slogan. [R3,R4]

## WS1 — the shape of what the evidence cannot see

### The demonstrated class

**Semantic miscompilation across a composition boundary:** source says operation B may allocate memory and produce a pointer; target code also changes unrelated live state or progress. An unaffected loop counter must retain its value until the source increments it. Changing it can produce wrong results, wrong addresses later, or nontermination without any immediate memory-boundary violation.

A memory-access detector answers whether an executed access touches a forbidden region. It does not, by that fact alone, answer whether `i` is still the value required by the source. A differential guard answers whether two executions agree on the covered inputs and observables. Agreement can preserve the same old bug or omit the triggering composition. A collection of individual construct examples does not establish that their composition preserves state.

**One demonstrated bug class is not evidence of a known total number of undiscovered classes.** For this project I propose the following **eight review obligations**. They overlap and are an engineering organization, not a theorem that exactly eight bug classes exist or a claim to have discovered eight defects.

| Obligation | Failure shape | Why the currently cited evidence is insufficient by itself |
|---|---|---|
| 1. Live-state/frame preservation | Wrong register reuse, stack-slot reuse, binding identity, emitter scratch state, or argument/result save/restore changes an unrelated value. | No relevant live value may be observed across the selected operation/path. All accesses can remain in bounds. This is the reported symptom family. |
| 2. Control-flow and progress | Wrong branch/loop target, join state, early exit, iteration count or return path. | A test that never takes the edge cannot check it. A bounded source loop needs both a value oracle and a completion oracle. |
| 3. Representation and numeric meaning | Integer/float conversion, sign extension, width, argument/result location, or mixed-class value handling changes a result. | Memory can be valid while its interpretation is wrong; small homogeneous examples may hide it. |
| 4. Effects, order and alias semantics | An operation executes twice, evaluates arguments in the wrong specified order, changes the wrong object, or changes sharing without approval. | A final checksum or unaliased example can miss different observable state. Preservation must exclude permitted effects, not all memory changes. |
| 5. Failure-path atomicity and recovery | Failure leaves partially published state, broken cursor/header, lost live values or wrong status. | Happy-path executions do not cover reserve failure, fallback failure, empty cases and uncommon exits. |
| 6. Spatial access and logical bounds | Under/over-read, under/over-write, terminator, subobject or logical-length violation. | Guard pages cover only executed protected boundaries and can miss lower/logical boundaries. Earlier R140/R141 work remains relevant. |
| 7. Lifetime, initialization and resource behavior | Stale reference, reused uninitialized bytes, retained allocation growth, or resource exhaustion under a finite working set. | Accessible memory can have the wrong lifetime/value; short successful runs do not establish bounded resource use. |
| 8. Target/build/composition equivalence | Direct versus linked output, ELF versus PE, different runtime adapter, or instrumentation substitution exercises different lowering. | A passing replacement allocator or one target is not coverage of a disabled production path or another target. |

There are also **five evidence failure modes**, distinct from compiler bug families: absent stimulus, weak/missing oracle, instrumentation that removes the suspect mechanism, shared-bug differential baselines, and aggregation that loses failures/skips. This incident principally illustrates the first three; the wrapper finding below supplies a concrete aggregation concern. Do not infer every obligation above is currently broken.

### Important correction to “none of the gates could have caught it”

`tests/run_tests.py` executes compiled positive tests with a timeout and compares stdout/exit to goldens. If the precise reproducer had a correct independently specified expected result and was routed through a correctly enforced parent result, an infinite loop would be a failure. The current blind spot is **coverage of the relevant composition and faithful observation**, not that output testing can never detect state corruption. [R5]

The new guard-page build still disables production arena/extension paths (`GUARD_PAGES`). Thus adding the reproducer only to that configuration can miss a production-only defect. Its embedded native execution/oracle could detect some wrong-value defects, but memory protection itself does not check values. Run the production binary too. [R4,R6]

### Additional concrete finding — parent status is discarded

`tools/guard_page.py` defines `run()` as `subprocess.run(...)` followed by returning only `r.stdout + r.stderr`. It does not return `r.returncode`. Its suite branch looks for `PASS=(...)` and `FAIL=(...)`, treating absent FAIL as zero. Meanwhile `tests/run_tests.py` intentionally returns nonzero for `NO-EXPECTATION` as well as failures. [R5,R6]

A small local regex check with the synthetic summary `NO-EXPECTATION=4  PASS=225` produces a zero suite-failure increment in the wrapper's displayed logic. The child may have returned 1, but that value is unavailable to the wrapper. **This is a text/status demonstration, not a rerun of the repository tool or a claim that a particular reported execution was corrupt.** A reviewed exclusion list could legitimately classify known missing expectations; silently discarding the whole child status is not such a list.

Required disposition: carry subprocess return code, timeout/signal, case manifest and structured outcome through every wrapper. Reject missing/malformed summaries, unexpected empty control sets and lost cases. Classify expected compiler refusal, expected child failure, positive execution, approved exclusion and infrastructure failure separately. A deliberately failing negative child is allowed only when its own expectation matches. Do not replace this with blindly requiring every individual child to exit zero.

## WS2 — evidence that would have exposed this failure

### A. Freeze the original counterexample, then its semantic neighborhood

Keep Sarvam's exact program as a positive regression with expected semantic trace **0, 1, 2, then done**, preserving its original printing placement. Use a child-process timeout and bounded output capture: a test that prints forever must not exhaust the test runner's memory. Do not regenerate its expected output from the broken compiler.

Also retain the described control placements: allocate before the loop, inside a taken branch, before increment in the loop and after increment. Add a no-intermediate-print version whose final state is observed only after the loop. Printing or extra helper calls can themselves change register allocation, spilling and state exposure; a diagnostic print is not always an inert observation.

**Not a test per construct alone:** the crucial combination is `live values × builtin/effect path × surrounding control flow × build mode`. Both a tiny exact reproducer and a systematic property are needed. Mutation controls should establish that the gate actually rejects this historical bad compiler, a deliberately wrong expected result and a timeout. Those controls are proposed, not executed here.

### B. The preservation property

For a returning builtin B with evaluated arguments, let `L` be the source bindings live both before and after B, and let `Allowed(B)` describe its specified writes/effects, including mutations reachable through allowed aliases.

```text
For every v in L not explicitly assigned and not affected by Allowed(B):
    source_value_after(v) == source_value_before(v)

Also check:
    B's result and specified effects are correct;
    object identity/contents outside the allowed footprint are preserved;
    each specified branch/iteration/return is taken the right number of times;
    a bounded positive fixture terminates with its expected status.
```

Do not require every physical register to remain unchanged: caller-clobbered registers may be used if live source values are saved/reloaded correctly. Do not require a mutating builtin to leave its legitimate destination unchanged. A `kosh_push` alias case needs the owner's actual approved sharing contract; it cannot be swept into “all variables unchanged.”

Use independent runtime inputs and distinct nonzero integer values, exactly representable binary64 values and preexisting valid pointers. For example, 104729, -13007, 3.25 and -6.5 are distinguishable witnesses; avoid all-zero state. Keep arithmetic within the intended range, make pointers live by using their contents after B, and check values individually rather than relying on a cancelling sum. Include parameter, local and module-global bindings in the applicable contexts.

### C. More than one oracle

1. **Source-contract oracle:** a small host-side model predicts scalar values, authorized memory changes, operation counts and termination for the generated templates. It does not use the same emitted code to compute its own expected answer.
2. **Metamorphic companions:** preserve semantics while renaming/reordering independent declarations, altering live pressure, or replacing a straight-line repetition with a three-iteration loop. Only use transformations whose equivalence is established for the specific operation; do not reorder side-effecting calls or treat allocation as pure.
3. **Differential execution:** compare appropriate v261/v263/v264/fixed candidates, production and instrumented configurations, and output modes. Agreement is supporting evidence, not the oracle when both versions can share a defect. Pointer addresses, handles and approved alias differences need explicit treatment.
4. **Targeted emitter/ABI review:** after Claude isolates the cause, trace live compiler registers and emitted registers/stack/flags around that helper and its siblings. A focused machine-code sentinel test or emission-state invariant can catch violations masked by a particular source register allocation. Do not infer a specific bad register from the symptom alone.

The same logic applies to a future K0 checker: accepting source syntax is only one layer. A backend preservation obligation connects the accepted source behavior to the generated executable.

### Obligatory scenario expansions beyond the base matrix

- **Allocator:** first reservation, warmed fast path, exhausted-arena fallback, forced reservation/fallback failure, zero and boundary requests. Preserve live state through each reachable branch. The property must use the production allocator, not only `GUARD_PAGES`.
- **Printing and signatures:** `likha`'s value/float/string forms, 1–6 arguments, and its distinct three-argument raw-write interpretation; `dvaram` 2/3 arguments; `aksharank` 1/2. One happy-path call per ID does not cover these dispatch paths.
- **Collections:** empty/nonempty outcomes, typed integer/float forms where supported, spare capacity, in-place growth, forced copy growth and failed growth. Owner-approved alias effects must be explicit. Existing invalid parameter-growth refusal is separate from successful local growth.
- **Memory/text:** byte versus qword width, zero/exact lengths, legal alias/overlap domains, terminator requirements and pointer-return forms. Do not manufacture undefined/contract-invalid inputs and then call every failure a miscompile.
- **I/O/network:** isolated temporary files, deterministic stdin and parent-coordinated loopback only. Prepare enough valid descriptors/connections for repeated operations; closing the same descriptor repeatedly is not a valid preservation fixture. Time-bound all blocking operations. Missing sandbox capability is BLOCKED/UNSUPPORTED, never silent PASS.
- **Control-flow expansion:** `chakra`, `kuru`, short-circuit/conditional expressions, nested call argument evaluation, return/failure propagation, and live expression temporaries. Six contexts are the first batch, not a claim to cover every control-flow edge.

A scalar-returning wrapper can observe an operation that otherwise mutates state; its adapter must preserve the operation's real effect semantics. Preparation/cleanup may themselves call builtins, so label them and validate their contracts rather than blaming the tested operation for an invalid fixture. Avoid observer calls between B and the first state check where they could hide the failure; retain both immediate-check and delayed-observation versions.

### Build profiles and recording

Start with **native Linux direct production output**. Reuse appropriate cases for Linux object/link and separate compilation, because the source says these share the arena path. Add native Windows for the shipped supported subset; the owner owns that execution. PE parsing and Wine do not stand in for real Windows. Run guard-page output as a complementary mode with its layout/alias differences documented. Do not multiply 519 by every mode and claim those executions occurred. [R4,R7]

Per case record: source and input hash, expected outcome/effect manifest, compiler source commit and binary hash, target/mode, generated binary hash, executed branch evidence where instrumented, stdout/stderr, exit/signal, timeout, and exact state discrepancies. Distinguish successful compile, expected compile refusal, native execution, infrastructure failure and unrun cases. A source fixture compiled and rejected has not exercised live-value preservation at runtime.

## WS4 — K0 and allocation inside loops

**Does K0 have to forbid `nirmmita` in a loop permanently? NO.** Repeated, bounded scratch use is a legitimate purpose of the proposed feature. A backend bug is not a sound language-design reason to prohibit that composition forever.

**May the affected v264 binary be called a safe K0 compiler meanwhile? NO.** The pinned source says scratch cursor state is reserved but unused and `mandapa` does not exist yet. Neither its bump allocator nor a paper checker establishes a shipped checked-block safety property. Do not credit rejection of an unknown keyword as a working escape check. [R4]

The future assurance chain is:

```text
accepted source satisfies the K0 restrictions
    AND the checker correctly enforces those restrictions
    AND lowering preserves their value, control-flow and memory semantics
    AND the relevant target/link/runtime assumptions hold
    => the stated checked-subset guarantee
```

A value-provenance checker can reject an escaping scratch address while a broken emitter still overwrites a live counter, omits cleanup or damages the scratch cursor. Restricting `kosh` narrows the source problem; it does not verify the compiler implementation. Test source-checker rejection/acceptance and native backend preservation separately, including both persistent and future scratch paths, all exits and recursion only where supported.

**Temporary release policy:** keep the stop on the affected candidate until Claude's exact repair is reproduced, independently expected, calibrated against the bad case and accompanied by sibling/path preservation checks. A narrowly documented temporary rejection or disabled optimization is a possible containment choice, not a proof of v1 adequacy. Do not assume reverting to v261/v263 is safe without running the same reproducer and controls there. A later fix must be assessed at its own commit; this pinned review does not certify one.

**Reference wording remains:** `mandapa` is planned opt-in fixed-size numeric scratch, not the complete memory model and not unrestricted vector processing. Once implemented, its safety claim must name the checked subset, verified compiler/target and assumptions. Do not weaken that scope to compensate for a compiler defect, and do not broaden it because a new test count is green.

## Release recommendation

**Current gate set alone: NOT ADEQUATE to release the reported affected v264 as v1.0.** Keep the useful existing gates, correct their result propagation, and add the builtin preservation/effect property. Close the exact regression and its demonstrated mechanism, not merely one printed symptom. Completion means an evidence record against the actual release candidate; it does not mean promising an exhaustive proof from a finite matrix.

This incident does not invalidate every earlier measurement. The measurements establish what their inputs, oracles and configurations actually checked. The release claim exceeded that scope. The remedy is traceable semantic obligations and adversarial calibration, not replacing one impressive aggregate count with another.
