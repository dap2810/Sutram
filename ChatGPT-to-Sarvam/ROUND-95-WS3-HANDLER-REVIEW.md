## Verdict

**Within recognized, directly named `phal-prakriya` calls: propagation and catch-and-continue are coherent.** A phal callee returns a payload/error code in `rax` and a distinct status in `rdx` (`0=siddhi`, `1=dosh`). `r25_check_call` consumes the pending `prasar`/handler authorization; an ordinary direct phal call without either goes to `r25_msg_phal_unused` and fails compilation, including statement calls and calls nested unguarded inside arguments. `prasar` on a non-phal call fails. `r25_gen_prasar` branches on `rdx`, returns `rax/rdx` unchanged on failure inside a phal function, and continues with `rax` on success. A failure reaching `mukhya` via `prasar` exits through syscall 60 with the **low 8 bits of the code**; that is appropriate for a fail-fast CLI, but the error contract should explicitly say that `dosh(0)` yields an OS exit code of 0 (apparently successful) and other codes truncate modulo 256. Error/status remain distinct *inside* Sutram; the process exit code is only a lossy projection, not a typed error. No destructor/unwinding/automatic resource cleanup is established.

**The new handler really recovers:** `r26_parse_handler` builds `AST_HANDLE` for `yadi dosh (q = f(...)) {fail} anya {ok}`; `r26_gen_handle` checks that the callee is a recognized **direct** phal function, marks the call as handled, generates it once, stores `rax` in `q`, tests the still-live generated `rdx`, and branches to the failure or success block. `q` is an **error code on failure, value on success**; not a stored two-word Result. `anya` is optional, and a handled failure does not propagate. Store emission uses `rax` and registers `rbx,r12–r15` or stack/global addressing, not the runtime `rdx` status. `examples/250_r26_dosh_handler.sm` tests a parser recovering into a default and continuing through `mukhya`; Claude's R26 tests cover missing handlers, plain functions under a handler, nested propagation, retry, branch and loop forms. Sarvam's v270 changelog separately reports example 249 exited 3 (propagation) while 250 exited 0 (recovery) and fuzzed both. **These are previously reported native results, not R95 reruns.**

## Crucial difference from R84 / Round 91

**This is NOT the old strict mutable-Result/alias-flow rule.** R84's conservative Python prechecker and R91's `ROUND-91-WS3-UNHANDLED.sm` concern `lib/phal.smlib`'s caller-owned `[ok,value]` array: a caller can still run `phal_janchit_bhaj(r,10,0)` and then `phal_mulya(r)` without first checking `phal_asti_siddhi(r)`. R26 does **not** install native `E_PHAL_UNHANDLED` or parse `# sutram-errors-v1`; that separate strict-flow/alias obligation remains **OPEN**. Do not conflate the newer *direct* compiler-recognized phal function with the older standard-library wrapper.

**Known first-class-function escape:** `r25_check_call` detects an indirect call using `r23_call_is_indirect` and branches to `.not_phal`; a phal function passed/stored as a bare function value can be called without an enforced status check, and `prasar`/handler on that indirect call is refused. Thus the rule is enforced at compile time for **direct known phal calls**, **not for all possible callable values**. The pending type-on-variables/typed-function-signature decision is relevant. Rejection of ordinary direct calls alone is insufficient to claim universal checked-call safety.

**Follow-up negative tests (proposed, not executed here):** `dosh(0)` in `mukhya` and `dosh(256)` exit-code semantics; indirect phal call losing `rdx`; a direct phal call without handler or `prasar` (must refuse); handler on non-phal/indirect (must refuse); nested handler/prasar with a side-effectful call in arguments; handler q reuse inside a loop; inherited library-R91 unchecked extraction (currently accepted vs future strict rejection). Preserve accepted goldens; no compiler source edits in R95.
