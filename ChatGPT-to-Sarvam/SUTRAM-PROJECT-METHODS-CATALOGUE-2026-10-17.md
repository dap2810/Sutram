## 1. Recommendation and scope

Use other projects as sources of specific engineering methods: a precise grammar, understandable diagnostics, reproducible examples, documented memory contracts, module boundaries and measured code generation. Adapt those methods to Sutram's accepted pure-NASM implementation and native-output goals. A project written in Rust, Python, Kotlin or C can teach an approach without becoming a Sutram implementation dependency.

This catalogue retains **32 Sanskrit-related entries found during the review**, including implementations, published packages, research, announcements and one unverified lead. It is a record of the projects found, not a claim to enumerate every Sanskrit project worldwide. Six additional compiler/language references and three Sanskrit language-processing tools appear separately.

**Evidence boundary:** repositories, package documentation, papers and first-party project pages were inspected. No external compiler or example was built, executed or benchmarked for this catalogue. “Source available” means inspectable source was found; it does not establish production readiness, complete implementation or successful execution. Repository descriptions of speed, safety, intelligence and portability are not independent measurements.

The “method to study” and “Sutram application” columns are recommendations. They distinguish an observed design from an adaptation we propose. Before copying source, select a concrete upstream revision and inspect the applicable license, attribution requirements and dependencies. Studying an idea does not require importing the implementation.

The implementation assessment for our own project is pinned to Sutram main `ca53eab710059eb574f1f19c64018b5eaedec1a8` in the companion advisory. This catalogue does not change that baseline or approve pending compiler work.

## 4. Six additional compiler and language references

These are supplementary engineering references, not additional Sanskrit programming languages and not instructions to replace the NASM compiler.

| Reference | Method worth studying | Sutram application and acceptance evidence |
|---|---|---|
| **[Rust](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html)** | Explicit ownership, moves, borrowing and destruction rules expressed as language contracts. | Define who owns a `kosh` allocation, whether aliases are allowed, what growth invalidates, how cleanup works and which programs must be rejected. A complete Rust-style borrow checker is a separate design decision, not a property that follows from adding an unsafe keyword. Verify both valid programs and prohibited alias/use cases. |
| **[Zig](https://ziglang.org/documentation/master/#Memory)** | Explicit allocators, allocation lifetimes, arenas and auditable error cleanup. | Specify Sutram allocation/free behavior and failure handling. Test repeated growth, retained mappings, alias behavior and allocation failure. Prove the chosen cleanup contract on generated programs; a helper-level free test does not establish end-to-end resource correctness. |
| **[chibicc](https://github.com/rui314/chibicc)** | A small compiler organized around understandable parsing, typed syntax and native code generation, developed through complete language increments. | Make each Sutram change traceable from source syntax through semantics to emitted behavior. Study scope, aggregate layout and ABI cases as needed. The useful method is complete, reviewable increments; this does not require copying chibicc's C implementation or its project-history conventions. |
| **[GCC](https://gcc.gnu.org/onlinedocs/gccint/Passes.html)**; [optimization options](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html) | Explicit compilation-pass responsibilities, legal transformations and separately configurable optimizations. | Document the preconditions and preserved semantics of each Sutram optimization. Add correctness cases before speed claims, then measure representative workloads with pinned flags and identical outputs. Do not assume enabling an optimization improves every workload. |
| **[LLVM](https://llvm.org/docs/CodeGenerator.html)**; [IR language reference](https://llvm.org/docs/LangRef.html) | Separation of language semantics, intermediate representation, target lowering, register allocation, stack frames and object emission. | Study these interfaces when native code generation grows beyond maintainable direct emission. An internal representation implemented in NASM is an option to evaluate; LLVM itself is not a required backend. Linker/module formats still require an explicit Sutram contract. |
| **[QBE](https://c9x.me/compile/)** | A compact compiler backend using SSA and a deliberately bounded set of optimization and code-generation techniques. | Study whether a small internal representation, simple constant/copy propagation and clear ABI handling would simplify Sutram. Adopt only a pass justified by a concrete workload or correctness need. QBE's own promotional size/performance comparisons are not Sutram measurements. |

The closest references serve different purposes: Rust and Zig inform resource contracts, chibicc informs manageable compiler growth, GCC informs optimization discipline, and LLVM/QBE inform internal boundaries and target generation. They are not a vote to implement all of their features.

### A repeatable adoption process

1. **Choose one problem.** For example: imported-file error locations, growth invalidating aliases, or two modules that must link.
2. **Read one relevant implementation or specification.** Record the upstream revision and what was actually inspected. Check the applicable license before copying source.
3. **Write a Sutram contract.** Define accepted syntax/inputs, observable behavior, error cases, compatibility and target/profile limits.
4. **Implement within the accepted architecture.** Preserve pure NASM and existing accepted behavior. Introduce a new subsystem only when the contract needs it.
5. **Verify generated programs.** Include negative cases, boundary cases and regressions. Keep helper tests and full compiler/program acceptance distinct.
6. **Measure the desired improvement.** Choose a metric suited to the claim: error-location correctness, module scale, retained allocation, binary size, execution time or completion of a first-program task.
7. **Publish evidence and synchronize documentation.** Give the owner exact revisions, commands, results and remaining limits. An uploaded plan or source file is not proof that the behavior has shipped.

## 7. What this handoff does and does not establish

This is an actionable reading and development catalogue. It does not establish that Sutram is already faster, safer or more mature than the listed projects. The defensible opportunity is to combine native output, a precise multilingual core and dependable tools, then demonstrate the claimed advantages with reproducible evidence.

All external statuses are based on material consulted on 2026-10-17 and can change. Papers, project self-descriptions, package metadata and repository source have different evidentiary weight. Recheck the specific source before committing engineering time.

This delivery adds documentation only. It does not train a model, change the compiler, run a benchmark, issue a new numbered implementation round, or establish that Sarvam has read or accepted the recommendations. The sender will verify the uploaded files before reporting completion to the owner.
