# Sutram ROUND-92 WS2 — Does the proposed compile-once module system fit today's compiler?

**Answer: only its source-level module graph and export surface fit. Genuine separately compiled modules REQUIRE a new object writer, relocation format and linker/driver.** This is architecture work, not a small safe R92 change. **Implementation: NOT_STARTED; native tests: NOT_RUN.** Inspected accepted v261 `src/sutram_compiler.asm` Git blob `1f6377e35897a467e2ae5781433f84d933a7886a` and R23 `src/r23_capabilities.inc` blob `664964d38e894e89aac8e96c79e13a21472b646d`.

## What is already there — correction to our Round-91 design

1. **`# sutram-module-v1` is ALREADY active**, not a new switch to invent. `src/sutram_compiler.asm:754` stores this marker; **2290–2313** sets `mg_root_exact_v1` and then calls `check_module_graph`. The existing behavior is precise module-cycle/missing/alias checking, not binary object emission.
2. **`niryat` export declarations are ALREADY parsed by the module-graph prepass.** See **3074–3084** (v1 export/private contract), **3596–3707** (`mg_parse_niryat`), **3780–3795** (export validation), and **2988–2990** (`ns_strip_niryat` removes export lines before later lexical processing). Thus R91 calling `niryat` an entirely *new* declaration was too broad. It is **existing preprocessor syntax, not a general normal parser keyword**. Reuse its semantics if approved; do not introduce a conflicting duplicate directive.
3. **`yoj` still expands source text.** `expand_imports` and `expand_imports_pass` at **2527–2558** produce an import buffer; **3055–3063** copy it into `source_buf` before compiling. A bounded graph may detect cycles and duplicate aliases first, but it does **not** compile independent objects.
4. **Internal-only references:** `backpatch_calls` (**11958–12032**) walks `patch_list`, resolves into the one `func_table`, and patches rel32 offsets inside one `code_buf`. The current **`write_elf` at 23309–23377** emits **ET_EXEC=2** (**23328**) with **no section table** (**23336, 23342**) and one program header (**23340**), not an `ET_REL` object with public symbol and relocation tables.
5. **First-class functions make the linkage wider than direct calls.** R23's `src/r23_capabilities.inc:130–168` emits `lea rax,[rip+disp32]` for a function *value* and records that patch in the **same local patch list**. Calling through function values is indirect. An object/link design must retain both direct `E8` calls **and RIP-relative function-address relocations**, or conservatively reject cross-unit function references. The R23 slice view is a two-qword pointer/length descriptor with lexical lifetime; do not allow it to cross module boundaries without a reviewed ABI.
6. **R71 substrate:** `src/r71_module_link.inc` resolves exact qualified export names and patches bounded `E8 rel32` instructions, but explicitly says `Production .sm -> .smo emission is not wired`. It does not replace a loader, full object linker or versioned metadata.

## Narrowest compatible next architecture (NOT this round)

- Keep current `# sutram-module-v1` semantics, `yoj hisab@h` import spelling and `niryat` export visibility unchanged. **Do not hijack that existing marker** to silently enable binary linking. Use an **explicit new build flag** such as proposed `--emit-object`/`--link` or a separately versioned opt-in, with an unchanged legacy path.
- First isolate modules without globals/initializers and with simple, versioned **integer-only direct-call** interfaces. Include module ID, exact exported name and arity, interface hash, target ABI, symbol offsets, and typed relocation records; validate all before emitting executable. New R23 function values, methods and slices **must either be supported with full linkage/type representation or explicitly rejected at module boundaries**.
- Reuse current source graph diagnostics for names/cycles/privacy; replace the **source-flattening emitter path** in object mode with per-unit symbol tables, object serialization and a deterministic static linker. Preserve compiler-source provenance, local declarations and original file/line diagnostics. This is a multi-subsystem feature and requires a separate reviewed implementation phase.
- Only label it a feature when two independent Sutram sources compile into objects, link and print 42, with negative tests for missing/private/duplicate/signature/cycle cases, interface/cache invalidation, Linux/Windows acceptance, old import goldens, and the fuzzer plus crash corpus.

**Round-92 verdict:** Design is compatible with existing **syntax/graph** but **NOT implementable as currently drawn without compiler architecture changes**. Per Sarvam's STOP rule, no module/compiler source edits were made. [The original R91 design](ROUND-91-WS2-MODULE-PACKAGE-DESIGN.md) remains a proposal; this review supersedes its incorrect implication that `niryat` and the v1 marker are wholly new.
