# Sutram ROUND-99 WS1 — The *second-smallest* FFI: what breaks next?

**Status:** design + **actually executed GCC 14.2 host ABI inspection**, not Sutram feature implementation. Source baseline: main `98380b9bd3a2a29775a65018c4172defa0b5a7c1`, project v289, compiler v241. Verified current source: `src/r32_ffi.inc` Git blob `56b83942cc87ac39f693d604a805979e4c569184`, `tests/r32/test_ffi.py` `8cdbc315ae6e7d51917f83bc416b140f1dd3e28e`, converter `linker/sutram_elf2smo.asm` `591011aaaad62d7b42ad1cb820df992499e686d6`.

**Current contract:** `sutram-ffi-v1|linux-x86_64-sysv` + `name|arity|i64,...|i64|symbol`; strict v1 parser in `r32_load_sidecar` accepts **only i64 arguments and i64 return**. It deliberately rejects `f64`, `ptr`, `void`, aggregate and Windows target records (R32 tests demonstrate those refusals). **Structurally there is already an argument-kind field and return-kind field**, so the first three need **new accepted kind tokens + type checking + ABI codegen**, not extra columns or a new `SUTRAMO1` symbol/relocation table. A versioned `sutram-ffi-v2` / feature profile is preferable to silently advertising a richer ABI under the old v1 header. **An ELF `STT_FUNC` symbol never provides C argument/return types**: matching names is not ABI compatibility proof.

## Priority by expected Linux foreign-library use (not implementation ease)

| Priority / case | Does the current sidecar layout suffice? | What must change before an actual Sutram call is safe? | First scoped milestone |
|---|---|---|---|
| **1. C string or pointer (`const char*`, `void*`)** | **Yes for opaque `ptr` kind**, already a proposed token but rejected by v1. **No** for a checked C-string lifetime/encoding contract: may need `cstr` or explicit `ptr,len` semantics. | Pointer still travels through SysV **integer registers** (`rdi,rsi,rdx,rcx,r8,r9`): **no new register class** for an already-valid address. But Sutram must verify provenance, allocated/readable length, lifetime, NUL termination where C expects `char*`, embedded-NUL behavior, mutability, ownership/free and no escaping temporary/movable buffers. Without a pointer/type model, do not accept arbitrary `i64` as a safe C pointer. | `ptr + explicit length` read-only, caller-owned, no retained pointer, with a negative out-of-bounds/expired-pointer contract test; expose any raw-pointer operation behind a deliberately unsafe API. |
| **2. `void` return** | **Yes**, existing return-kind field can spell `void`, but v1 rejects it. | C has **no specified useful return value in `rax`** for `void`. The Sutram parser/type checker must allow a foreign call as a **statement**, reject use in arithmetic, assignment, `likha`, etc.; codegen must not interpret `rax` as a return value. Side effects need explicit pointer/resource handling. | `s_notify(42)` as a statement, `likha(s_notify(42))` compile **FAIL**; no silently synthesized zero. |
| **3. `dasham`/C `double` (`f64`)** | **Yes**, `arg_kinds`/`return_kind` support an `f64` token structurally; **actual v1 parser currently refuses it**, so accepted grammar version/profile and record storage must change. | SysV scalar double arguments are in **`xmm0`–`xmm7`**, with integer arguments counted **independently** in `rdi,rsi,rdx,rcx,r8,r9`; mixed `(i64,f64,i64,f64)` uses `rdi,xmm0,rsi,xmm1`, not four sequential integer slots. `double` returns in **`xmm0`**, not `rax`. The existing Sutram `dasham` values must be passed in the correct register/bit representation and result must preserve binary64 semantics. | C `double add(double,double)` then mixed int/double call and float return; test exact bits/NaN/-0 and stack alignment. |
| **4. Struct by value** | **NO** for general structs; the current flat list `i64,ptr,f64` cannot specify field layout, alignment, size, nested aggregates or ABI classes. | Needs a **versioned structured signature/layout contract**, by-value marshalling, SysV eightbyte classification (INTEGER/SSE/MEMORY and combinations), stack slots/alignment, and possible hidden return-storage pointer. **Do not** guess that “struct = pointer”. | First ban by-value structs; later one approved 2×i64 struct and one >16-byte stack aggregate with checked layout and compiler/link tests. |
| **5. Windows x64 deployment** | **Header/target must change** (`linux-x86_64-sysv` is deliberately Linux-only). Per-record five-field layout may be reused for scalars, with new target/ABI ID and possibly explicit calling-convention rule; complex aggregates need richer layout. | **Different calling convention**: first integer args in `rcx,rdx,r8,r9`; floating args use `xmm0`–`xmm3` by **argument position**; caller reserves **32-byte shadow space**, meets stack-alignment and nonvolatile-XMM rules. Requires PE/COFF foreign-object ingestion, correct relocation/import strategy, Windows Sutram object emission/linking and actual **native Windows** verification; a Linux ELF C `.o` cannot simply be linked into PE. | After the owner-run real Windows baseline, one integer-only Windows `extern` call using a verified COFF input and project-owned PE link, then floating/pointer cases. |

**Windows is an immediate platform blocker for a Windows-first user even though it ranks fifth by *Linux C API signature frequency*; prioritize it separately in the Windows release roadmap.** Not all pointer/C-string APIs are safe just because their ABI register position matches i64. `void` is the smallest codegen/return-type extension, but pointer/type semantics are the most common ecosystem boundary.

## New measured GNU/Linux ABI control, NOT Sutram

[Exact C input](ROUND-99-WS1-ABI-HOST-CONTROL.c) and [raw GCC/objdump output](ROUND-99-WS1-ABI-OBSERVED.txt) were genuinely compiled on Linux x86-64 with **GCC 14.2, GNU objdump 2.44**, `-O2 -c -ffreestanding -fno-pic -fno-pie -fno-stack-protector -fno-asynchronous-unwind-tables -fno-unwind-tables`. **8/8 host checks PASS; zero relocations** for these simple functions.

| Actual observed instruction | ABI implication |
|---|---|
| `r99_f64_add: addsd %xmm1,%xmm0; ret` | double parameters/return in XMM |
| `r99_mixed: add %rsi,%rdi`, `addsd %xmm1,%xmm0` | integer and SSE argument slots allocated independently |
| `r99_pointer_sum: movzbl (%rdi),%edx` | pointer is address in RDI and is **actually dereferenced** |
| `r99_void_store: mov %rsi,(%rdi); ret` | no return value contract |
| `r99_pair_sum: lea (%rdi,%rsi),%rax` | small 16-byte 2×i64 struct passed in two registers |
| `r99_big_sum: mov 0x10(%rsp),%rax` etc. | 24-byte struct passed on stack |
| `__attribute__((ms_abi)) r99_ms_abi_add: lea (%rcx,%rdx),%rax` | Microsoft x64 integer argument registers differ from SysV |

GCC control SHA-256 `c39c8d1a617ced6641a6a00c063307df7582e847d8c029333562aeccbb1174e0`, compiled ELF `32651448ce4de28f803420922a0c2b8f309a740415000c49a316dddd00cd41fc`, raw output Git blob `7b009718ede72da52529c7782293d3ddb7ba9271`. **One check initially falsely read the `nop` padding after `ret` as the body of the `void` function; the test check was corrected to stop at `ret`, then passed 8/8.** This is a checker correction, not a compiler defect. ## Compatibility/engineering decisions for Claude

1. **Never silently reinterpret a v1 `i64` signature as `f64`/pointer/void**. Prefer a versioned accepted sidecar feature profile, explicit type-checking and finite negative cases before allowing the kind in codegen. Tests must assert wrong-kind rejects, not only wrong-arity.
2. **No automatic direct C string marshalling via `i64`**. Specify lifetime, NUL, encoding, buffer size, mutability and cleanup before enabling pointer-friendly standard library APIs.
3. **Separately gate Windows**: the ELF reader and Linux SysV stack shim cannot supply the MS ABI or PE object importer.
4. Keep **`SUTRAMO1` v1** unchanged for direct integer-code relocations where possible, but update interface metadata/version if aggregate ABI, symbol type contracts or cross-language signatures need it. No missing symbol may become a fake stub.
5. The first stage-2 feature should be **one narrowly typed `void` return or simple binary64 float**, chosen based on current compiler support; write positive+negative native tests *before* promotion. **All these native stage-2 features: NOT_IMPLEMENTED / NOT_RUN in R99.**
