# ROUND-100 WS1 — FFI's next meaningful pointer/string contract (not a repeat of R33)

**Source pin:** `main` `6ed4d11a3f787de4d5791430c506c42f090ba1aa`, project log v294, compiler v242. R100 was issued against v291 **before Claude R33 implemented `ptr`, `f64`, `void` and R33 tests/fuzzers**. Therefore the old "enable a `ptr` argument" is ALREADY DONE. The next useful top-priority deliverable is a **checked, size/lifetime-aware pointer/string boundary**, not another generic `ptr` token. **Design only**; no accepted `v2` syntax or compiler changes in R100.

## Existing behavior — do not erase

`src/r32_ffi.inc` accepts `sutram-ffi-v1|linux-x86_64-sysv` and five fields `local|arity|arg_kinds|return_kind|foreign_symbol`, with `i64,f64,ptr` args and `i64,f64,ptr,void` results (introduced in R33). `ptr` accepts a string address, kosh element pointer **or integer**, and `tests/r33/test_ffi_kinds.py` exercises C reading strings/kosh and writing kosh. A `dasham` provided where `ptr` or `i64` was declared now raises located `E_FFI_KIND` with no object. This is **ABI passing**, not a proof of pointer provenance, buffer size, terminator, lifetime, or mutability. `ptr` results are currently treated as integers; do not claim memory safety. The Linux X86-64 SysV pointer value uses the same 64-bit integer register sequence as `i64`; no distinct floating register class. Ordinary compiler path must remain byte-identical.

## Proposed sidecar v2 — exact bytes, no new column; new KIND semantics

**Header**, byte-for-byte ASCII, LF required: `sutram-ffi-v2|linux-x86_64-sysv\n`. Same v1 record shape: `local|arity|comma-separated arg kinds|return kind|ELF symbol\n`; no BOM/CR/space/comments, at most 8192 bytes, 64 records, arity single ASCII digit `0..6`, strict local ASCII identifier 1–63 and ELF symbol 1–127, duplicate local/external disallowed. V1 stays frozen with its current accepted meaning and bytewise parser; **do not silently recast a legacy `ptr` declaration into a safe buffer**.

First new kind is **`cstr_ro`**: `s_strlen|1|cstr_ro|i64|sutram_strlen_checked\n`. ASCII bytes `63 73 74 72 5f 72 6f`, no trailing spaces. The compiler must accept only a known Sutram string whose **backing storage contains a NUL within the allocated buffer**, remains alive/stable for the duration of the synchronous call, and is not freed/reallocated/moved during it; prohibit passing a raw integer, kosh or arbitrary pointer to `cstr_ro`. C can observe only up to the first NUL; explicitly reject/define embedded NUL semantics, and document the encoding (Sutram UTF-8 bytes, C function accepts bytes). Treat it as **read-only**; a C callee that writes through the pointer violates the contract. No implicit conversion of arbitrary Unicode to UTF-16. If source string storage cannot prove the NUL/storage stability, **compile error or a reviewed temporary copy with proven lifetime**, not a guessed address.

Second useful, separately staged kind is **`buf_ro@2`**: `s_sum|2|buf_ro@2,i64|i64|sutram_sum_bytes\n`. The literal `@2` binds arg1 pointer to **arg2's byte count** (1-based indices). Parser v2 can recognize `buf_ro@N` where N is a one-digit argument index `1..6`, different from the pointer argument and whose declared kind is `i64`; disallow forward ambiguity/duplicates and require **length >= 0**. The compiler's checker must verify the underlying source is an owned/pinned contiguous byte buffer (not assume that `kosh` of 64-bit elements has length in bytes), calculate `len ≤ allocation_extent - offset` with checked math, and reject out-of-bounds or lifetime/mutability conflicts. `buf_rw@2` is **NOT approved** until alias/ownership and writeback rules exist. For v2's first real native milestone implement **`cstr_ro` only** and fail closed on `buf_ro@N` until its source buffer-length/type model is genuinely implemented. These proposed kinds keep the five-field layout but change the **accepted v2 grammar**, not `SUTRAMO1` v1 bytes.

**Required C-side declaration:** C `long long sutram_strlen_checked(const char *p)` (or a `size_t` return with a documented range); C `long long sutram_sum_bytes(const unsigned char *p,long long n)` for the later buffer contract. **ELF symbol type `STT_FUNC` carries NO prototype, arity, pointer ownership, `const`, size or encoding.** Exact exported symbol matching alone is not type-safety proof. Require a reviewed ABI manifest/bound header plus one-to-one sidecar signature or explicitly call raw pointers `unsafe`; do not execute a bad pointer as a negative test.

## What the compiler emits and what the existing ELF converter must read

- **Compiler:** in `--ffi` + `--object/--separate`, validate sidecar v2 **before code**, classify arguments using actual typed AST metadata, validate NUL/length/lifetime, preserve source-located `E_ARITY`/`E_FFI_KIND` and ensure **no `.smo` on refusal**. For valid `cstr_ro` code, place the verified address in `rdi` (or the next free SysV integer register if mixed with other args), preserve alignment and live backing storage across the external `E8 disp32` call; return `i64` from `rax`. Emit the **existing `SUTRAMO1` named relocation** for exact foreign symbol; **no `FUNCDEF`, fake stub, or new import table**.
- **ELF reader `sutram-elf2smo`:** require the exact globally defined `STT_FUNC` in valid x86-64 `ET_REL` and copy its code; small self-contained functions need **zero external relocations**. The current R33 reader also accepts bounded read-only data with PC32 relocations resolved inside code. It cannot and should not infer `const char*`, buffer extent or `size_t` from ELF. Reject undefined helpers, unsupported external GOT/TLS, writable-data dependencies, unsupported alignment and bad metadata. No format change for simply calling a pointer-taking C function.
- **Tests:** (A) a known valid NUL-terminated literal `"abc"` passes and C produces 3; (B) a string with embedded NUL has a **documented** outcome (reject or C-prefix length) and exact stdout; (C) `cstr_ro` rejects integer zero, arbitrary `ptr`, `dasham`, kosh; (D) source-located wrong arity and no object; (E) nested calls preserve allocation and stack alignment; (F) C side requires const/read-only without relying on accidental nonfaulting writes; (G) pointer-return remains explicitly *unsafe/opaque*, not silently dereferenceable. **Native v2 tests NOT_RUN**.

**Risk call:** Existing v1 `ptr` is powerful but deliberately low-level: R33 allows integers to stand for addresses and C writes into a kosh. Do not mislabel it safe. A string-length-aware API with provable buffer lifetime is the next high-value *semantics* milestone; enabling `cstr_ro` without those proofs would be the same silent-incorrectness class as R33's old `dasham` truncation.

**WS1 result: DESIGN PASS, implementation NOT_STARTED.** The original request also named `f64` and `void`; these are already real R33 features, while aggregate-by-value, callbacks and Windows foreign-object FFI remain unsupported. The existing FFI is still opt-in and Linux-only.
