**Rules to keep comparisons honest:** preserve identical integer overflow and failure semantics, memory safety and bounds-check policy labels; never compare a checked Sutram loop against an unchecked Zig `ReleaseFast` binary without explicitly showing that difference. C: system clang/gcc `-O2`, `-O3`, note version and libc/CRT/static flags; Zig: `ReleaseSafe` and `ReleaseFast` separately; Sutram: baseline and explicitly enabled verified optimisation profiles. Use identical input datasets, random seeds, output hashes, data structure growth policy, warm/cold cache regime, thread count, core affinity, power/thermal state, and target ISA. Ensure the checksum is externally observed so compilers cannot delete computations; measure wall-clock process time and internal timed section separately, binary disk size, *peak* RSS, compile time, syscall counts, and instruction counts. Multiple independently launched runs (≥20–30), report median plus p10/p90 and uncertainty rather than best-of-five only; randomise run order and record OS/kernel/CPU/tool versions and flags. Do not claim “faster than C and Zig in all aspects”: for any finite suite, the defensible claim is **“faster on these measured programs/configurations”** only.
