# ROUND-97 WS2 — Byte-level ELF64 `ET_REL` → Sutram `SUTRAMO1` adapter contract

**Design/inspection only.** Implement in the project's **NASM** linker or a **project-owned NASM converter**, not by requiring the system `ld` for opt-in Sutram output. The handwritten `SUTRAMO1` linker currently reads **only** the `SUTRAMO1` magic and named `rel32` holes; an arbitrary Linux C `.o` remains unsupported. Pin current `linker/sutram_link.asm` blob `5d5616fb559d05ce8e7390d18763205516bbc292`; reference proof in R96's `ROUND-96-WS1-ELF-BRIDGE-ORACLE.py`. The positive/negative ELF headers below were **actually compiled and inspected with GCC 14.2.0/GNU readelf** on Linux x86-64, not by Sutram.

## What to read, exact bytes/offsets (all little-endian)

**ELF64 header 64 bytes**; require `e_ident[0:4]=7f 45 4c 46`, `EI_CLASS[4]=2` (ELF64), `EI_DATA[5]=1` (little-endian), `EI_VERSION[6]=1`; require **`e_type@16:u16=1`** (`ET_REL`), **`e_machine@18:u16=62`** (`EM_X86_64`), `e_version@20:u32=1`. Section-header table pointer **`e_shoff@40:u64`**, header size **`e_ehsize@52:u16=64`**, section-entry size **`e_shentsize@58:u16=64`**, section count **`e_shnum@60:u16`** (bounded), string-table index **`e_shstrndx@62:u16`** (valid). Reject extended counts, nonzero program headers, big-endian/32-bit/wrong-machine/version and checked multiplication/offset overflow. Every `offset+size` must be proven inside the bytes read **before dereference**.

**ELF64 section header 64 bytes** (`Elf64_Shdr`): `sh_name@0:u32` (offset in section-name string table), `sh_type@4:u32`, `sh_flags@8:u64`, `sh_addr@16:u64`, `sh_offset@24:u64`, `sh_size@32:u64`, `sh_link@40:u32`, `sh_info@44:u32`, `sh_addralign@48:u64`, `sh_entsize@56:u64`. Find one bounded **`.text` section** with `SHT_PROGBITS=1`, `SHF_ALLOC=2`, `SHF_EXECINSTR=4`; its `sh_offset/sh_size` identify the raw machine bytes to copy into `SUTRAMO1` CODE. Reject any other **nonempty allocated** section (data, initialized constants, TLS, constructors, exception tables) in the minimal subset; empty `.data`/`.bss` and nonallocated metadata (e.g. `.comment`) may occur but have no runtime content. `SHT_NOBITS` size is logical allocation, not bytes to read; reject **nonzero allocated NOBITS**. Require a bounded text length fitting Sutram's linker capacity.

**ELF64 `SHT_SYMTAB=2`: each `Elf64_Sym` is 24 bytes**, `st_name@0:u32`, `st_info@4:u8`, `st_other@5:u8`, `st_shndx@6:u16`, `st_value@8:u64`, `st_size@16:u64`. The symtab section's `sh_link` identifies `SHT_STRTAB=3` for the **symbol names** (distinct from `.shstrtab` for section names); names are NUL-terminated in that table. For each explicitly requested sidecar external symbol, accept exactly one **GLOBAL STT_FUNC** (`st_info bind=1, type=2`, visibility DEFAULT, `st_shndx=.text`), with `st_value < .text size` and `st_size` within the section. The first milestone rejects duplicate, weak/IFUNC, TLS, common, executable-in-unexpected-section, undefined C helpers and unrequested exports with unsafe dependencies. Name/arity/kind come from the *sidecar*; ELF symbols do **not** encode C argument counts or return kinds. The converter cannot infer type safety from `STT_FUNC` alone. External symbol must match sidecar exactly.

## How an ELF relocation differs from Sutram's hole

**ELF64 `SHT_RELA=4` entry is 24 bytes:** `r_offset@0:u64` (offset in relocated section), `r_info@8:u64` (`symbol_index=r_info>>32`, `type=r_info & 0xffffffff`), **`r_addend@16:i64`**. ELF64 `SHT_REL=9` entry is 16 bytes and its addend is **implicit in the relocation field**. Section header `sh_info` identifies which section's bytes are being relocated; `sh_link` identifies the symbol table. Reject unsupported `REL/RELA` kinds, bounds, alignment and symbol indices.

For an ELF **`R_X86_64_PC32=2`** or **`R_X86_64_PLT32=4`** relocation, the ELF formula is `D=S + A − P`, where **`P` points to the relocation's 4-byte FIELD**, and a typical direct-call entry has **`A=-4`** (GCC's R93/R97 host controls measured this). The existing Sutram `SUTRAMO1` relocation carries **only the offset of the 4-byte hole and the target name**, and its linker computes `D=S−(field+4)`: these formulas coincide for exactly `A=-4`, a single code section and an instruction whose disp32 ends at `field+4`. The Sutram record has **no relocation kind or arbitrary addend**. Thus **do not blindly translate** general `PC32/PLT32`, GOTPCREL, absolute `R_X86_64_64`, TLS, PLT/GOT or PC32 data references to an `SUTRAMO1` record. A future narrow mapping may accept verified `E8 [disp32]` (`PLT32,-4`) and a verified RIP-address form (`PC32,-4`), after resolving relocation's symbol and the instruction boundary, checking code bounds/range and preserving per-section offsets. Otherwise return a clear unsupported-relocation error **without generating a file**.

**First implementable milestone (no relocation handling at all):** insist there are **zero nonempty REL/RELA sections and no unresolved symbols**. Extract a freestanding integer-only `.text` body and one sidecar-named `STT_FUNC`, then emit **unchanged `SUTRAMO1` v1**: header `SUTRAMO1` + `code_bytes:u64` + `symbol_count=1:u64` + `reloc_count=0:u64`, code bytes, `{function_offset:u64,name_len:u64,name_bytes}`. `sutram-link` can then resolve the root object's existing unresolved name without changing the format or requiring `ld`. Conversion is an opt-in developer build step only; default `.sm → ELF/PE` must never invoke it.

## Actual Linux control observed this round

Built `long sutram_ffi_add(long a,long b){return a+b;}` with GCC 14.2 `-O2 -ffreestanding -fno-stack-protector -fno-asynchronous-unwind-tables -fno-unwind-tables -fno-pic -fno-pie`: **ELF `ET_REL`, x86-64, 9 sections**, `.text` **offset `0x40`, length `5`**, `.symtab` linked to `.strtab`, **GLOBAL FUNC `sutram_ffi_add` offset 0 length 5**, **no relocations**, no unresolved symbols. A negative `missing_helper` call produced ELF `.rela.text` **`R_X86_64_PLT32` offset 4, symbol `missing_helper`, addend -4**. See exact [GCC/readelf stdout](ROUND-97-WS2-ELF-OBSERVED.txt) and the pinned C input files. Raw host controls are **PASS**; actual `sutram-link` foreign `ET_REL` input **NOT_RUN/NOT_IMPLEMENTED**. The host witness does not cover C variadics, `printf`, double/XMM ABI, PIC, helper libraries or Windows x64.

**Review risk:** even in the no-reloc subset a self-contained function can contain unsafe machine instructions; validating headers is not a sandbox. Reject malformed objects deterministically and publish the output atomically *after* all references validate; no root/admin writes. The reference Python oracle from R96 is only developer-time test machinery. Native NASM conversion and Sutram-side `E_ARITY` enforcement require Claude's separately reviewed implementation and genuine full-suite, fuzz and Windows gates.
