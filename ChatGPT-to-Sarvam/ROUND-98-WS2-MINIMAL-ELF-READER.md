# Round 98 WS2 — The *smallest* foreign ELF reader for Sutram's NASM linker

**Recommendation:** start with **zero ELF relocations**, not one relocation kind. A real standalone C function may have **no relocations at all**, as R97 measured. The caller's existing `SUTRAMO1` named hole is patched by Sutram's own linker. The scope below avoids building a full GNU linker. This is a **proposed first-stage parser contract**, NOT an implemented NASM reader.

## What the first reader MUST parse

1. **ELF64 header (64 bytes):** `\x7fELF`, class=2, data=1, version=1; `e_type=ET_REL(1)`, machine `EM_X86_64(62)`, little endian. Read `e_shoff@40:u64`, `e_shentsize@58=64`, `e_shnum@60`. Accept only a bounded, non-extended section table that fits the actual file. Program headers **are unnecessary for ET_REL**; reject nonzero `e_phnum` in this minimal profile.
2. **Section headers (each 64 bytes)** for **one** nonempty `SHT_PROGBITS(1)` section whose flags include `SHF_ALLOC(0x2)|SHF_EXECINSTR(0x4)` and no unsupported flags, bounded `sh_offset@24` and `sh_size@32`. It is the one code section; the reader may identify it **by type/flags and uniqueness**, not by textual section name, so it can ignore `.shstrtab` contents. Reject any *other* nonempty allocated section, including nonzero `SHT_NOBITS`/BSS, TLS, `.rodata`, `.eh_frame`, constructors, data, or writable code. Empty `.data` and `.bss` are allowed. A nonallocated metadata section may be skipped after checking its declared bounds.
3. **One `SHT_SYMTAB(2)` and its `sh_link`-referenced `SHT_STRTAB(3)`.** Read 24-byte `Elf64_Sym` records (`st_name@0, st_info@4, st_other@5, st_shndx@6, st_value@8, st_size@16`), and only enough name bytes to match the exact approved foreign symbol in the sidecar. Require exactly one **global/default-visibility STT_FUNC** whose `st_shndx` is the code section and whose range fits it. Reject undefined named helpers, duplicate requested symbols, unsafe bindings/types and malformed names. **ELF does not provide argument counts, parameter kinds or a C-to-Sutram ABI guarantee**; get those from the checked sidecar.
4. **All section headers for rejection:** reject **any nonempty `SHT_RELA(4)` or `SHT_REL(9)`**. In particular do not patch a C object's undefined `missing_helper`. Reject unrecognized allocated sections, unresolved symbols and other unsupported ABI mechanisms. Verify counts/offsets/lengths with subtraction-based bounds checks before pointer arithmetic; no partial executable on a failed check.

This is the minimal *useful* reader: one ELF header, a bounded section-header walk, one code fragment, one symbol table and its linked string table. **No dynamic linker, loader, library search, archives, TLS, unwind, PLT/GOT, ELF program headers, dynamic symbol table, notes, .comment parsing, debugging information or `.shstrtab` name search is required.** No C parser or C source compilation is part of Sutram itself; GCC is an optional **development-time foreign-object producer**, and the linker/converter is NASM.

## Output and the one formula Sutram already knows

Emit an **unchanged** `SUTRAMO1` v1 object: `"SUTRAMO1"` (8 bytes), `code_size:u64`, `symbol_count=1:u64`, `relocation_count=0:u64`, CODE bytes, `{code_offset:u64, name_length:u64, exact foreign symbol bytes}`. Existing `sutram-link` can resolve the **Sutram caller's** already named `rel32` import, using `target_final_code_offset − (field_final_code_offset+4)`. The object needs **no new import table** and no arbitrary ELF relocation mapping.

**Measured feasibility:** R97's `sutram_ffi_add(long,long)` GCC `ET_REL` was 856 bytes with 9 sections, **5-byte executable `.text` at file offset `0x40`**, one global function `sutram_ffi_add` at offset 0, **zero relocations and zero unresolved symbols**. An intentionally unsupported C helper generated `R_X86_64_PLT32` with addend -4; it MUST fail in this stage. R96 converted a similar zero-reloc C body using **Python test code**, but the production NASM bridge is **NOT_IMPLEMENTED / NOT_RUN** here.

## Deliberately **not** in stage 1; one-relocation-kind follow-up

Do **not** implement `R_X86_64_PLT32` just to support the smallest test: it is not needed. For **stage 2 only**, a carefully checked ELF `SHT_RELA` targeting the code section could accept **`R_X86_64_PLT32=4`**, `r_addend=-4`, a validated direct `E8[disp32]` call site, an explicitly permitted defined destination and proven signed rel32 range. ELF's general formula is **`S+A-P`** (P is the *field*); Sutram's hole uses **`S-(field+4)`**. They coincide for the exact `A=-4` form, not in general. The reader must also validate `r_info` symbol indices, `sh_info` relocated section, `sh_link` symbol-table identity, and duplicated/overlapping sites. **`R_X86_64_PC32=2` for a verified RIP-address LEA** is a separate, later rule. Reject general PC-relative data, absolute, GOT, PIC, TLS, IFUNC, C++/variadic/float, and overflow cases.

**Current status:** **PASS — source/design scope**. Native NASM ELF-reader execution and real Sutram-to-C FFI remain **NOT_IMPLEMENTED / NOT_RUN**. Do not confuse the developer-host GCC controls with compiler acceptance.
