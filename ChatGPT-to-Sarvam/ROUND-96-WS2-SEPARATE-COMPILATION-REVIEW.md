## What is real now (and what remains source-flattened)

- **Ordinary path**: `sutram_compiler in.sm out.bin` still calls `expand_imports` and builds one standalone executable. No extra tool, linker, C or Python is required for an ordinary Sutram program. This path is protected: Claude's **558-program v238-v239 default-path comparison** reports **470 byte-identical binaries + 88 identical rejected inputs, zero differences**; Wine was **182/182** matching, but real Windows acceptance is **NOT_RUN** for R29.
- **Explicit opt-in**: `sutram_compiler --separate unit.sm unit.smo [root.sm]` parses all imported sources **to retain definitions, arities, `dasham` return types and direct `phal` obligations**, but marks imported functions using R51 source-origin mapping and **does not emit their function bodies** in the importing unit. Each owner unit independently emits its own definition. `tools/sutram_build.py` discovers `yoj` dependencies, compiles each distinct discovered path once, then calls our project-owned NASM `sutram-link`. Result: the module body is **compiled/emitted once per build** even though imported source is **still reparsed in multiple compilation units**. It is *real separate code emission/linking*, **not yet header/interface-only compilation or incremental builds**.
- **R29 validation**: Claude reports **253 programs using modules** with matching stdout/exit; **144 examples without modules** byte-identical; a diamond compiles its shared module once; wrong arity into an imported module is rejected with the old diagnostic; and it preserved correct `dasham` returns after an earlier unsafe attempt yielded wrong integers for 39 programs. Unlike R28's untyped link-by-name, the *caller compiler* still sees imported signatures by reading the full source.
- **Restrictions (real current limits):** `yoj module@alias` is **refused** by the separate driver (10 cases in Claude's survey), module-level `vitti` is **refused** in object emission, only Linux is supported, no incremental cache, callback from library into root lacks root signature/return-type proof, and `sutram_build.py` is currently a **developer-time Python** driver. This opt-in Python dependency does **not** affect ordinary compiler-alone output, but if the owner's wider developer-tool fundamental requires no Python anywhere, a future NASM driver is separate work (Claude estimates approximately 160 lines).

## Next reliable `yoj` evolution — staged, never a default rewrite

1. **Make the graph authoritative, reusable, and lexical.** Keep old `yoj` expansion untouched by default. For opt-in separate builds, use a token-aware scanner or the compiler's own resolved graph, not a second hand-rolled approximation. Establish stable canonical project-root/module IDs, traversal order, versioned interface digests, duplicate/cycle/missing/private checks, original source locations and an import-edge alias map. Prevent traversal and path escapes, including symlink cases, with a documented rooted policy. Compile one owner unit per stable identity; dedupe diamonds by identity, **not by alias**.
2. **Split interface availability from body emission.** The current reparse-all-sources path is a safe compatibility bridge. Later emit an interface-only record (name, arity, integer/`dasham` return convention, `phal` status, parameter kinds where declared, visibility, ABI ID, module ID) so clients can type-check calls **without reparsing implementation bodies**. Version it separately; do not pretend current `SUTRAMO1` carries these fields.
3. **Resolve aliases without cloning bodies.** For `yoj m@a`, preserve the existing source spelling `a__f(...)` and `niryat` privacy on the importer side, but resolve link symbols to one canonical `(module_id,f)`. A renamed `a__f` should not force another machine-code copy. Current global name-only linker **cannot** encode this identity and privacy soundly. Require a separately reviewed versioned symbol format or a proven canonical-mangling/import-adapter strategy; do **not** hack R29 by globally removing prefixes or changing the legacy v1 marker.
4. **Add globals/init semantics only with data relocations and lifetime rules**; never silently compile an object containing module-level `vitti`. Add dependency cache only after reproducible object/interface identity, source hash and collision invalidation tests; no network package registry.
5. **Windows separately**: PE entry/runtime, import table placement and relocation/RVA rules need independent owner Windows acceptance. The Linux format/linker alone is not PE readiness. Save old legacy goldens and run all suite/fuzz/corpus and Windows guard on each opt-in integration.

## New concrete source-review finding: builder scanner matches imports inside strings

Live `tools/sutram_build.py:yoj_names` skips `#` and `//` comments but **does not skip quoted strings**. In an **exact source-equivalent Python copy** ([probe](ROUND-96-WS2-BUILDER-SCANNER-PROBE.py), [raw stdout](ROUND-96-WS2-BUILDER-SCANNER-OBSERVED.txt)), the case `mukhya() { likha("yoj bogus") }` yields **`['bogus")']`** instead of an empty import list. Positive `yoj ganita` gives `['ganita']`; both comment controls give `[]`. The *driver's scanner algorithm* therefore has a false-positive path for legitimate string data and may refuse builds of such programs with a nonexistent module, even though native Sutram treats the text as a string. **PASS: reproduced scanner logic**; **NOT_RUN: end-to-end native direct vs separate build for that exact program**. This is a bounded test/fix candidate for Claude/Sarvam: use the canonical lexer or correctly skip quoted strings/escapes while preserving the exact compiler grammar, then verify identical graph/behavior and all existing R29 tests. Do not change legacy parsing to hide this mismatch.

**Conclusion:** `yoj` need *not* change in the normal compiler. The important future work is a **separately opt-in module-identity and interface contract**, not another source-flattening pass. R29 is a meaningful achieved stepping stone; report it accurately instead of re-proposing it.
