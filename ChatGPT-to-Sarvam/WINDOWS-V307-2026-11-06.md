# Sarvam handoff: native Windows v307

**V307 still has the OOM crash, three slice escape failures, and an upgrade that
Acronis suspends. The ordinary native suite passes 322 checked cases.**

Tested repository commit: `75586a754371dc27f9ed850f592df6194b8e11a6`, containing
v307 implementation `60ce554d`. Setup SHA-256:
`cbbfd0a66c0a9728c3fd88096631462430c0185cd8c6738964d5b885253e7481`.
Compiler SHA-256:
`0444b43552f6140147ee4701aeac857d585086681bbe4e5bd71d8f90bedd3f7b`.

- **OOM:** B3 at 448 MiB crashes 2/3; 480 and 512 MiB crash 3/3 each.
  B3 at 544, 576, 608 and 640 MiB cleanly refuses all three repetitions.
  Mandapa at 64 MiB crashes 10/10. Page-touch control at 64 MiB cleanly refuses.
  Across all 32 runs, all 32 messages are complete, including the 18
  `0xC00000FD` exits. Completeness does not prove handler completion or locate
  the later fault. [OOM evidence](../Windows-to-Sarvam/win-v307-2026-11-06/OOM.md).
- **Slice:** the two function-value variants now refuse with `E_KOSH_VIBHAG`.
  Cell-store and untyped-parameter probes still lose writes; the untyped-return
  probe still reads stale data. The exact cell-address-printing snippet alone
  cannot validate slice contents; a companion write discriminator demonstrates
  the failure. [Slice evidence](../Windows-to-Sarvam/win-v307-2026-11-06/SLICE.md).
- **Native suite:** 322 PASS, zero FAIL/COMPILE_FAIL/TIMEOUT; three cases have no
  expectation and six are deliberately skipped by the unchanged harness.
  [Raw cases](../Windows-to-Sarvam/win-v307-2026-11-06/native-cases.json).
- **Installer:** clean v307 installation succeeds, with 657/657 payload hashes
  and a fresh shell resolving exactly one canonical v307 compiler. The repeated
  same-directory upgrade triggers Acronis at file 87/657; vendor records explicitly
  suspend both the engine PID 43868 and wizard PID 31584 at 22:47:41.041459.
  Removing mass deletion did not prevent this machine's detection during per-file
  replacement. [Setup, security and recovery evidence](../Windows-to-Sarvam/win-v307-2026-11-06/UPGRADE.md).

The suspended upgrade produced no result through **936.39 s**; its processes
were then stopped and its partial tree preserved. **The final deliberately
interrupted installation recovered successfully in 16.57 s**, with engine exit
0 and a visually verified Finish page. Fresh-shell identity and **657/657 hashes**
pass afterward. The machine is left with working v307, DisplayVersion 1.0.307,
no pending/partial files, and no test-owned wizard/engine process left running.

**Additional logging finding:** a local fixture proves that Windows PowerShell
5.1 `Add-Content` fails while even a fully shared log reader is open. The engine
uses it with stop-on-error. The first recovery attempt used such a reader, so it
is retained as confounded evidence. The final recovery pass used no live-log
reader. Please review this logging fragility independently. A further upgrade
without a live reader was not run; direct vendor records establish Acronis as
the cause of the observed suspension, not the outcome of every future upgrade.

The evidence package includes the owner's instructions, all six slice probes,
three OOM probes, unchanged Job Object runner, every command and raw result,
native screenshots, security excerpts and diagnostic limitations. The observer
issues (clean JSON serialization and live-log-reader interference) are
disclosed in [COMMANDS.md](../Windows-to-Sarvam/win-v307-2026-11-06/COMMANDS.md).
No product files, original examples/goldens or security settings were changed;
no debugger was installed and no CI run was triggered. This is diagnostic
evidence, not release acceptance.
