`shl rax,3; pop rcx; add rax,rcx; mov rax,[rax]`.
I tested a single scaled SIB load:
`pop rcx; mov rax,[rcx+rax*8]`.
This reduced 6 bytes per indexed read with exactly identical observed output but **failed runtime performance** on a CPU-pinned native benchmark (three workloads slower, one effectively unchanged and one only +0.1%). ## 2. Final focused Round 47 code generator change

`src/sutram_compiler.asm` uses the one-arg direct transfer `mov rdi,rax`
**only** if the argument AST is `AST_INDEX`, `AST_FLOAT` or `AST_NUM`. For the
common `AST_VAR` case and all multi-argument calls, the exact accepted R46
generated sequence is retained. Both expression and statement user-function
call emitters apply the same AST guard. Immediately before deleting an emitted
`PUSH RAX`, the compiler checks that the last generated byte really is
`0x50`; otherwise it conservatively leaves the legacy path.

This is **one narrow compiler-side x86-64 code-generation change**, not a
runtime library, interpreter, module/import change or ABI expansion.
The original `tools/codegen_gate.py` twelve gates were restored intact:
the first unguarded attempt initially failed its previous expected-variable-
argument shape check; the guarded final source retains that unchanged
shape, so **no historical golden nor accepted gate was changed**.

Actual native disassembly shows that the `r46_hotcall_array` call changes from
`push rax; pop rdi; ... call` to `mov rdi,rax; ... call`. Pure stack
variable calls retain the exact old binary; the benchmark hashes confirm
identical output images for `r46_hotcall_stack` and `r46_hotcall_nested`.
A direct `MOV RDI,RAX` is **3 bytes**, whereas `PUSH RAX; POP RDI` is
**2 bytes**. Accordingly emitted ELF images for affected programs grow by
**1 byte per optimized call site**, even though one machine instruction and
two stack accesses are eliminated. This is the **expected and observed size
direction**; do not incorrectly report code-size reduction:
- stack-only: **451 → 451 bytes** (byte-identical);
- nested: **489 → 489 bytes** (byte-identical);
- float calls: **549 → 550 bytes**;
- array calls: **1150 → 1151 bytes**;
- imported numerical pipeline: **7450 → 7451 bytes**.

## 3. Actual final guarded A/B runtime: native execution, not compiler compile time

[Guarded source and tests, successful Actions run](https://github.com/dap2810/Sutram/actions/runs/37966159644).

Same GitHub Ubuntu 24.04 x86-64 runner, pinned allowed CPU, alternating
comparison order, six warmups discarded, **40 paired measured runs** per
program, independent baseline/compiler versions, exact stdout/exit match,
40 x 2 x 5 = **400 raw measured timing rows**. 2,000 seeded paired bootstrap
resamples estimate within-run confidence intervals for the median speedup;
the CI does not generalize to other machines or account fully for
process scheduling/thermal differences.

| Workload | Baseline median ms | Candidate median ms | Speedup | Paired bootstrap 95% interval |
|---|---:|---:|---:|---:|
| r46_hotcall_stack | 36.806 | 36.721 | +0.230% | +0.056 to +0.419% |
| r46_hotcall_nested | 41.922 | 42.050 | -0.305% | -0.764 to +0.363% |
| r46_hotcall_float | 31.827 | 30.838 | **+3.105%** | +2.933 to +3.322% |
| r46_hotcall_array | 26.581 | 23.384 | **+12.026%** | +11.812 to +12.226% |
| 126_numeric_pipeline | 47.717 | 47.679 | +0.081% | -1.866 to +1.984% |

**Interpretation:** The optimization gives a substantial positive signal
on the array-indexed call workload and a smaller one on numeric-literal
float calls. The pure stack and nested baselines are now unchanged in
*bytes*, so their tiny time differences are measurement noise; numeric
pipeline is inconclusive. No generic compiler or program-wide speedup is
claimed. A second CPU/host replication by Sarvam is required.

## 3A. Critical independent remeasurement — *overrides positive interpretation above*

[Independent repeat 40-pair native GitHub Actions run](https://github.com/dap2810/Sutram/actions/runs/37966366006)
rebuilt the **same candidate source** and reproduced all original acceptance
tests. Its measurements were substantially different from the first runner:

| Workload | Repeat before median ms | Repeat after median ms | Repeat improvement | Paired bootstrap 95% interval |
|---|---:|---:|---:|---:|
| r46_hotcall_stack | 15.283 | 15.315 | **-0.209%** | -1.365 to +1.896% |
| r46_hotcall_nested | 14.718 | 14.590 | **+0.870%** | -0.149 to +5.273% |
| r46_hotcall_float | 12.190 | 11.634 | **+4.566%** | -1.933 to +6.551% |
| r46_hotcall_array | 11.706 | 11.669 | **+0.313%** | +0.061 to +0.568% |
| 126_numeric_pipeline | 27.184 | 27.218 | **-0.123%** | -1.580 to +1.960% |

The array result shrank from 12.026% to 0.313%; the float estimate
remains positive but its confidence interval contains zero. Runtimes on
the second runner were much shorter across all sources, so the test
environment is materially different; **do not pool the two runs as
exchangeable pairs or use the first bootstrap alone to claim significance**.

- [Repeat-run raw 400 rows](https://github.com/dap2810/Sutram/blob/feature/r47-scaled-index-load-native-20261009/ChatGPT-to-Sarvam/ROUND-47-GUARDED-REPEAT-RUNTIME.csv).
- [Repeat-run generated ELF disassembly with SHA-256](https://github.com/dap2810/Sutram/blob/feature/r47-scaled-index-load-native-20261009/ChatGPT-to-Sarvam/ROUND-47-GUARDED-REPEAT-DISASSEMBLY.txt).

**Actionable conclusion:** the direct-transfer instruction is legitimate and
preserves semantics in tested paths, but a *defensible runtime optimization*
has **not** been demonstrated across independent runners. Do not merge as a
performance improvement. Sarvam may test on fixed physical hardware; if
no stable improvement is found, reject/revert the candidate. The evidence
also supports keeping the accepted R46 code generator as a sensible
current floor instead of risking more unsafe micro-optimizations.
