Critical — memory corruption, no guard

B10 — the break/continue patch buffer overflows at 64 critical

The break_patch_positions and continue_patch_positions buffers are resb 512 — 64 eight-byte entries — with no capacity check. A loop containing 64 krama (break) or uddeshya (continue) statements writes past the end and corrupts adjacent compiler state.

It fails silently, surfacing as a misleading parser error rather than a capacity message — the same signature as B8:

63 breaks: OK, correct output (63)
64 breaks: Sutram Error: parse error at line 69:5 near token '}'

Fix: add a bound check before each patch-position write and raise the cap (or size it to the source), failing with a named error. Exactly the pattern already used for func_params.

Deep nesting fails with a misleading error critical

~100 nested blocks compile; ~150 fail — and again the message is misleading (parse error … near token 'end of file'), which points at a depth/stack buffer being overrun rather than a clean "too deep" diagnostic.

100 deep: OK, 1580 bytes
150 deep: Sutram Error: parse error at line 186:211 near token 'end of file'

Lower severity in practice (nobody nests 150 deep by hand), but it is the same class: an unbounded structure reporting a parse error instead of a capacity error.

B11 — nested block bodies cap at 64 statements critical

Found while re-testing the B10 fix. A yadi or yavat body with more than 64 statements fails with the same misleading parse error near '}' — the parser's per-block statement list has a fixed 64-entry capacity and no guard. The function body is not capped the same way (200 statements compile fine), and no named capacity constant exists for block statement lists.

yavat body, 64 stmts: OK
yavat body, 65 stmts: Sutram Error: parse error near token '}'

mukhya body, 200 stmts: OK   (function bodies are not capped)

Fix: give the per-block statement list a named cap and a clean failure, exactly as B10 got. This is more likely to bite real code than B10 — a loop body of 65 statements is ordinary.

Known limits worth documenting

Arrays are unchecked — the library trusts its length argument medium

Every array function takes an explicit n and indexes without bounds-checking (a[i], a[j], a[mid]). Passing an n larger than the array reads and writes out of bounds — a crash or silent corruption, not a diagnostic. This is inherent to the no-runtime design, so the honest fix is documentation plus optionally bounds-checked helpers (*_safe variants), not a global runtime check.

The AST ceiling still binds medium

12 library modules; a program importing several can hit compiler AST capacity exceeded. It fails cleanly (a guard was added), but it caps multi-module programs and library growth.

Three library modules are documentation-only stubs medium

array, io and net define zero functions — importing them does nothing. Either fill them or mark them clearly as reference-only so users are not misled.

What held up under attack

Guarded buffers, no secrets, least-privilege installer pass

The main arenas — token array, AST heap, string pool, import buffer, parameter arena, function table, patch list, function definitions — all have named capacity constants and clean-failure guards. A large program (8,000 statements) and 24 module imports compiled without corruption. No credentials, keys or tokens appear anywhere in the source. The Windows installer is per-user with a self-enforcing build gate that rejects UAC/HKLM/machine-PATH if they ever return.
