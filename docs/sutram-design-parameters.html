Design parameters · what Sutram is being built to be

Sutram ॥ सूत्रम् ॥
Design Parameters

A multi-paradigm, native-compiled language with an easy procedural core, strong type checking, memory safety by default, and explicit low-level control for operating systems. The target is Python-like ease for everyday work, Rust-inspired safety, C-level hardware control, and reusable abstractions — without copying every feature or every complexity of those languages.

The charter, as given Develop Sutram as a multi-paradigm systems-and-application language with a small procedural core, practical functional features, generics, composition-based object orientation, data-oriented capabilities, and optional concurrency and metaprogramming. Prioritise easy everyday syntax, strong static typing with inference, a coherent memory-safety model, explicit low-level control, freestanding OS capability, modular libraries, portability, multilingual consistency, and excellent tools. Keep advanced complexity optional for the programmer — not undefined in the implementation. Audit the current compiler first, preserve established project constraints, and implement this in tested stages. Do not claim safety, portability, performance superiority, or OS readiness without corresponding evidence.
Read this page as requirements, not as a description of what exists. Everything below is the design target. Each item carries an honest status measured against the compiler as it stands today: implemented, partial, or not started. Where something is partial, the gap is named. Nothing here should be read as a claim that Sutram already does it.

A · The paradigms Sutram should support

No single paradigm delivers the whole target. Sutram needs a coherent combination — language rules, libraries and tools that agree with each other.

01

Imperative and procedural programming

Implemented

Variables, conditions, loops, functions, and straightforward step-by-step programs as the easiest starting point. Useful programs without first learning classes, traits, concurrency or memory annotations.

Aim: make simple programs simple; advanced features build on this foundation rather than replacing it. Today: this is the core of the language and its strongest part — mukhya, vitti, yadi, yavat, chakra, prakriya.
02

Practical functional programming

Partial

First-class functions — passed as arguments, returned, stored. Closures, immutable values, iterators, pattern matching, and collection operations such as mapping and filtering. Functions that calculate results without unexpectedly modifying unrelated state.

Aim: functional tools where they improve clarity, while ordinary loops and mutable data stay available. Today: functions exist and can be called, but they are not first-class — there are no function values, closures, iterators or pattern matching.
03

Generic programming

Not started

One collection or algorithm working with multiple types without duplicating its implementation. Generic functions and structures with clear constraints — a shreni should require values that can be compared. Understandable constraints and error messages over elaborate template rules.

Today: none. Every collection in lib/ is written against one concrete cell type.
04

Object orientation through composition

Partial

Structures, methods, encapsulation, interfaces or traits. Larger objects built from smaller components. Polymorphism, with runtime dispatch an explicit choice where practical. No deep class hierarchies or multiple inheritance in the initial design.

Aim: structures + methods + traits + composition, not a reproduction of the C++ class system. Today: rachana gives plain structs. There are no methods, no traits and no polymorphism.
05

Data-oriented programming

Partial

Contiguous arrays, slices, predictable layout, alignment controls, explicit allocation choices. Processing large collections without every element being a separately allocated object. Vector operations and SIMD later, backed by benchmarks.

Aim: control over how data is represented and accessed — not promising speed merely because code is compiled. Today: mala and kosh exist and are contiguous, but there are no slices, alignment controls, SIMD or vector operations.
06

Structured concurrency and parallelism

Not started

Threads, tasks, channels, synchronisation primitives, cancellation. Task lifetimes tied to an owning scope rather than uncontrolled background work. Convenient message passing; explicit shared mutable data. Ownership and thread-safety rules designed before advertising safe concurrency.

Today: none. Note: a sangrah of socket builtins exists in the compiler and is under audit — they are not a concurrency model and may be retired.
07

Event-driven and asynchronous programming

Not started

Callbacks, events, timers, asynchronous input/output — for GUI applications, networking, servers and automation. Event loops and task executors optional rather than mandatory. No application scheduler required by kernel or embedded programs.

Aim: a small sangrah of primitives where necessary, with most event-driven behaviour in reusable libraries. Today: the IDE runs its own X11 event loop, but the language has no event or async facility.
08

Controlled compile-time metaprogramming

Partial

Compile-time constants, assertions, and eventually constrained code generation — for generic libraries, fixed-size data structures, serialisation and hardware descriptions. Compile-time execution bounded and deterministic by default. No unrestricted textual macros; no hidden network or filesystem access.

Aim: begin with a smaller, carefully specified subset. Today: sutra gives constants and yoj performs textual inclusion — which is not the bounded, deterministic compile-time evaluation this calls for.
09

Multilingual and native-script programming

Strong

One language whose meaning is fixed, spelled in many scripts. A program's behaviour must not change because its keywords are written in Devanagari rather than Latin — the canonical meaning sits beneath every spelling, and a library written in one pack is usable from another without translation. Identifiers, strings and comments are preserved; only keyword spellings change.

Why this is a paradigm, not a feature: every other language on this suchi can be described without naming a natural language. Sutram cannot. Sanskrit is the keyword core and the mathematics library is built on the Indian tradition, so the language's identity and its grammar are the same decision. Today: this is the project's strongest and most distinctive work — 11 packs over one canonical meaning, native-script digits, the danda । and dvigun danda ॥, a Sanskrit-first keyword core, and six book editions. The gap: Unicode normalisation and ambiguous-identifier diagnostics are not implemented, and Devanagari glyph shaping is not done at the font level.

B · Capabilities beyond paradigms

Not additional paradigms — what would make the language safe, practical, portable and suitable for serious development.

10

Strong static typing with inference

Partial

Types checked before execution, with obvious local types inferred. Clear type contracts at public library boundaries. Integer sizes, conversions, overflow, initialisation and comparison defined precisely. No silent conversions that lose information.

Aim: concise ordinary code whose meaning stays predictable. Today: anka, dasham, satya and strings are typed and checked at compile time; overflow behaviour is documented and tested (checked and saturating forms exist), but inference is limited and there is no formal type-contract system.
11

A coherent memory and resource model

Not started

Ownership, borrowing, deterministic cleanup for memory, files, locks and other resources. Common cases easy; advanced lifetime relationships only when needed. Raw pointers and unchecked operations behind explicit, narrowly scoped unsafe boundaries. No tracing garbage collector for the core.

Aim: specify the rules before claiming memory safety — adding ownership syntax alone is insufficient. Today: memory is manual. There is no ownership, no borrow checking, and no unsafe boundary. Sutram does not currently claim memory safety, and must not until this exists and is tested.
12

Explicit, convenient error handling

Partial

“A value may be absent” represented explicitly. Recoverable success or failure as a phal type. Concise error propagation and automatic resource cleanup. Recoverable errors separated from unrecoverable failures. Exhaustive handling required where appropriate.

Today: the checked library functions take an ok out-parameter and return a defined value on failure rather than wrapping — a real, tested convention. There is no phal type, no propagation operator, and no exhaustiveness checking.
13

Genuine freestanding capability

Partial

A core library that does not assume an OS, filesystem, network or heap allocator exists. Custom entry points, memory layout, sections, relocations and startup code. Explicit pointer operations, hardware access, calling conventions and interrupt entry code. Carefully specified inline assembly with register and memory effects. Heap allocation optional.

Aim: the distinction that matters is running without an existing OS, not merely producing a native executable. Today: the compiler emits native ELF and PE32+ with no runtime and no libc — a genuine head start — and yantra provides inline assembly. But no documented boot path or minimal kernel has been demonstrated. A small kernel that boots, prints, and passes repeatable tests is the acceptance target; a full OS is a separate project.
14

One language with layered libraries

Partial

Conceptual layers — core (no OS or allocator dependency), allocation (dynamic collections when an allocator exists), standard/application (files, networking, threads). The same type and safety rules across all layers. Not an unrelated “easy language” and “systems language”.

Today: lib/ holds 21 modules, but the layers are not formally separated — nothing marks which modules are allocator-free.
15

Portability designed into the compiler

Partial

Separate parsing, type checking, internal program representation, machine-code generation and OS integration. Track source portability, where the compiler runs, and which targets it can generate for separately. Reliable Windows/Linux x86-64 first, then other combinations individually. Every advertised target tested.

Today: Linux x86-64 works and is tested. Windows x86-64 sources exist and have never been executed by this project — the one gate nothing has passed. The one-patra pure-NASM constraint is preserved unless an architectural change is explicitly approved; clear internal phase boundaries should be introduced within that implementation.
16

Real modules, packages and separate compilation

Partial

Namespaces, explicit imports, public/private visibility, clear dependency boundaries. Modules compiled independently rather than relying only on textual inclusion. Versioned packages, dependency lockfiles, offline builds, reproducible settings. Compatibility and migration rules.

Aim: suitable for teams and substantial codebases, not just single-patra examples. Today: yoj is textual inclusion, and niryat gives export visibility. There is no separate compilation, no package manager, no lockfile.
17

Language packs and the multilingual toolchain

Strong

One canonical language meaning beneath Sanskrit and other supported keyword spellings. Versioned language packs defining how each source patra selects its language. Packages usable across packs without translating implementations. Unicode identifier rules, normalisation, and diagnostics for suspicious or ambiguous identifiers. Identifiers, strings and comments preserved when translating keyword spellings.

Today: this is the project's distinctive strength — 11 packs over one canonical meaning, with native-script digits and dandas, and a keyword core that is Sanskrit. The gap: Unicode normalisation and ambiguous-identifier diagnostics are not implemented, and Devanagari glyph shaping is not done at the font level.
18

Excellent developer tools

Partial

One consistent workflow for creating, building, running, testing, formatting and documenting projects. Editor support for completion, navigation, renaming and diagnostics. Debug information, stack traces, profiling, actionable error messages. Standardised formatting, layout, contribution rules. Ready-to-use binaries so ordinary users need not build the compiler.

Today: a working IDE on Linux (16 GUI tests), a Windows installer, an install-with-binaries path so end users need no toolchain, and actionable compiler diagnostics. Missing: a formatter, language server, debugger, and stack traces.
19

Interoperability and a useful ecosystem

Not started

A documented C-compatible foreign-function interface first. Optional C++ wrappers and Python bindings later, never mandatory for basic use. Reliable libraries for collections, text, files, networking, mathematics, testing and serialisation. GUI, database, scientific and AI integrations as packages rather than compiler expansion.

Aim: reuse existing software while growing our own ecosystem. Today: there is no FFI. The library is self-contained and 281 functions deep, which is a foundation, not an ecosystem.
20

A precise specification and evidence-based gates

Partial

Evaluation order, memory rules, numeric behaviour, Unicode behaviour and error semantics specified. Both valid programs and invalid programs that must be rejected are tested. Regression tests, fuzzing, cross-platform tests, reproducible benchmarks. Compilation time, execution speed, memory consumption and executable size measured separately. Documentation, examples and feature status aligned with the tested implementation. Compatibility review before changing syntax or behaviour.

Aim: a smaller sangrah of dependable features over a large suchi of partially working ones. Today: the gates are real and enforced — 187 pass / 4 no-expectation, codegen 12/12, packs 33/33, module graph, 180 library proofs, 72 property proofs, 16 GUI tests — and there are dedicated overflow-safety and byte-parity documents. Missing: a formal written specification, fuzzing, and cross-platform execution.

C · The implementation order

Design the interfaces and the safety model early, even when the implementation comes later.

Stabilise the foundation Written semantics, compiler correctness, procedural programming, type rules, diagnostics, regression tests.
Make substantial programs manageable Modules, visibility, separate compilation, resource management, error handling, core libraries.
Prove systems capability Freestanding compilation, hardware interfaces, a documented boot path, and an actually tested minimal kernel.
Add reusable abstractions Generics, traits, methods, first-class functions, closures, predictable collections.
Expand carefully Concurrency, asynchronous libraries, additional targets, interoperability, controlled metaprogramming.
