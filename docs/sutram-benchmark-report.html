philosophy / why sutram is different

Why Sutram is different

Most fast languages buy speed with a heavy toolchain and a fat runtime. Most lightweight languages buy smallness with an interpreter that's slow and itself enormous. Sutram's bet is that you can have native-tier speed in a sub-kilobyte binary with no runtime at all.

No runtime, ever

Java needs a 200 MB JVM. Python needs a 35 MB interpreter. Node needs a 70 MB V8. Sutram needs nothing — the 203-byte output is the whole program. It runs where those runtimes can't even fit.

Tiny artefacts

A 203-byte binary vs C -O2's 4,736 bytes (23× smaller), Go's ~2 MB, or Rust's ~3.5 MB. On constrained or embedded targets, the size of the program is the feature.

Native speed, no VM

Sutram compiles to run at 86% of C -O2 on simple loops — within ~15% of the fastest mainstream compiled language — with no JIT warmup, no GC, and no interpreter overhead.

Honest about the gap

Sutram doesn't pretend to beat C everywhere. On arithmetic it trails C -O2 because it doesn't yet do loop-invariant code motion. The roadmap closes that gap rather than hiding it.

honest analysis / where sutram loses

Honest analysis — where C and Rust win

A benchmark report that only shows wins isn't a benchmark report. Here's exactly where Sutram is behind, and why.

// arithmetic — C -O2 is ~1.8× faster than Sutram

On sum += i*2, Sutram takes 190 ms vs C -O2's 103 ms. C, Rust, and C++ all perform loop-invariant code motion (LICM) and strength reduction: the compiler sees that x*2 can be turned into an additive recurrence (sum += 2i ⇒ track a running +2), or even hoisted, so the multiply disappears from the hot loop.

Sutram's current codegen does not yet perform LICM, so the x*2 is recomputed on every one of the 100M iterations. That single missing optimisation accounts for nearly the entire gap. It's a known, scoped item on the compiler roadmap — not a fundamental ceiling.

// C -O2 still wins on the pure loop — 87 ms vs 101 ms

Even on the simple loop, C -O2 is ~16% faster. GCC/Clang have decades of peephole, register allocation, and instruction-scheduling work behind them. Sutram's ~15% gap on a pure counter loop is respectable for a young compiler, but it's a real gap — closing it is a matter of backend maturity, not marketing.

// Rust and C++ match C, and add safety

Rust (release) and C++ (-O2) produce machine code essentially as fast as C -O2, while Rust adds memory safety and C++ adds richer abstractions. On raw speed they are peers of C, and on the arithmetic benchmark they will beat Sutram for the same LICM reason. Sutram's pitch is not "faster than Rust" — it's "tiny + zero-runtime + near-native", a slot none of those three fills.

// Java and Go are close on speed — but carry weight

Java (warm JIT, ~120 ms) and Go (~110 ms) are within ~20% of Sutram on the loop. They are genuinely fast. The trade-off is dependency mass: Java drags a ~200 MB JVM, Go a ~2 MB runtime-embedded binary. If your constraint is "fast and tiny and dependency-free", Sutram, C, and Rust are the only realistic contenders — and among those, Sutram is by far the smallest artefact.

// where Sutram clearly wins

Three categories where the verdict is unambiguous: binary size (203 B vs the next smallest real binary of 4.7 KB — 23× smaller), runtime footprint (zero vs 35–200 MB for the interpreted/JIT languages), and speed vs interpreters (160× over Python, 1.9× over Node.js, while also being infinitely smaller in deployment). Sutram isn't trying to replace Python for data science — it's trying to be the language you reach for when "small, fast, and nothing else required" is the constraint.

methodology / notes

How these numbers were produced

Measured rows (Sutram, C -O2, C -O0, Python, Node.js) were actually executed in a sandbox: a 100 million iteration loop, timed as wall-clock, averaged over 3 runs. Estimated rows (C++ -O2, Rust release, Java HotSpot, Go) use well-known published benchmark figures for equivalent workloads, because those toolchains weren't available in the sandbox. C++ -O2 is expected to match C -O2 closely since both compile through the same backend and produce near-identical machine code for a trivial loop.

Binary sizes for Sutram, C -O2, and C -O0 are the actual output binaries. Sizes for the others are representative of a minimal "hello world"-class program in that language and will vary with toolchain, linker, and static/dynamic linking choices. Java's "binary" is the .class file; its runtime cost is the JVM. Python and Node ship source, not binaries — their footprint is the interpreter/runtime that must be present to execute them.

The bar chart clips Python's bar (which would extend ~40× past the chart frame) for readability; its true value is shown in the table and the multiplier section.
