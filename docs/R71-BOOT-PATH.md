# Round 71 — minimal firmware boot-path artifact

## What was produced

`boot/r71/boot.asm` is a 16-bit x86 BIOS boot sector written in NASM. The source
initializes segment registers and a stack, sets the direction flag, prints
`Sutram R71 boot-path probe` using the firmware video service, then halts.
It does not call Linux/Windows, read a filesystem, write a disk, allocate a heap
or access a network. Firmware is not an existing operating system.

The supplied 512-byte `boot.bin` and padded 1,474,560-byte `boot.img` are binary
artifacts from that source. The sector has the `55 AA` boot signature at offsets
510–511. In the local environment, the reviewed instruction subset was assembled
with GNU as/ld through `build_probe.py`. Its repeat build is byte-identical.

**The image was NOT booted here. It is NOT generated by the Sutram compiler.**
This establishes a concrete entry/layout/output artifact for the boot-path
workstream, not a freestanding Sutram implementation or a completed kernel.

## Entry and layout

The BIOS loads the boot sector at physical 0x7C00. DS/ES/SS are initialized to
zero; the stack starts at 0x7C00 and grows below the sector. All message addresses
are linked to the 0x7C00 origin. The code and message fit before byte 510. There
is no second stage, relocation loader, filesystem, allocator or libc.

The BIOS video call uses 16-bit firmware. This is not the future x86-64 kernel
ABI. A 64-bit Sutram kernel additionally needs a tested transition to long mode,
page tables/startup, a suitable native object/flat-output path, interrupt rules,
and non-firmware output once those modes are entered. These remain open.

## Reproduce the binary

From the repository root, using an already installed assembler:

```sh
nasm -f bin boot/r71/boot.asm -o /tmp/r71-boot.bin
```

The developer test bridge is an alternative only for this fixed boot source:

```sh
python3 boot/r71/build_probe.py --output /tmp/r71-boot.bin
```

It refuses an existing output. It does not install tools or execute the image.
In the supplement, binary artifacts are under `artifacts/boot/`, not claimed as
an installed Windows executable.

## Pending emulator acceptance

Use an already installed QEMU in a normal user session. Example:

```sh
qemu-system-i386 -drive file=boot.img,format=raw,if=floppy,readonly=on -boot a -nic none -snapshot -no-reboot
```

Use only the supplied image file, never a real block device. No administrator
permission is required by this procedure. The expected observation is the exact
message on the virtual display followed by no further progress. Record the
QEMU/firmware versions, image SHA-256, command and a screenshot. The expected
message is a test criterion, **not an observed result in this delivery**.

Windows GUI testing, a Linux process returning a value, or the boot signature
alone would not satisfy this emulator acceptance gate.
