Codegen Performance Analysis

Where Sutram's generated machine code spends its instructions — and the one change that would cut it most.

Source SHA a14d0241 · suite 123/123 · compiler 347,156 B
Method: delta-instruction counting over ndisasm disassembly of the emitted ELF

Why this document exists

Performance is the standing project priority, and the compiler is now feature-complete enough that speed — not features — is the main gap. Register allocation and local-memory traffic are the next work item. This analysis measures the current codegen so that work has a baseline and a target, rather than proceeding on intuition.

The compiler emits a real ELF (entry 0x400078, code at file offset 0x78) with no section headers, so objdump -d cannot read it; the disassembly here comes from ndisasm -b 64 -e 0x78. Per-construct cost is measured as a delta: two programs that differ by exactly one statement, subtracted, so prologue and the integer-print routine do not dilute the result.

The headline

10instructions for c = a + b (incl. decl) — ideal 3

0spills with ≤16 live variables — registers are used

Variables are allocated to registers (rbx, r12, r13, …) — that part works, and 16 live variables still do not spill. The cost is elsewhere: every binary operation routes its operands through the machine stack instead of using the registers the values are already in.

Finding 1 — binary operators bounce operands through the stack

For c = a + b, with a in rbx and b in r12, the compiler emits:

mov rax,rbx      ; load a
push rax         ; \
mov rax,r12      ;  |  operands round-trip through the stack
pop rdx          ;  |
xchg rdx,rax     ; /
add rax,rdx
mov r13,rax      ; store c

The same value could be produced in three instructions — and s = s + i in one:

mov rax,rbx      ; a is already in rbx
add rax,r12      ; b is already in r12
mov r13,rax      ; c

add rbx,r12      ; s = s + i, in a single instruction

This is not a register-allocation problem — the values are already in registers. It is that the expression evaluator is written as a stack machine: evaluate the left operand, push it, evaluate the right, pop and combine. In a tree-walking codegen that is the natural first shape, but the register file is sitting unused beside it.

Finding 2 — integer constants cost three instructions to load

A literal is materialised as xor rax,rax / mov al,N / mov rbx,rax — three instructions to put a small number in a register. A single mov rbx, N would do. This shows up in every constant initialiser and every literal operand.

What is already good

  • Register allocation works. Variables live in rbx/r12–r15; 16 simultaneous variables do not spill.
  • Loop conditionals are cheap. i = i + 1 compiles to mov rax,rbx / inc rax / mov rbx,rax — an inc is already used rather than add.
  • No hidden calls. Arithmetic is inline; there is no runtime to call into.

Recommendations, in order of expected payoff

1. Evaluate binary operands in registers, not on the stack

The single highest-value change. Keep a simple destination-register discipline for OP_ADD/SUB/MUL/DIV: evaluate left into a register, evaluate right into another, combine in place. This removes push/pop/xchg from every arithmetic statement — the most frequent construct in real code. A s = s + i inside a loop is the canonical case and drops from six instructions to one.

2. Load small constants directly

mov rN, imm instead of the three-instruction xor/mov al/mov sequence. Cheap and local to the literal emitter.

3. Peephole: mov rax,rX / … / mov rX,rax round-trips

Many statements end by moving a result into rax and straight back into the variable's register. A peephole pass that folds mov rX,rax into the preceding operation's destination removes a further instruction per statement.

PERF1 results — measured, not claimed

ChatGPT's PERF1 patch (source 532eaff7) attacks the exact hotspot above: values already register-resident were being copied through rax, the runtime stack, rdx and xchg. It adds direct self-update forms (x = x + y → one add), direct register comparisons, and cleaner punaravartana codegen. Both hosts rebuilt; suite 125/125; 113/114 outputs match exactly.

The hot loop, before and after

AFTER — 5 instructions
cmp rax,byte +0x64
jnl near 0x3d
add r12,rbx      ; s = s + i   — one instruction
inc rbx          ; i = i + 1   — one instruction
jmp 0x25

s = s + i is now a single add r12,rbx, and i = i + 1 a single inc rbx. The loop body drops from 13 to 5 instructions.

Why nested_loop barely moved — it is now branch-bound

The inner body shrank as promised, but the loop still carries two branches per iteration:

0x43  cmp r14,rbx
0x46  jg  near 0x57   ; forward conditional (exit)
0x4c  inc r12
0x4f  inc r14
0x52  jmp 0x43        ; backward unconditional

Once the body is only two instructions, the branch pair dominates. A test-at-bottom loop form — an initial jump into the test, then a single backward conditional at the end — would halve the branches per iteration:

        jmp test
top:    inc r12
        inc r14
test:   cmp r14,rbx
        jl  top        ; one branch per iteration, not two

That is the natural PERF2 candidate for loop-bound code, alongside the general c = a + b destination scheduling that PERF1 deliberately left out.

Revised recommendation order

  1. PERF1 is verified and a large win (loop_sum 4.9×). Keep it.
  2. Test-at-bottom loop form — the remaining cost in nested_loop is the branch pair, not the body. Halve the branches per iteration.
  3. General c = a + b register scheduling (PERF2) — the distinct-destination case still round-trips through the stack.
  4. Direct small-constant loads (PERF3).
  5. An instruction-count gate in CI, so these hot forms cannot silently regress.

PERF-F1 — the float hotspot, found by measurement and fixed

For five rounds the optimizer shrank integer instruction shapes. A static census of real numerical code showed why that produced no measurable speedup: 61% of assignments are float, and PERF5's integer pattern occurred 0 times in a realistic program and 4 times in the whole 13-module library. Meanwhile the float path cost 8× the integer path.

The fix keeps the operands out of general-purpose registers for a float self-update:

BEFORE — 8 instructions, with a stack round-trip
mov rax,r12
movq xmm1,rax
pop rdx
movq xmm0,rdx
addsd xmm0,xmm1
movq rax,xmm0
mov rbx,rax

AFTER — 4 instructions, no stack traffic
movq xmm0,rbx
movq xmm1,r12
addsd xmm0,xmm1
movq rbx,xmm0

This is the first optimization since PERF1 to move the clock. Still on the slow path: distinct-destination float (c = a + b), complex float expressions, and persistent XMM residency (which needs an explicit ABI design).

Method notes, so the numbers are checkable

  • Delta measurement: two programs differing by one statement; instruction counts subtracted.
  • Disassembly: ndisasm -b 64 -e 0x78 (skips the 0x78-byte ELF header; code begins at the entry point 0x400078).
  • Instruction totals include prologue/epilogue and the integer-print routine, which is why per-construct figures use deltas rather than totals.
  • Run-time samples use the median of ten runs, excluding I/O-bound programs.
