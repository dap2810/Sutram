How to use the library

Every module is a patra in lib/ ending in .smlib. You pull one into your program with yoj, naming it without the extension:

; bring in the maths module
yoj ganit

mukhya()
    vitti g = mahattam(48, 18)
    likha(g)
samapt

yoj is textual inclusion — the compiler pastes the module's source into your program at that point. That has three consequences worth knowing:

What that means in practice

  • Include a module once. Including it twice defines its functions twice and the compiler will refuse. Pull in only what you use.
  • Only functions, no namespaces. A function is called by its bare name, so two modules defining the same name would collide.
  • Resolution order: the source patra's own directory, then the compiler's directory, then the working directory.

A worked example

; checked arithmetic, digit work, and text
yoj ganita
yoj ank
yoj varna

mukhya()
    vitti ok[1]
    ; add, reporting overflow instead of wrapping
    vitti total = ganita_janchit_yuj(9223372036854775807, 1, ok)
    yadi ok[0] == 0
        likha("overflow — the phal is not the wrapped value")
    samapt

    ; digit work
    likha(ank_gan(12345))       ; 5
    likha(ank_yog(12345))         ; 15
    likha(viparyay_ank(12345))       ; 54321
samapt

The three layers

Every module declares what it touches, and a checker enforces the claim on every build:

  • core — pure computation. No heap, no OS. Safe anywhere, including a freestanding program.
  • alloc — needs a heap, still no OS service.
  • std — talks to the operating system. Only patra does today.

The checker fails the build if a module marked core calls an OS builtin — so a layer label is a kramgun the toolchain verifies, not a comment.

Two things to know before you rely on any of it

  • Checked forms return 0 on failure, never the wrapped value. For any operation that can overflow, use the ganita_checked_* form and read the ok cell. The plain operators + - * / % still wrap silently, and division by zero faults unless the trap build is enabled.
  • The whole library is verified by execution. 191 proof checks and 86 property checks run against it on every build, and the most recent audit exercised all 24 modules at their edges — finding and fixing 51 defects. That does not make it correct; it means the obvious failures have been found and the rest are labelled.
