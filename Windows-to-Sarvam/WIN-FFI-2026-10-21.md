## 2. The FFI on Windows - which part is which

### a. The sidecar's Windows target record

The v2 header (R34-11) already carries the ABI as its second field and refused `windows-x86_64-msabi`. Now:

- **`sutram-ffi-v2|windows-x86_64-msabi`** is accepted **only by a compile that writes a PE program** (the
  Windows compiler); **`linux-x86_64-sysv`** only by one that writes an ELF. Each mismatch is refused at line 1,
  exit 1, no object - tested: sysv on the Windows compiler; msabi on the Linux compiler (R32's net, 50 / 0).
- **msabi exists only under v2** - v1 stays R32's form exactly. Near-miss names (`windows-x86_64-ms`,
  `...msabiX`) and `v3` are refused. The declarations and their kinds are unchanged.
- The change is in `r32_load_sidecar` (the header) and the argument parsing (`--ffi` is no longer `%ifndef
  WINDOWS`: on Windows `argv` lives in `win_stack`, and only that shift differs).

### b. The Microsoft x64 call (ChatGPT `ROUND-100-WS3-WINDOWS-X64-ABI.md`)

- **Argument k by its POSITION:** `rcx rdx r8 r9`, or **`xmm0..xmm3` for an f64 at that position** - not the
  next free xmm. `f(i64, f64, i64, f64)` is **`rcx, xmm1, r8, xmm3`**.
- **The 5th and 6th on the stack:** `[rsp+32]`, `[rsp+40]` at the call (the callee's `[rsp+40]`, `[rsp+48]`).
- **A 32-byte shadow space for every call**, `rsp = 0 mod 16` at the call:
  `mov r11, rsp / and rsp, -16 / push r11 / sub rsp, 56 / [mov [rsp+32], r10] [mov [rsp+40], rax] / call / add rsp, 56 / pop rsp`.
- The result: `rax`, or `xmm0` for an f64. Volatile registers: Sutram keeps nothing in a register across the
  call, so the Microsoft set (narrower than System V's) is safe; tested with a callee that destroys every one.

### c. COFF ingestion - `sutram-coff2smo`

`linker/sutram_coff2smo.asm`, NASM, **one source built for both hosts** (`sutram-coff2smo`,
`sutram-coff2smo.exe`), the Windows counterpart of `sutram-elf2smo`. **It writes SUTRAMO2 - version 2 is
unchanged; no field was needed, so there is no version 3.** One code section; read-only data after it at its
alignment (at most 16); only `IMAGE_REL_AMD64_REL32`..`REL32_5` relocations in the code, all resolved in the
reader; refused: calling out, writable data, bss, unwind tables, `.drectve`, relocations in data, a weak
external. `tools/sutram_build.py --foreign f.obj` picks the reader from the object's own first bytes.

**One linker rule came with it:** in a PE, `sutram-link` starts **every object after the first on a 16-byte
boundary of the image** (int3 padding). GCC reads 16-byte constants with aligned SSE (`xorpd` for `-x`), and
a PE's code starts at RVA `0x1000 + 759`, unaligned. **Linked by `main`'s `sutram-link.exe` (no padding), the
test program crashed at `w_neg`** (the C object began at 14 mod 16); with the padding it runs. The first object
does not move - **every example linked alone is still byte-identical (182 / 182)** - and the ELF does not change.

## 4. Not done, and why

- **Varargs (`printf`), structs by value, a 16-byte struct result (the hidden pointer), callbacks** - not in
  the sidecar's kinds; refused or absent, as on Linux and as WS3 says to start.
- **A C function that calls out** (into libc or a DLL), **DLL imports, exception unwinding** - refused by the
  reader; the import table the PE writes is the runtime's own (kernel32), not the FFI's.
- **More than 6 arguments** - the sidecar's arity is 0..6 on both platforms (Windows puts 5 and 6 on the stack).
- **`SUTRAM_LANG` on Windows** - the Windows compiler reads no environment; not this change.
- **The installer is not rebuilt** for v245 - it carries v243 and has no `sutram-coff2smo.exe`. Rebuild once
  this is accepted (and `windows-build-integrity.sha256` is re-signed - R34-02).
- **Merging** - the branch is pushed for Sarvam to accept, as AGENTS.md asks. `Sarvam-to-Claude/` and
  `Claude-to-Sarvam/` were not touched.

**Two mistakes of mine, both caught before this was written:** `src/r32_ffi.inc`'s pin was set before its
header comment changed, so `--check-only` refused a clean clone of `c6ef3b36` - re-pinned in `79654e20`,
`SOURCE_PINS_CHECKED` on an LF clone and a Windows clone (`pins.txt`). And Git Bash's `.exe` name magic made
one copy write the Linux reader over `sutram-coff2smo.exe`; the Windows test could not start it (WinError
216), the copy was redone with PowerShell, and the committed pair is right (`MZ` and `ELF`, and they rebuild
byte for byte).
