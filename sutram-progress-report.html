Why the arithmetic loop is the interesting one

On the simple loop Sutram is essentially at native speed. On the arithmetic loop it is 5.4× off hand-optimal code — and the reason is known and documented, not mysterious: the expression evaluator is written as a stack machine, so every binary operation pushes its operands and pops them back even though both values are already sitting in registers. There is also no loop-invariant code motion, so i*2 is recomputed every iteration instead of strength-reduced. That single fix — using the register file the values already occupy — is the largest remaining performance win available.

4 · The honest summary

What is genuinely strong

  • It is a real compiler. 20,230 lines of hand-written x86-64 assembly in one file, emitting native ELF with no runtime, no libc, no linker script of its own — and it beats Node by 8× and Python by 167× on a loop.
  • The safety net is unusually good for a young language. 186 regression tests, 12 codegen ceilings, 30 pack checks, 18 module-graph tests, 147 library proofs, 33 properties, and four byte-identical reference binaries held across every single merge. Changes are verified, not hoped for.
  • Diagnostics are a genuine feature now, not an afterthought: located, recoverable, accumulating, with correct file attribution through nested imports.
  • It runs real programs. Three non-trivial programs — word frequency, an expression evaluator with precedence, a formatted report — compile and reproduce their goldens exactly.

What is honestly weak

  • No optimiser. This is the single biggest gap and the clearest opportunity.
  • Nothing has ever run on real Windows — the one untested platform claim.
  • No concurrency, no ecosystem, no FFI, no debugger, no package manager. Five parameters at 0–5%, all of which need people rather than code.
  • The suite is a corpus, not a proof. 186 passing tests does not mean 186 correct behaviours.

What would move the needle most, in order

  • A register-based expression evaluator — closes most of the 5.4× arithmetic gap. Big, contained, measurable.
  • Module-level globals — the remaining half of R55, and the thing that makes larger programs bearable.
  • A real Windows end-to-end run — one binary, executed, converts the biggest unverified claim into a fact.
  • Library breadth — formatting, file I/O, dates. The 45% bar is the one most within reach.
