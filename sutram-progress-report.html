Three figures that are stale — understated, not overstated

  • B · Optimiser, 15%. Predates R65. The peepholes and the integer trap are implemented and measured — a probe shrank from 563 to 560 bytes with identical stdout, and the trap fires on all five arithmetic cases with correct file:line.
  • D · Standard library, 50%. Written when the library was far smaller. It is now 278 functions across 21 modules, with a complete checked/saturating arithmetic surface, containers, maps, sets, and both string and byte-string toolkits.
  • Devanagari is well ahead of the scorecard. Sanskrit keywords, the danda, native digits, 54 pack entries, and GUI support through colour, cluster advance and a cluster-accurate caret.

4 · The one number that is overstated

G · Cross-platform & packaging reads 38%. The honest figure for verified Windows support is closer to zero.

The Windows acceptance has never been executed by anyone. The Windows compiler and IDE build, the PE headers are correct, and the installer payload is complete and hash-verified — but no Windows binary has ever been run. A GUI that builds is not a GUI that works.

This is the largest gap in the project, and the only one that is an assumption rather than a measurement. Running the acceptance once converts it into a real number.

6 · The honest summary

Genuinely strong

  • One pure-NASM compiler, native output, no runtime dependency
  • A frozen keyword core held across every merge
  • Verification that catches real regressions, not just a corpus that passes
  • Indian-language support that is real, not decorative

Honestly weak

  • Windows support is unproven — never executed
  • No concurrency model at all
  • No ecosystem: no packages, no releases, no community
  • Optimiser still early; no glyph shaping

What would move the needle most, in order

  1. Run the Windows acceptance once. It turns the project's biggest guess into a measurement, and it is the only item on this page nobody has ever tested.
  2. Concurrency, or an explicit decision not to have it. 0% is not a gap that fills itself.
  3. A release and a package story. Ecosystem at 5% will hold v1.0 back more than any compiler gap.
  4. Finish the Indic roll-out — Gujarati's pack collides with an accepted test and needs resolving, then the remaining scripts are mechanical.

7 · Bottom line

As a compiler, this is around 85% — the hard part is done, and done in the most difficult way available: one hand-written assembly source, native machine code, no runtime, and a verification net that holds.

As a usable language, it is nearer 55% — the library is real but not yet broad, the tooling is good on Linux and unproven on Windows, and there is no ecosystem at all.

Toward the project's own v1.0 definition, roughly 60%. The single highest-value remaining action is not another compiler feature; it is running the Windows acceptance, because until that happens the largest gap on this page is an assumption rather than a kramgun.
