## WS1 — three small things

### 1. The two splitters (`varna_bhed`, `khand_bhed`) — fixed

ChatGPT's R140 found two problems; both were real.

- **Class B, `maxparts = 0`:** the contract says the count is capped at `maxparts`, but the empty-input and
  empty-separator paths wrote one segment and returned 1 before looking at the cap. **Both functions now return 0
  and write nothing when `maxparts <= 0`** — ChatGPT's preferred resolution, and the one the test that covers
  them already claimed: `tests/stdlib/r8_split_model.sm`'s header says its expectation is *"Python's str.split,
  truncated to maxparts"*. I printed every one of its 300 inputs and scored both functions against that model
  (`evidence-r69/splitters-vs-model.txt`): **old library 40 results differ — exactly the `maxparts = 0` cases on
  the two special paths, 6 + 14 per function; new library 0.** The golden had recorded the 40 wrong answers;
  it is re-recorded (the only golden that moved).
- **Class C, capacity not stated:** now stated. **`varna_bhed`: `sn + 1` cells. `khand_bhed`: `sn + 2` cells** —
  `khand_mukt` writes a `0` cell after each segment it copies, and the last one lands one past the segments. The
  inline comment that called that cell *"harmless"* now says why it needs the extra cell.

Not touched, though R140 classes them the same way: `nighantu_kunjika` and `rakh_tak_mala` (also `33·cap + 1`,
same `khand_mukt` cell). The brief named the splitters; those two contract lines are one each, listed in R68-00.

### 2. The pack/unpack proof can no longer regress silently

**It could have.** The fixed seed draws lengths 6, 1, 5, 3, 4, 3, 1, 5 — never 8, the only length at which R68's
8-cell buffer overran. Two changes in `prop_strb_pack_unpack`:
- **a fixed length-8 case (`"abcabcab"`) is always appended** — after the random draws, so no other property's
  random stream moves;
- **after `khand_mukt`, the proof checks that `out` — the next allocation after `back` — still holds its bytes**,
  so the overrun is caught on the ordinary compiler, not only under guard pages.

**Shown, not argued** (`evidence-r69/pack-unpack-regression.txt`): the same file with `back` put back to 8 cells,
ordinary v263 compiler → **`FAIL strb_pack_unpack: unpack wrote past back`, 85/86.** As committed: 86/86.

### 3. The guard-page run is a permanent tool and a gate

- **The build lives in the compiler source**, behind a flag: `nasm -dGUARD_PAGES`. `r38_nirm_seq` jumps to a
  94-byte sequence that `mmap`s the block's pages plus one, `mprotect`s the last page `PROT_NONE`, and returns
  `guard − size` — the block ends on the byte before the unreadable page. The ordinary build does not contain it.
- **`tools/guard_page.py`** builds that compiler in a scratch directory and runs, in order:
  - **the controls, `tests/guard_page/`** — each `control_*.sm` must SIGSEGV, `clean_*.sm` must exit 0:

    | control | the real bug it reproduces |
    |---|---|
    | `control_217_overrun` | `examples/217_r12_report.sm` before R68: 4 cells handed to `pad_vam(width 6)` |
    | `control_proof_overread` | the *bigint divmod reconstruct* proof before R65: a **read** of cells 8..15 of an 8-cell block |
    | `control_pack_unpack` | `prop_strb_pack_unpack` before R68: `khand_mukt` writes cell 8 of 8 |
    | `control_one_byte_past` | one byte past a 13-byte block — the guard is exact to the byte |
    | `clean_last_byte` | the 13-byte block's last byte, written and read — the guard is not one byte too tight |

    If a control does not fault, the build is not a guard-page build, and the tool says so and does not run the
    corpora. **Every one of the four runs silently on the ordinary compiler** (exit 0) — which is the point.
  - **the suite, the 226 library proofs, the 86 property proofs.** Last line, e.g.
    `guard pages: controls 5/5, suite PASS=225 FAIL=0, library proofs 226/226, property proofs 86/86, 0 failed`.
  - `--quick` runs the controls only (seconds).
- **`tools/gates.sh` runs it as the gate `guard pages`.** The gate count moves from 48 to 49 PASS; `PROJECT-MASTER.md`
  still quotes 48 and `doc_counts_gate` NOTEs it (below).
- **What it cannot see, written into the tool's own docstring:** paths no test runs; an access that jumps far past
  the guard page into another block without touching it; a negative index (the page *before* a block is not
  guarded); mistakes inside a block's own bytes; Windows. The static audit (R68-00) is the other half.

## WS2 — Step 2, `dvi-mukha`

### What was built

One range, two cursors, three hidden module globals (`src/r65_arena.inc`):

| global | role |
|---|---|
| `0kshetra_cur` | **persistent cursor** — grows up from the start (unchanged from Step 1) |
| `0kshetra_end` | **scratch cursor** — starts at the top of the range; from Step 3 it grows down. It is also the persistent side's limit |
| `0kshetra_sima` (new) | **the range's true end** — the scratch side's own limit (`end == sima` means the scratch side is empty) |

**The persistent fast path is the same comparison as Step 1, `room = end − cur`, but `end` is now the scratch
cursor — so the persistent side cannot grow into scratch memory, and `kosh` growth (which is persistent, including
in-place extension, which checks against the same `end`) cannot either. The R61 case 4b is not expressible.**

**Constraints, as asked:**
- **The persistent path does not change behaviour:** 248 programs changed bytes, **248 same output and exit code**.
- **Nothing uses the scratch cursor:** it is reserved, set to the top at the first `nirmmita`, and never moved.
  No path reads `0kshetra_sima` yet.
- **The guard-page run still passes and still faults on the controls** (5/5, 0 failed).

**One structural change I made to fit it:** in Step 1 the reservation sat after the fast path and jumped back
(`jmp .retry`, −126 bytes, the edge of a `rel8`). One more store would have pushed both that jump and the fast
path's `jb .mmap` past `rel8`. So the reservation now comes first and **the fast path jumps over it once the arena
exists** (`test rax,rax ; jnz .have`); success and failure share one store sequence (failure sets all three to 16,
room 0 forever, as before). **No backward jump, every jump `rel8`, and the sequence is 152 bytes against Step 1's
151** (`evidence-r69/sequence-v263-v264.txt`, both disassembled).

## WS3 — the block's scope, in `docs/MEMORY-DECISION.md`

New section, **"What a `mandapa` block can hold in v1.0 — and what it cannot"**, plus **"Step 2 as built"** beside
the Step 2 description (which still says `.bss`; the as-built note explains the `MAP_NORESERVE` range instead of
editing the decision text). The section has the allowed/refused table from ChatGPT's K0 profile, a sentence for a
beginner, and the usefulness stated plainly. **One thing in it is new and makes the block smaller than even the
K0 framing suggests:**

**Because the region is lexical, a block in a caller does not reclaim what a library function allocates inside
its own body** — that `nirmmita` uses the persistent cursor by the rule decided in Step 3. Muse's R68 count found
one example the block would help (`217`, whose loop calls `ank_tak_varna`, which allocates 176 bytes per call).
**Under the lexical rule, a `mandapa` around that loop reclaims nothing** — the allocation is in the library body.
So among the examples, the caller-side count is **0**. **Where a v1.0 block does help is inside the library:**
`ank_tak_varna`, `ank_tak_aadhar_varna`, six roop formatters, `brihat_ank_tak` and the brihat division helpers each
allocate scratch on every call and never release it, and use it only inside their own body. Those bodies are the
block's first real users — if Step 4's checker can prove their indexing. The doc says this; it is the honest scope.
