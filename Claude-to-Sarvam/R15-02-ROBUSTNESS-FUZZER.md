# R15-02 — WS2: a robustness fuzzer

**The compiler crashes on invalid input: 107 of the 50,171 inputs tried, Linux, main's compiler.** All 107
fall into **six kinds**. Each has a small file in `evidence-r15/robust/`. **None hangs.** None of the six is
fixed by the D2/D3 fix (R15-01): it is a different defect each time.

## The tool

`tools/fuzz_robust.py`. Two parts:

1. **171 fixed cases, one per kind of hostile input.** All generated by the tool, none committed except the
   crashes. They include:
   - an empty file, and NUL bytes (alone, inside a name, inside a string)
   - unclosed braces, parentheses, strings, block comments and index brackets
   - nesting 100, 1,000, 10,000 and 100,000 deep: parentheses, braces, `yadi`, unary minus, the ternary,
     calls
   - 100 to 100,000 statements, locals, functions, globals or record fields
   - a 1 MB name, string and comment
   - malformed UTF-8 (lone continuation bytes, `FF`, truncated sequences, overlong forms, surrogates, past
     U+10FFFF), each in a name, a string, a comment, at the end of the file, and in Devanagari
   - a BOM, CR-only line ends, UTF-16
   - 64 KB of random bytes, and the compiler binary itself as source
   - `yoj` of a missing module, of `../../etc/passwd`, and of eight modules
   - **a 10 MB and a 50 MB file, a single 100 MB line, and a 100 MB expression**
2. **Mutations of valid programs.** The seeds are every `examples/*.sm` and 60 programs from
   `fuzz_valid.py`. Each mutation is one to five edits: truncate, delete a run, insert a token or random
   bytes, flip a bit, duplicate a run, swap two lines.

**Each run is one of four outcomes:**

| Outcome | Meaning |
|---|---|
| **CRASH** | killed by a signal |
| **HANG** | still running after 20 s |
| **ERROR** | non-zero exit: the right answer |
| **ACCEPTED** | exit 0 |

**Every CRASH and HANG input is saved.** `--reduce FILE` shrinks a crash by delta debugging: first lines,
then bytes.

```sh
python3 -B tools/fuzz_robust.py --seed 15 --mutations 50000     # the run below: about 4 minutes
python3 -B tools/fuzz_robust.py --reduce some-crash.sm
```

## The run (seed 15)

| Inputs | ERROR | ACCEPTED | **CRASH** | HANG |
|---|---|---|---|---|
| 171 fixed cases | 107 | 59 | **5** | 0 |
| 50,000 mutations | 43,242 | 6,656 | **102** | 0 |

## The six crashes

**Each of the 102 mutation crashes was reduced, then sorted by hand into the kinds below**
(`mutation-crashes-reduced.txt`: every reduced input, one per line).

| # | Input that crashes the compiler (SIGSEGV) | Of the 102 | File |
|---|---|---|---|
| **R1** | **`yoj` as the last bytes of the file** (no newline after it) | 27 | `R1-yoj-at-end-of-file.sm` (3 bytes) |
| **R2** | **a function's parameter list cut off by the end of the file:** `prakriya f(` or `prakriya f(a,`. Also a number where a parameter name should be, then the end of the file (`prakriya f(0)q`). **Note: `prakriya f(0) { … }` compiles.** | 40 | `R2-…`, `R2b-…`, `R2c-…` |
| **R3** | **a `rachana` field list cut off by the end of the file:** `rachana P = {` | 9 | `R3-rachana-at-end-of-file.sm` |
| **R4** | **`anya yadi` after a finished `anya` block** | 5 | `R4-anya-yadi-after-anya.sm` |
| **R5** | **an expression on the left of `=`:** `x + 1 = 7`, `a[1] + 1 = 2`, `likha("") = x`. **But `5 = 7` and `likha(1) = 7` compile without a word.** | 21 | `R5-…`, `R5b-…` |
| **R6** | **nesting about 19,000 deep:** parentheses, braces, unary minus, nested calls. 18,000 deep does not crash. It is recursion running out of stack. **A 40 KB file is enough.** | 5 fixed cases | `R6-parentheses-20000-deep.sm` |

**R1, R2 and R3 are the same kind of bug:** a parser step reads the next token without checking for the
end of the file. The fix is probably the same in each place, but **I have not read the parser to confirm
it.**

**How I sorted them:** by the shape of the reduced input, then I wrote a clean version of each shape by hand
and confirmed that it crashes.

## Accepted, but should not be

These are not crashes, so they are not failures under the WS2 rule. **But each one accepts a wrong program
without a word, and three of them are silent wrong answers.**

| Input | What happens |
|---|---|
| **an integer literal past 64 bits:** `99999999999999999999999999999`, `9223372036854775808`, `18446744073709551617` | **compiles, and wraps silently:** prints `7886392056514347007`, `-9223372036854775808`, `1` |
| `mala a[-5]`, `mala a[99999999999999]` | compiles; **the program crashes (SIGSEGV)** at the first store, with no diagnostic |
| `mala a[0]` | compiles; the first store stops with `mala ank seema atikram` (correct, but at run time) |
| **two `mukhya`** | compiles; **the second is ignored** |
| **text after the program:** `} } likha(5)` after `mukhya` | compiles; **ignored** |
| `5 = 7`, `likha(1) = 7`, `(x) = 7` | compile |
| `yadi … anya { } anya { }` | compiles |
| `prati` with no value in `mukhya` | compiles |
| NUL bytes in a string; malformed UTF-8 in a string or a comment | compile (arguably right for comments) |

**A source file over 64 KiB is cut at 64 KiB without a word.**

- The compiler reads one 65,536-byte block (`source_buf`). **The largest file that compiles is 65,537
  bytes.**
- Anything longer is parsed as its first 64 KiB, so it gets whatever error that cut produces, for example
  `vyakaran dosh, pankti 1:2, shabd 'patra-ant'`, with the cut first line echoed.
- **So only the first 64 KiB of the 10 MB, 50 MB and 100 MB inputs ever reached the parser.** Those cases are
  weaker than they look.
- **The error should say the file is too long.**
