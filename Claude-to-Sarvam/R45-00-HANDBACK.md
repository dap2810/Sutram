## WS1 — the debugger

```
sutram --debug <in.sm> <out>
sutram --debug --lang <pak> <in.sm> <out>
```

Before every statement of the program's own file, the program prints the statement's **line** and **every scalar
variable in scope**, then goes on:

```
[shodhan] pankti 11
    yoga = 2
    ardha = 0.500000
    i = 2
[shodhan] pankti 2
    n = 2
```

(From `evidence-r45/example.sm`. The full trace is `evidence-r45/example-trace-linux.txt`.)

### How it is built, and why that way

**The trap is not new machine code. It is ordinary Sutram statements.**

- The trap is `likha("[shodhan] pankti 11\n")`, then `likha("    yoga = ")`, then `likha(yoga)`, and so on.
- Those statements are built as AST nodes and generated by `gen_stmt`, **exactly as if they were written in the
  source before the statement.**
- **This is the technique the compiler already uses** for its bounds-check failure message.

**So, with no new code path:**

- A variable held in a register prints correctly.
- So do a parameter, a `dasham` and a Devanagari name.
- A PE program prints the same trace: the Windows compiler's trace, under Wine, is identical to the Linux one.
- Every statement-level cache in the code generator is invalidated by these statements, as by any statement.

**Two hooks, in `src/r45_debug.inc`. Both are skipped without the flag:**

- **`parse_stmt` is now a wrapper.** Without the flag it jumps straight to the old body. With it, it notes the
  source position of each statement's first token.
- **`gen_stmt` tests `r45_debug`.** Without the flag, nothing else changes.

### What it shows, and what it deliberately does not

| | |
|---|---|
| **The line** | **the original file's line**, mapped the way parse errors map it (`r51_origin_line_col`), so `yoj` does not shift it |
| **The variables** | the current function's locals and parameters, in declaration order. A shadowed name is shown once, as the inner one |
| **Not traced** | **statements that came in through `yoj`.** A library call is one step, not hundreds of lines |
| **Not shown** | a `mala`, `kosh` or slice (`likha` would print an address); a module-level `vitti` (not in the function's table); a name longer than 112 bytes |
| **No trap before** | **`yantra("...")`.** Raw machine code may depend on registers that the previous `yantra` set: `examples/29_nishkriya.sm` splits `mov/mov/syscall` over three. **The suite found this. The first version broke that example.** |
| **Where it goes** | where `likha` goes: **standard output**, in order with the program's own output |

## R45b — a defect I found after pushing, and fixed: out-of-scope variables

**After R45 landed, ChatGPT's R120 spec named a risk:** *"visibility is not the same as var_table membership"*. **I
tested it instead of arguing with it, and it was real.**

- `var_table` is **flat per function**. Block scope is enforced only at parse time.
- So **a name declared inside a `yadi` block was still printed after the block ended.**
- **In a branch never taken, it would have shown an uninitialized slot.** That is a wrong value, which is worse
  than none.

**The fix, in v252, works under `--debug` only:**

- `alloc_var` and `gen_block` are wrapped the way `parse_stmt` is.
- A declaration makes its name visible at the current block depth.
- The end of that block hides it again.
- A new function starts clean.
- **Without the flag, both wrappers jump straight to their bodies.** The guard, v251 → v252, is 0 DIFFER on all three
  paths.

The case is now a permanent check (`evidence-r45/scope-example-trace.txt`):

- `b` is shown only inside its block.
- `z`, declared in a branch never taken, is never shown.

## WS3 — my capability choice

**I made the whole suite run under `--debug` and compared it with its expectations.** The reason, in one sentence: **a
debugger that changes what the program does is worse than none, and only the whole suite can show it does not.**
That check is what found the `yantra` case.

## What I did NOT do, and why

- **No stepping, breakpoints or variable inspection on demand.** The brief asked for the smallest version: trap,
  print, continue.
- **The output is not on stderr.** It goes through `likha`, so it shares stdout with the program, in order. Moving
  it to stderr needs a new runtime path, and that is a bigger change than "smallest".
- **The usage text does not mention `--debug`.** That text is a message in all eleven language packs, and ten of
  them are frozen.
- **ChatGPT's R120 spec asks for more than this round built,** and I agree with its direction:
  - typed displays for `mala`, `kosh` and slices;
  - globals;
  - "changed values first";
  - step / continue / quit controls;
  - output on stderr.
  - **What R45 does instead:** it shows only what it can show **correctly**, and leaves the rest out rather than
    print an address. It does not yet print an explicit "unavailable" marker. Each of those items is a round of its
    own.
- **The label `[shodhan] pankti` is mine** (शोधन). R120 proposes पङ्क्तिः for "line", which agrees. It is one string
  in `src/r45_debug.inc`.
- **The label is not translated by `--lang`,** for the same frozen-pack reason.
- **`--debug` with `--object`, `--separate`, `--ffi` or `--check`: not supported.** It is a usage error.
- **Not run:**
  - **real Windows:** Wine only this round. The R42 workflow could run this on GitHub's Windows runner;
  - **`fuzz_robust` under `--debug`.**
- **Not touched:** `backups/`, `lang/` and `windows/`. **The non-Sanskrit packs are unchanged.**
- **No prose document describes `--debug` yet.** That is ChatGPT's or yours; the header of `src/r45_debug.inc`
  has the full description.
