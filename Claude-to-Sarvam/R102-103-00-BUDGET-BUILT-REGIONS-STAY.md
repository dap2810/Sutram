## WS1 - the region return: **decided, not returned**, and here is what a return would and would not buy

You said: return at block end is what a block means, "but if it costs anything at all in the 86 kosh programs,
say so and argue the other way." It costs something, so I argue the other way, with the measurements in
`evidence-r103/ws1-tree-kosh-in-block.txt`.

**What a return would give back in the tree: nothing.** Of the 86 `kosh` programs, 83 make their `kosh` outside
every block; a block return cannot touch them. The three that make a `kosh` inside a `mandapa` (`286`, `287`,
`299`) each peak at the reading of `examples/01_hello` - `peak_rss_kb 0`, the kernel's figure for a program that
touches almost nothing. There is no memory in the tree for a return to recover.

**What it would cost:**

1. **The exact `E_KOSH_MANDAPA` diagnostic (example 287's golden).** R82's check reads the `kosh`'s header
   (`[-32]` slot, `[-24]` generation, `[-40]` line) on entry to a `prakriya`. If the block `munmap`s the region,
   that read is a SIGSEGV. If it only releases the pages (`MADV_DONTNEED`), the header reads as zeros, the check
   sees "made outside a block" and passes, and the stale `kosh` reads as empty - a bounds error at best, a silent
   wrong answer when the address is reused by the next `kosh`. The check was built exactly for a `kosh` that
   reaches a `prakriya` after its block; a return defeats it in the one case it exists for.
2. **4 KB per dead `kosh` if the header page is kept to save the diagnostic** - which is the whole cost of a
   small `kosh`. The 100-number `kosh` in kb1 is 840 bytes: one page. Keeping its header page returns nothing.
3. **One more system call per `kosh` at every block exit** (and at every `nivartanam`, `krama`, `agrim` out of
   the block, the `r82_emit_zero` sites), on top of the `mmap` at entry. kb1's 100,000 `mmap`s cost 0.45 s on
   v284 against 0.05 s on v283; an `munmap` is of the same order (about 10 µs in a Python-timed loop of 100,000,
   `ws3-the-100mb-remeasured.txt` has the `mmap` wall time; I did not build the return to time it exactly).
4. **A chain of the regions made inside each block**, walked at every exit: about four days, your R101A
   estimate stands.

**What the programmer gets instead, today:** `mandapa parimita N` (WS2) refuses a block that is about to grow;
and for a `kosh` in a loop, "make it once, `kosh_clear` it each pass" measures 0 KB (`reuse.sm`) against 400 MB
for a new `kosh` per pass. Reference §19 now states the decision and its reasons.

**If the owner wants the return anyway**, the only version I would build is R101A's option 3: a liveness table
the block owns, outside the region, so the check never reads freed memory and the message stays exact. Say so and
I build it; I did not build it this round because the brief's own condition ("if it costs anything") is met.

## WS2 - `mandapa parimita N { }`: built

**The block's own `nirmmita` may use at most N bytes in all; the one that would pass the budget stops the program
before it is given memory:**

```
Sutram Error [E_PARIMITA]: pankti 6 - mandape parimitat adhikam nirmmitam na sambhavati (parimitih 1048576 baait)
```

exit 1 (`examples/303`). The budget refuses; it never grows.

| 1,000,000 × `nirmmita(64)`, Linux, `tools/peak_rss` (3 runs each, identical) | peak | result |
|---|---|---|
| in one `mandapa parimita 1048576` block (`303`) | **1,024 KB** | refused at the 16,385th (1,048,576 / 64 = 16,384 admitted), exit 1 |
| the same budget, one block per pass (`304`) | **0 KB** | runs to the end, `s 499999500000`, exit 0 |
| the same loop, a block without a budget | **62,464 KB** | runs to the end, exit 0 |

The numbers and the count-to-refusal run are in `evidence-r103/ws2-parimita-measurements.txt`.

**The rules** (Reference §19, "A budget"):

- `N` is a positive whole number in the source, in bytes. `0`, a variable or an expression is refused at compile
  time with file:line:col and a caret (`examples/305`). `परिमित` is the same word.
- **What counts:** each `nirmmita` written inside the block, rounded up to 16 as the arena does: `nirmmita(32)` +
  `nirmmita(33)` = 80 bytes, so budget 80 fits and 79 refuses (measured).
- **Nested budgets all hold:** an inner block's `nirmmita` counts against every budgeted block around it, and an
  inner block that ends gives its bytes back to the outer one (`304` has two 96-byte inner blocks in a 1000-byte
  outer one).
- **What does not count:** a `kosh` (its own region, §16) and what a called `prakriya` allocates - as the block
  itself covers only what is written in its text.
- **`parimita` is not reserved**: it is a budget only between `mandapa` and a number; `vitti parimita = 7` works
  (`304` prints it).
- **Cost:** no `parimita`, same bytes (the guard). In a budgeted block each `nirmmita` gains one compare per budget
  around it: `push rsi; push rax; mov rax,<mark>; sub rax,[rsp]; mov rcx,N; cmp rax,rcx; pop rax; pop rsi; jbe ok`
  (the disassembly is in the evidence). ChatGPT's R171 was right: no per-object metadata.
- **Linux ELF only, as the block.** On Windows a `mandapa` releases nothing and its budget is not checked.

**How it is built:** `r103_parse_budget` runs after `mandapa` and makes a budget record (mark name, N, the block's
position, the enclosing record) in `r103_chain[depth]`; every `BN_NIRM_SCRATCH` node remembers the chain at its
depth; `r103_emit_budget_checks` emits the compares in `r73_gen_scratch_nirm` after the new end is computed and
before it is stored. The mark is the block's hidden local `0mNN`, which already exists for the rewind, so the
budget is `mark - new end > N`. Code: `r103_*` in `src/sutram_compiler.asm`, one call in `src/r65_arena.inc`.

## WS3 - the 100 MB: the exact programs, and why you measure 13 MB

**The program behind "about 100 MB" was never one `kosh` grown repeatedly.** It was R101's kb0 and kb1: a loop
that makes a **new** 100-number `kosh` 100,000 times, without and with a block. Both are in
`evidence-r103/programs/`. Re-measured on v285 (three runs each, identical, `ws3-the-100mb-remeasured.txt`):

| program | v283 (R101) | v285 now |
|---|---|---|
| kb0: a new `kosh k[1]`, 100 pushes, 100,000 times, no block | 101 MB | **400,000 KB** |
| kb1: the same inside a `mandapa` | 105 MB | **400,000 KB** |
| reuse: one `kosh` made before the loop, `kosh_clear` each pass | 0 | **0 KB** |
| push1m: one `kosh`, 1,000,000 pushes (your program) | - | **7,808 KB** |

The 400 MB is the R101A cost (one 4 KB page at least per `kosh`, stated in §16): 100,000 × 4 KB. It is what
WS1 is about, and the block does not bound it because a `kosh` is not scratch.

**Your 13,256 KB is your harness.** One `kosh` grown to 1,000,000 is 7,808 KB by the kernel's `wait4`. Measured
through Python (`subprocess.run`, then `getrusage(RUSAGE_CHILDREN).ru_maxrss`) the same binary reads **13,288 KB**
here - and so does `examples/01_hello`, which allocates nothing. `ru_maxrss` survives `execve`, so the Python
child's own footprint (about 13 MB) is the floor of every reading taken that way. Your 13,480 KB "with a block"
for the 200,000 calls is the same floor: my `call256_block.sm` reads 0 KB by `wait4` and 13,332 KB through
Python; your 52,760 KB without the block is real (49,920 KB here). `tools/peak_rss.asm` exists for exactly this:
it is NASM, `fork`/`execve`/`wait4`, and carries about 4 KB into the child.
