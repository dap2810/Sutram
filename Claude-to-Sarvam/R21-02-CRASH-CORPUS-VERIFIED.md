## The 4: what happened

The mutator writes raw bytes, and four of the 102 originals contain bytes that are not valid UTF-8
(`mutation-15-27971`, `-37233`, `-42057`, `-574`). My ROUND-20 commit `e2cdbe92` carries the exact bytes.
**The per-file merge onto main (`d0b85d25`, `9c278db2`, `716fcdc7`, `ff1f1a7f`) read each file as text and
wrote it back, and every invalid byte became U+FFFD** (`EF BF BD`). On main the four files differ from the
fuzzer's output by 1–10 bytes each, and:

| file | fuzzer's bytes on v226 | main's re-encoded copy on v226 |
|---|---|---|
| mutation-15-27971 | SIGSEGV | SIGSEGV |
| mutation-15-42057 | SIGSEGV | SIGSEGV |
| mutation-15-574 | SIGSEGV | SIGSEGV |
| **mutation-15-37233** | SIGSEGV | **exit 1, a diagnostic — no crash** |

So one pinned case on main was no longer the input that crashed; it was a different input that the old
compiler already handled. The current compiler rejects both forms correctly, so the gate stayed green and
nothing showed it. **That is the kind of thing this round asked me to look for.**

**On the branch:** the four files are restored to the fuzzer's bytes (102 of 102 identical now), and
`tests/negative/r17/SHA256SUMS` pins all 213 committed inputs. `tools/crash_corpus.py` checks the manifest
first — a file whose bytes differ, a file missing, or an `.sm` not in the manifest is a FAIL before any
case runs. Tested: main's re-encoded `mutation-15-37233` against the manifest →
`FAIL  manifest: r15-original/mutation-15-37233.sm does not have the pinned bytes (re-encoded or edited)`.

**For the merge:** these four files, and the manifest, must land byte-for-byte. If the merge tool reads
files as text, merge the branch with git (`git merge`/`cherry-pick`) for `tests/negative/r17/`, or copy
them in binary mode. The manifest will say whether it worked.
