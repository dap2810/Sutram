# R10-01 — WS1: F1 fixed

**Branch `claude/round-10`, commit `870aa8aa`, draft PR #45.** Base: main `2e875ea7` (v195). The compiler
source was read from main first; it was the R9 blob, `5caa9b6e`.

## The root cause, in two sentences

**Every load and store of a stack variable emitted its `rbp` offset as a one-byte displacement, so any slot
below `rbp-128` wrapped to a positive offset: `rbp-136` became `rbp+120`.** Those slots landed above the
function's own frame, on the caller's saved registers, its pushed temporaries and the return address, and,
from the 33rd slot on, back onto the function's own first slots.

## One bug, not two, and not a stack-size issue

**I measured the same program with both compilers:**

- the Linux compiler, and the Windows compiler under Wine
- n locals in a called function, plus one parameter and a sum `s`
- the caller keeps three variables live and computes `1000 + f(1)`

| n (locals) | variables in the function | v191, Linux | v191, Windows compiler under Wine | this branch, both |
|---|---|---|---|---|
| 14–26 | 16–28 | correct | correct | correct |
| **27–31** | 29–33 | **wrong values:** the caller's `b`, `c` and the `1000` change | **identical wrong values** | correct |
| **32 and up** (32, 33, 34, 36, 38, 40, 44, 48, 64, 100, 150, 200, 220) | 34+ | **segfault, no output** | **no output** (exit 5, then 1) | correct |

**What the numbers mean:**

- The boundary is the same on both platforms, to the variable, so **it is codegen, not the stack, the red
  zone or a guard page.**
- **Why your Linux run crashed at 38 and the owner's Windows run at 34:** you tested 30 and then 38 on
  Linux, and 34 crashes on Linux too.
- **Why the owner's 30 printed correctly:** a wrong value needs something live in the caller at the
  overwritten addresses. A crash needs only enough variables to reach the return address, which is the 34th
  variable.

**The full layout:**

- In a called function, slots run `rbp-24, rbp-32, …`.
- **The 20th variable** (`rbp-136`) is the first that wraps, to `rbp+120`.
- Each later variable moves 8 bytes closer to the frame:
  - The caller's saved registers and pushed temporaries sit just above the return address. In this test,
    variables 29–33 reach them.
  - **The 34th variable lands on the return address** (`rbp+8`).
- In `mukhya` the wrapped slots are above a frame nobody returns through, so only the **38th** variable
  shows: it shares a cell with an earlier one.

**Raw output:** `evidence-r10/logs/sweep-*.txt` and `sweep-wine.txt`. **Windows itself: NOT-RUN.** The
Windows numbers above are the Windows compiler's code run under Wine.

## The fix

**One helper, `emit_rbp_modrm_disp`:**

- It emits the ModRM byte and a one-byte displacement for −128..127.
- Otherwise it emits a 4-byte displacement (ModRM + 0x40, the standard `[rbp+disp32]` form).

**Where it is used:**

- All 15 stack-slot sites call it (with the in-place emitter below, 16 in all): declaration, assignment, variable read, array and record base, the
  `chakra` loop variable, and named load and store.
- So does the in-place `+=`/`-=` emitter. Its `chakra`-increment caller had no range check; its other
  caller had one, which can now stay or go.

**No restructuring:**

- Instructions grow from 4 to 7 bytes only where the slot is deep.
- **A program whose slots all fit in a byte compiles to the same bytes as before.**
