## F2 first, as asked

**The defect:**

- On Linux, `nirmmita(n)` compiles to a raw `mmap`. A failed `mmap` returns `-errno`, and
  `nirmmita(0)` is `-EINVAL` (−22).
- The language reference and every library constructor promise 0.
  - `suchi_srij`, `avali_srij` and `nighantu_srij` check `== 0`.
  - The rest of the library does not check at all.
- So a failed allocation went on as a pointer to −12. **This is the same silent-wrong-answer family as
  Step 1.**

**The fix (`emit_nirmmita_from_rax`):** right after the `syscall`, it emits

```
cmp rax, -4095   ; 48 3D 01 F0 FF FF
jb  ok           ; 72 02
xor eax, eax     ; 31 C0
```

**Cost:** 10 bytes per allocation site and no other change.

**On Windows:**

- The Windows shim already returned 0.
- `win/sutram.exe` from this branch, **under Wine**, runs `r9_alloc_failure.sm` and gets `0 0 0 0 0 0 1 1 9`,
  as Linux does (`logs/f2-f3-wine.txt`).

**The proof:**

- `tests/stdlib/r9_alloc_failure.sm`: `nirmmita(0)`, a 2^60-byte request, `mala_nava(0)`, and the three
  constructors at an impossible size are all 0. A normal list still works.
- **It fails on v188 and passes here.**

## F3

**The defect:** `guna` is desugared into an if/else chain that reuses the one expression node, so each
`bhavana` re-evaluates it.

**The fix:**

- When the value is not a plain variable or number, the parser evaluates it once into a hidden local
  (`#g1`, `#g2`, …; `#` cannot start a name, so it cannot clash with a user name).
- The cases then compare against that local.
- Plain `guna (x)` and `guna (5)` compile exactly as before.

**Measured first:**

- The tree has 8 `guna` statements.
- **0 have a call in the value**, so no program's behaviour changes.

**The proof:** `examples/236_guna_once.sm`. It covers:

- `calls = 1`, where v188 gives 3
- a `guna` nested inside a case
- a `guna` in a loop
- a `guna` in a function that returns from inside a case
- a value that matches nothing

**Windows (Wine):** this branch's `win/sutram.exe` prints the same golden under Wine.

   - So `r69_build --check-only` on main refused.

   - `win/sutram.exe` and the Linux `sutram_compiler` were still R7's builds, and print `v160`.
   - Only the root `sutram.exe` had been rebuilt.

   - The branch rebuilds `sutram_compiler`, `win/sutram.exe`, `sutram.exe` and `sutram-ide-gui.exe` from
     this source.
   - **`Sutram-Setup.exe` is not rebuilt:** it is ChatGPT's, and its R77 asks it to do exactly that. The
     setup must be rebuilt **after** this merges, or it will still carry the old compiler and IDE.
   - `tools/cross_build_windows.py --check` on the branch: MATCH for the compiler and IDE, DIFFERS for the
     setup only.
