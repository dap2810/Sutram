## What was built

**New module `lib/map.smlib`** — hash map over parallel `pankti` arrays,
open addressing with linear probing.

**Key representation: byte strings** (the R10 `strb_*` surface), not
char-code arrays. Rationale: keys are usually literals, and byte strings
let the caller pass a literal directly (`map_put(m, 8, "apple", 5, 42)`);
the hash (`fnv1a` from `lib/hash.smlib`, pulled in via `ayojan hash` —
nested `ayojan` verified working) is byte-based (`char_at`), so the choice
is consistent end to end. Documented in the header with a worked example,
kept consistent with the `string.smlib`/`strb.smlib` headers.

Functions (7 public + 4 internal helpers):

- `map_init(cap)` — allocates and zeroes a map (cap clamped to ≥ 1)
- `map_put(m, cap, key, keyn, val)` — insert or update; 1 on success,
  **0 if the table is full (map unchanged)**; update keeps size unchanged
- `map_get(m, cap, key, keyn)` — value, or documented absent sentinel
  **-1** (`0-1`; use `map_contains` to disambiguate a stored -1)
- `map_contains(m, cap, key, keyn)` — 0/1
- `map_remove(m, cap, key, keyn)` — 1 if removed, 0 if absent; deletion is
  **backward-shift (Knuth 6.4R)**: the freed slot is filled by shifting
  later probe-chain entries back toward their home bucket, so there are
  **no tombstones** and lookups stop at the first empty slot
- `map_size(m)` — live entry count (kept in the buffer header)
- `map_keys(m, out)` — live keys in length-prefixed form
  `[len0, b0, b1, ..., len1, b0, ...]` (same shape as `str_split` parts);
  returns the count (== `map_size`)

Buffer layout (documented in the header): `m[0]` = cap, `m[1]` = live
count, then per-slot state / keylen / val cell arrays, then a byte region
of 32 bytes per slot for key bytes (`KEY_MAX = 32`; longer keys are
**truncated to 32 bytes consistently** on put/get/contains/remove —
documented, excluded from the properties).

Golden tests (2 new): `map_basic` (put/get round-trip with literal keys,
absent → -1, contains 0/1, update keeps size, new value visible),
`map_remove` (three keys `eaeb`/`ad`/`abaed` sharing bucket 0 at cap 8 —
one probe chain, verified via Python FNV-1a; removing the middle and then
the head leaves the rest reachable; absent remove → 0; `map_keys` count).
All goldens recorded from actual runs; no existing golden modified.

## Properties — 30/30 hold (21 prior + 4 R10 + 5 new)

- `map put/get roundtrip`: 8 distinct keys, `map_get` returns what
  `map_put` stored, `map_size` == 8
- `map update`: same key twice → size unchanged, second value wins
- `map delete`: after `map_remove`, `map_contains` == 0, size decreases by
  one, all other keys still return their values
- `map collision survival`: three keys with the same `fnv1a % 8` bucket
  (found deterministically in Python) are all retrievable from a cap-8 map
- `map keys count`: `map_keys` count == `map_size`, and walking the
  length-prefixed output yields exactly the total key bytes written

**Deliberately excluded:** keys longer than 32 bytes (truncation rule);
storing -1 as a value without a `map_contains` check (sentinel ambiguity);
`cap < 1` (clamped, not a distinct behavior).
