# R105 WS2 — Attack on ChatGPT's R178 arena DESIGN itself (not the branch)

Base: current main (`9ace6e95`, v292 + ROUND-183 doc; the arena design itself is unchanged since v290). R178's base was v290; the branch inspected is `0e71e54` (R108 review branch, v289-based). This attacks the DESIGN's own claims. R105 already attacked the branch; §6 of R178 lists branch findings, which I verify below rather than repeat — with two corrections.

## Verdict

The core is sound: stable descriptors plus independent owner arenas solve the branch's refusal-not-coherence price (aliases share one descriptor, so growth preserves names instead of being refused), and the student model is honest ("The budget includes old slots left by growth" embraces the waste instead of hiding it). The cost arithmetic in §5 is correct (capacities 4→1024 sum to 2044 × 8 = 16,352 payload bytes, dead 8,160, + 48 descriptor = 16,400, under the stated 16-aligned, control/page-excluded assumptions). But the design has eight gaps, three of them high/medium, and it must not be built until the first five are closed — because each is a choice the implementation will otherwise make silently.

## Gap 1 (HIGH) — The descriptor ABI migration has no enforcement mechanism for its own headline rule

§1 says "No implicit descriptor-to-integer or raw payload-pointer conversion." But Sutram has no pointer type: pointers are `vitti` (addresses as integers). A kosh variable under the new ABI holds a descriptor pointer; passing it where a raw pointer is expected (as a `vitti`) is indistinguishable from passing any integer — unless the compiler tracks kosh-ness at every such position and refuses. The design states the rule, not the mechanism: it never says the compiler will refuse a kosh variable in a pointer position, how it distinguishes one, or what happens to `smaran`/`khand` on kosh data.

Surveyed on v292 (precise, by name): ZERO examples and ZERO lib functions pass a kosh variable directly to `khand`/`smaran` as a raw pointer, and ZERO examples print a kosh directly with `likha`. So the migration breaks no existing program — but that is luck, not safety. Without a stated refusal, a future `smaran_cp(dst, kosh_var, n)` would silently copy the descriptor's 48 bytes instead of the data, and no test would catch it (the program still runs). The design must commit, before building: the compiler refuses a kosh-typed value in any raw-pointer position, and the refusal names the conversion. Until then, "no implicit conversion" is a wish, not a guarantee.

## Gap 2 (HIGH) — No performance evidence for THIS design, and the per-block reservation cost is unmeasured

R178 correctly disowns the branch's surrogate ("The branch's reported 0.02-second/0-KB surrogate is not a measurement of this descriptor/owner design") — but offers no replacement number. §5's estimates exclude syscalls for the bump path and list block first-allocation/exit only as "Reservation/release system calls plus control-record setup/cleanup; not a pure bump fast path" — with no count. The shape that matters is Claude's kb1: 100,000 blocks each holding a 100-number kosh. Under this design each block invocation gets its own reservation (a mapping) plus a control record plus a 48-byte descriptor. That is 100,000 reservations (mmap/munmap pairs if released to the OS) versus the branch's bump (zero syscalls after the first). The design calls this "an explicit correctness-first tradeoff" but never prices it: is the kb1 shape 0.05 s, 0.5 s, or 2 s under this design? v289 did it in 0.46–0.59 s at 400 MB; if this design does it in 0.5 s at 0 KB, it wins on memory only, not time — and the owner cannot judge that tradeoff without a number. The design must estimate (or, better, prototype-measure) the per-block reservation cost for the loop case before claiming to solve kb1.

## Gap 3 (MEDIUM, future-only) — Parameter growth is refused with no replacement and no ABI-update scope

§4: "Growth through aliases is semantically valid under the descriptor design, but enabling growth through parameters requires an explicit owner-aware ABI update; until implemented, retain that refusal." Combined with the existing refusal on returning a whole kosh, that leaves NO way for a function to grow a caller's kosh until an unspecified future update — no date, no scope, no interim path (return-and-reassign is refused; grow-in-place is refused).

Measured accurately, this breaks nothing existing: the refined survey (push of the kosh parameter BY NAME, examples + lib) finds exactly one case, `121_t18_kosh_param_push_reject.sm` (`yuj_ek` pushing its param `a`) — and it already expects refusal on v292 ("kosh-tarke kosh_push asamarthitam", golden matches). So the refusal matches main today. The gap is for future code, and it must be stated as such: the design removes a capability future programs will want, with no replacement and no timeline for the ABI update that restores it.

## Gap 4 (MEDIUM) — The lifetime gate is a requirement list, not an algorithm, and its safe subset is unmeasured

§4 requires "owner provenance through aliases, branch/loop joins, stored fields/elements and returns" — but gives no join semantics. After `k = yadi (c) { k1 } anyatha { k2 }` with k1/k2 from different owners, is k usable while EITHER owner lives (union, unsafe) or only while BOTH live (intersection, the safe rule)? The design does not say. For loop-carried variables — reassigned each iteration to a new block's kosh, then used after the loop (when the last iteration's owner is dead) — the design does not say whether the gate refuses, and a gate that does not handle loop-carried owners is unsound (a use-after-free through the loop variable). There is no lattice, no widening for loops, no soundness argument — the same gap R178 criticizes in the branch (a list of cases, not a proof), now in the design itself.

And "unproven programs refuse" assumes the proven-safe subset is large enough to be usable. It is unmeasured: how many of the 299 examples and 306 lib functions would the gate refuse? The branch already refused safe read-only aliases (R105's price #1); a stricter gate (unknown callees refuse, resource limits refuse) will refuse more. Before merging, the gate — once implemented — must be run over the whole tree and its refusal count published. A gate that refuses 50 examples is a migration, not a drop-in, and the owner should know which before approving the build.

## Gap 5 (MEDIUM) — parimana's charge categories are ambiguous

§3 charges "descriptor bytes, payload capacity and alignment padding, including every abandoned growth slot" — but never says whether the owner control record (per block invocation, size unstated) is charged. If it is not, parimana under-reports by depth × control size (small for shallow nesting, larger for deep recursion — and unstated either way). And "add occupied owner slots once; do not also count them as region allocations" states the no-double-count rule without the mapping: which allocator bytes map to which parimana category? Two implementations could count differently, and parimana's value — which R105 found meaningful on the branch (exact slot sums) — would differ between them. The design needs the category table (descriptor? payload? control? region? each: counted or excluded) before implementation, or parimana's meaning under this design is not yet well-defined.

## Gap 6 (MEDIUM) — The arena cache is unbounded by design (deferred), so loop-case memory is unknown

§3 allows reclamation to "an explicitly bounded arena cache"; §5 says such a pool "needs its own limit and metrics" — a TODO, not a design. If the cache is unbounded, 100,000 loop iterations retain 100,000 arenas — the kb1 400 MB problem returns through the cache. If bounded, the bound and the eviction policy (LRU? oldest? what happens on eviction — a munmap syscall, so the cache batches syscalls rather than saving them) are undesigned. So the loop case's memory under this design ranges from one arena (cache of 1) to 400 MB (unbounded) — a 100,000× range the design does not narrow. It must pick: default to release-to-OS (paying Gap 2's syscalls) or bound the cache (with a number and a policy) — before building, not after.

## Gap 7 (LOW-MEDIUM) — The R105 diagnostic gap is not closed

R105 found `kshetra purnam` (unbudgeted exhaustion) names no line and no count, while `E_PARIMITA` (budgeted) names the line. §3 says to "distinguish budget, arithmetic overflow and allocation failure diagnostics" but proposes "no new public names for these diagnostics here" and never commits to naming the line or the charge. The descriptor HAS a source-location/diagnostic-identifier field (offset 32) — so the line COULD be named — but the design never says the allocation-failure diagnostic uses it. A future implementation could still emit a lineless `kshetra purnam` and satisfy this design. The design must require: every refusal names the owner, the line, and the charge — or the gap survives.

## Gap 8 (LOW) — Views/borrows are blocked with no path and no timeline

§1: exposing an element pointer/view "requires a borrow that prevents structural growth until that view ends. First implementation may reject such views altogether." WS3 adds that a future borrow syntax needs "a separately justified full Sanskrit term before exposing that syntax." So programs needing views (slicing kosh data is the legitimate example) have no path until someone justifies a word — an open-ended deferral. Surveyed: zero existing programs need it (Gap 1's survey covers the khand/smaran shapes), so this is future-only, like Gap 3 — but it should be listed as a capability gap with no timeline, not left as "may reject."

## Branch findings (§6) — verified in source, with two corrections

**(a) 256-entry silent fallback — CONFIRMED, and worse than stated.** `r108_kosh_alloc`: `cmp rcx, 256; jae r101a_emit_kosh_alloc`. At the 257th block kosh it silently falls back to R101A's region allocation — which lives for the program's life, NOT the block's. So the fallback does not merely change budget/reclamation; it changes LIFETIME (the kosh silently becomes persistent, leaking past its block, with no diagnostic). R178's fix (reject compilation on metadata exhaustion) is correct and necessary.

**(b) 32-round convergence — CONFIRMED.** `r108_compute_esc`: `mov r14d, 32` then a round loop ending in `ret`, with no changed-summary check after the loop. It exits even if the final round changed summaries, so a sufficiently long adverse-order call chain is analyzed with stale summaries (potentially concluding no-retain for a retaining function). R178's fix (worklist, or refuse conservatively on exhaustion) is correct. Whether 32 suffices for the tree's longest chain is unmeasured — that measurement should be done before dismissing this as theoretical.

**(c) 65,536-entry silent drop — CONFIRMED in source, but LOW severity (downgraded).** The `.push` for the analysis walk's node stack: `cmp r15, 65536; jae .pr` (silent return, no diagnostic, no retaining mark). R178 is right that this is unsound in principle. But the stack is a DFS frontier, depth-bounded, not node-count-bounded — reaching 65,536 requires a 65,536-deep AST, far beyond the tree's programs (statement cap 256 per function bounds depth). So this is latent, not practical. The fix (diagnostic instead of silent drop) is still correct — cheap insurance, not an urgent hole.

**(d) Bare-AST_VAR alias scope — CONFIRMED as the mechanism, but the finding understates the branch (downgraded).** `r108_check_alias` does compare against `AST_VAR` — but it is not the branch's only path. The branch also has `r108_check_call` (call arguments), return checks, and store checks, and R105 verified all eight shapes refused through them. My new probes discharge one of R178's own test obligations: a second name assigned inside a branch (`kk = k` inside `yadi`, probe `cond2.sm`) is REFUSED with `E_KOSH_MANDAPA`, as is a direct assignment (`cond_alias2.sm`). And "conditional expressions" as a bypass shape are vacuous in this language — there is no ternary expression form, only conditional statements containing assignments, which the assignment check covers. So the remaining gap is the lack of a PROOF, not a demonstrated bypass: as a practical hole, this finding is empty for the language's actual forms.

**(e) NEW branch result, not in §6 — outer growth during an inner block WORKS on the branch.** Probe `outer_grow2.sm`: an outer kosh grown twice inside an inner block (while the inner kosh is live) reads back correctly after the inner block exits (len 3, peek 3). R178 §2's LIFO-discard hypothetical ("allocating an outer owner's replacement beneath an inner checkpoint would otherwise discard it") does NOT occur on the branch — its per-block arenas already handle this shape. §2's independent-arenas requirement is sound as a design principle for a naive cursor, but it is not a branch bug and should not be cited as one.

## What must happen before Claude builds

1. The ABI enforcement mechanism for "no implicit conversion" (Gap 1): commit to refusing kosh-typed values in raw-pointer positions, and state how (given pointers are `vitti`).
2. A per-block reservation cost estimate for the kb1 loop shape (Gap 2), and the cache decision: release-to-OS by default, or a bounded cache with a number and an eviction policy (Gap 6).
3. The gate's algorithm (lattice, join rule, loop-carried handling, widening) plus a safe-subset measurement over the whole tree once implemented (Gap 4).
4. parimana's category table (Gap 5) and the diagnostic commitment (every refusal names owner, line, charge) (Gap 7).
5. The branch fixes from §6 (reject on 256-exhaustion; worklist or refuse on 32-exhaustion; diagnostic on 65,536-drop) — with (c) low-priority and (d)/(e) corrected as above.
6. A scope or date for the parameter-growth ABI update and the borrow syntax (Gaps 3, 8), or an explicit statement that both stay refused indefinitely.
