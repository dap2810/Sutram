### What the R158 doc-currency gate would need to check for this class

Read first: the gate file (544 lines). It has **9 checks**, not 6 — its own module docstring says "Six checks" (C1). Check 8 `sizes` measures both descriptor sizes by running two tiny programs through `parimana()` and fails any current document stating a different size — it catches a *stated* 24-byte size, but not a three-field list with no size (P2). Check 9 `figures` rejects the replaced figures. Check 7 `reference` guards the nineteen claims via the forbidden-text table (21 patterns, C2) plus measured claims — but not claim 14 (C3). The companion doc-counts gate measures 8 labelled counts from a gate transcript and checks 7 of them — it never checks "packs" (C-A6), and its patterns miss the status-line form "80 PASS / 0 FAIL" (P4) and any example count in the README (P6).

A check for un-totalled lists — call it check 10, `lists` — would need three layers, because the class has three shapes. Described, **not written** (per the brief):

**Layer A — stated totals against the tree (mechanical, buildable now).** Extend the doc-counts gate's labelled checks with the patterns it is missing, and extend the measured set: (a) a "packs" row for language packs against the 11 pack files — this closes C-A6 and would catch B5's "fifteen" and B-A4's "ten packs" where they appear in current docs; (b) an example-count row for "N example programs" against the 331 top-level example files — this closes P6 (README "222"); (c) a gate-total row matching the status-line form "N PASS / M FAIL / K NOT-RUN" against the computed 79/0/1 (77 run_gate + X11 + doc-counts, 1 Windows skip) — this closes P4, which the current "N PASS, M FAIL" pattern misses; (d) a modules row that also matches the books' phrasing ("Twelve modules ship", "Fifteen modules ship") — this closes B1/B2 in the books. Each row is the same shape as the existing labelled checks: a regex whose group is the quoted number, compared with a measured value. What it cannot catch: any count whose ground truth is not a tree count (resident-memory peaks, speed ratios, run counts).

**Layer B — field lists against a stated size (mechanical, needs a field-size table).** Match, in current docs and books, a sentence that enumerates a struct's fields without a size in the same sentence or paragraph — the pattern is a comma/and list of field names followed by no "N bytes" within the paragraph — and compare the counted fields against the known field count for that struct. The gate already has the ground truth for the one struct that matters: check 8 measures the kosh descriptor (32 / 56). A `lists` check could reuse it: for any paragraph naming kosh descriptor fields, count the named fields and require the count to be 4 (or 7 with the liveness flag) and, if a size is stated elsewhere in the paragraph, require it to agree. This closes P2 and the C4/C-A3 comment class in docs. What it cannot catch: a field list for a struct the gate has no ground truth for (the slice descriptor is the other one — its size is stated in code, but the gate does not measure it); a list where the fields are named across several sentences rather than one paragraph; any list whose fields are not all the same size (the ×8 arithmetic only holds for qword fields).

**Layer C — "every" and row-count agreement (semi-mechanical, needs a whitelist).** Match the exhaustiveness words — "every", "in full", "the full", "all" — attached to a table or list in a current doc, and require the adjacent table's row count to equal a total stated in the same section, or to equal a measured ground truth where one exists (the library table: 24 modules; the keyword table: no ground truth exists — see "Could not determine"). Concretely: (a) for the Ch14 per-module table (B3), require each row's stated count to equal the number of names listed in that row AND the function count in the corresponding library file — both are mechanical; (b) for a table headed "Every X", require a stated total in the section and require the row count to equal it — this closes B7/B8 only if someone first supplies the true keyword total, which does not exist as a single table in the source (51 rows / 32 ids / 33 definitions / 36 max); until that ground truth is established, the check can only flag the *absence* of a stated total next to an "every" claim, not its truth; (c) cross-document consistency: the same noun's total ("modules", "packs", "functions") stated in more than one current document must agree — this closes B1 (12 vs 15 vs 24) and B5 (13 vs 15 vs 11) without needing to know which is right. ### Least confident: the E_KOSH_MANDAPA imprecision (line 8)

**The claim:** the document's blanket "A kosh made in a block cannot leave it" overstates the rule, because a read-only pass to a non-keeping procedure IS allowed — the check refuses only keeping procedures — and the document never says so.

**Why this one, and not the others.** The other nine rest on a direct quotation plus a direct check: a sentence read from the document against a field list read from the code (descriptor), a version read from history (walk), a golden test (parimana: a kosh of 1000 counts 8,288 = 64 + 32 + 1024×8), a measured fact the other agent has since reproduced on v315 (parimita counts rounded-up bytes; a 1000 budget refuses a 1000-byte allocation), a code path read line by line (handler "up to"), or a description that no longer matches the code it describes (§2). This one rests on a code-reading of a rule enforced by several cooperating checks, and there is **no positive test demonstrating the exception**:

- The rule is stated plainly in the check's own comment (above `r108_check_call`): "an argument that is a kosh of an open block of this function may go only to a parameter that does not keep it; to an unknown callee (a function value, a foreign function) not at all." The code implements it: for each argument that is a block kosh, it computes the escape table; an unknown callee refuses, a parameter whose escape byte is set refuses, otherwise it passes. Three readings agree (R155, R158 Task 1, this re-read at this base).
- But **every golden test for the refusal is a refusal** (four goldens: the after-block use, the kept-by-a-procedure case, the alias-kept case, the long-chain case) — and the example programs behind them. No example or golden in the tree demonstrates a block kosh passed read-only and accepted. The exception is established by reading, not by a passing program.
- The exact boundary of "read-only" depends on the escape fixpoint's definition of a read (a parameter starts as "does not keep" and is marked when some use of it is not a read — an index read is a read; a kosh builtin's own operand marks it; passing it on as an argument to a parameter that does not keep does not mark it). Whether a given real procedure counts as "read-only" under that definition — indexing yes, a length query yes, a growth call no, a store no — is a judgement about the fixpoint, not a sentence in the document. And the walk has its own say about what may sit beside a call.
- The failure mode runs in the other direction too: the fix (rewording the sentence to state the exception) could itself overstate. "A read-only pass is allowed" needs the qualifiers the comment carries: to a *known* procedure, whose parameter *does not keep it* — a pass through a function value or to a foreign function is refused outright, whatever it does with the argument.

**What a second reader should check before the sentence is changed:** (1) a positive program at v315 — a block kosh passed to a procedure that only reads it (indexing and a length query), compiled and run, so the exception has a golden, not just a reading; (2) the walk's treatment of the argument (does any walk door refuse a block kosh as a call argument in a shape the check allows?); (3) the fixpoint's definition of a read, against the procedures a beginner would actually write (a procedure that stores the kosh in a local variable and reads through it — is that a read, or a keep?).
