### Task 1b — Gap 2: `r58_fold_tree`, read whole. Verdict: no live defect — but the brief's description is wrong, and the guard has a real hole that only the walk covers.

**The branches, all of them (`src/sutram_compiler.asm:31541–31648`).** `r58_fold_tree` (`:31541`; header comment `:31530–31540`) is called once, at the head of `r142_gen_expr_body` (`:21436–21440`), i.e. *after* the walk — the walk ran in `gen_stmt` (`:18857`) or in `gen_expr`'s own fallback (`:21421`) before the body is entered. (In `SUTRAM_R65_TRAP_INT` builds the call is compiled out entirely, `:21435–21440` — no folding at all there.)

1. **Non-binop / null / depth cap** (`:31546–31555`): a null node, a node that is not `AST_BINOP`, or recursion depth `r12 >= 64` returns the node unchanged. No rewrite, no descent into calls, floats, strings, or arbitrary forms — the header comment's claim on this point is accurate.
2. **Bottom-up recursion** (`:31556–31564`): both operands are folded first and stored back (`[rbx+16]`, `[rbx+24]`). Folding is bottom-up, so an inner identity is resolved before the outer one is considered.
3. **Literal–literal fold** (`:31565–31607`): only when *both* folded operands are `AST_NUM`, and only for `OP_ADD/SUB/MUL/AND/OR/XOR/SHL/SHR`, the `BINOP` node is rewritten in place to `AST_NUM` with the computed value (`.r58_ft_set`, `:31602–31607`). `DIV`, `MOD`, comparisons and everything else return the node unchanged. **A slice is `AST_SLICE`, never `AST_NUM`, so this branch cannot touch a slice, create one, or erase one.** The old operand nodes are orphaned in the AST heap, never read again. Clean.
4. **Identity reduction** (`.r58_ft_identity`, `:31608–31648`): only when the right operand is an `AST_NUM` literal — `0` with `OP_ADD`/`OP_SUB`, or `1` with `OP_MUL` — and only after `.r58_ft_check_type` (`:31627–31645`). If it passes, the function returns the *left operand node itself* (`mov rax,[rbx+16]`, `:31646`), dropping the `BINOP` wrapper. This branch is the part the ROUND-151 summary omits when it says the fold "rewrites only `BINOP` of two `NUM`s".

**The identity guard, and the hole in it.** `.r58_ft_check_type` calls four predicates on the *left operand*:

| Predicate | Line | What it actually checks |
|---|---|---|
| `rfx_is_kosh_operand` | `:9404` | Returns 1 only for an `AST_VAR` whose name `is_kosh_var` or `is_kosh_param_var` (`:9404–9418`). An `AST_SLICE` fails the `AST_VAR` test at once (`cmp qword [rdi], AST_VAR; jne .no`) → **returns 0 for a kosh slice**. |
| `rfx_is_mala_operand` | `:9392` | Same shape: `AST_VAR` only, then `is_array_var` (`:9392–9402`). **Returns 0 for a mala slice.** |
| `r113_is_rname` | `:9358` | `AST_VAR` only, and only a name in the `r113_rn` (rachana) table (`:9358–9390`). Returns 0 for any slice. |
| `binop_needs_float` | `:27373` | Returns 1 only if an operand `expr_is_float` (`:27373–27412`). `expr_is_float` (`:26813`) has no `AST_SLICE` case → **returns 0 for a slice**, including a slice of a `kosh dasham`. |

So the code comment at `:31622–31624` — *"R126: `k + 0` is no identity for a kosh, mala or rachana: it stays a binop, and the binop check refuses it"* — is true only for a **bare kosh/mala name** (`k + 0`, `m + 0`). For a slice operand, all four guards return 0, and **as written, `k[0:1] + 0` would fold to the bare slice `k[0:1]`, and `k[0:1] * 1` likewise**. The ROUND-151 brief's sentence "It rewrites only `BINOP` of two `NUM`s" is therefore wrong as a description of the code, and its follow-on — the fold "does not [undo the check] because it runs after the walk" — names the wrong mechanism (see next paragraph). The brief's v314 measurement claim (`keep(k[0:1] + 0)` and `k[0:1] * 1` "are refused on v314, measured") is outside this base; I did not verify it, and on v313 the refusal comes from the walk, not from the fold.

**Why the hole is not a live defect on v313.** The fold is unreachable for slice binops, because the walk refuses them first. The walk's `.binop` handler (`:28502–28514`) does `xor r10d, r10d` — it resets the door flag to 0 — and then calls `.num` on both operands; `.num` (`:28590–28645`) refuses any slice with `r10 = 0` (`.bad`, `E_VIBHAG_ANKA`, `:28634–28645`). That refusal applies at *every* position: a binop nested inside another binop (the walk's `.gen`, `:28577–28587`, pushes fields 8–64, so the inner binop is reached and its own `.binop` resets `r10` again); a binop as a call argument (the walk's `.funcall`, `:28480–28501`, defers the argument itself at `r10 = 1`, but `.gen` still delivers the binop node to `.binop`); a binop as a `vibhag`-call argument (`.funcall` skips `.num` for `PARAM_VIBHAG`, but `.gen` still delivers the binop); a binop in a ternary branch (`.num` recurses into ternary arms, `:28596–28606`, with `r10` unchanged, so a `r10 = 0` from an enclosing `.binop` is preserved). The fold therefore only ever fires on binops whose operands already passed `.num` with `r10 = 0` — i.e. operands that are not slices and do not hold a kosh (`.numkosh`, `:28620–28632`). **The protection is the walk's refusal, not the fold's ordering.** If the walk ever stopped refusing slice binops, the identity branch would launder them: the door checks that run at generation (`r126_check_untyped_arg`, `:29204`, etc.) see the *pre-fold* node only through the already-walked tree, and generation would emit the bare folded slice. The guard should be fixed to recognise slices (e.g. via `r23_expr_is_slice` / `r134_holds_kosh` on the left operand) — that is a one-line hardening, not a live escape on v313. Whether the v314 tree changed the guard, I did not check: v314 is not my base.

Two smaller notes, read while tracing this. First, the parser-time `fold_const` (`:16750`, called at `:16467`, `:16517`, `:16567`) folds only when *both* operands are `AST_NUM` (plus string concatenation for `AST_STR`, `:16784–16810`); it has **no** identity reduction, so it cannot touch a slice binop at all — parse-time folding is clean. Second, the fold mutates only the tree of the statement currently being generated, after that statement's walk; it cannot affect the walk of a later statement, and it emits no code and calls no `gen_expr` itself.

### Gap 4 (short check) — the R143 walk-budget arithmetic. Verified exact, under floor division.

## Task 2 — the FFI shape, one step further (v313, before the v314 fix)

**Verdict: the foreign function receives the address of the two-word header (the descriptor), never the address of the elements.**

### The chain, with anchors

1. **The call reaches the foreign path.** In `gen_expr`'s `.ge_funcall` (`src/sutram_compiler.asm:21502–21517`), after `r129_check_call` and `r108_check_call`, a declared foreign name (found by `r32_ffi_find`, `:21511–21513`) goes to `r33_gen_foreign_funcall` (`:21517`; the statement form reaches it at `:18989`). `r129_check_call` (`:28771`) takes its `.unknown` path for a foreign name (`rfx3_fn_index` −1, `:28829`), which refuses a kosh slice **only beside another argument containing a call** (`r129_is_kosh_slice`, `:28883`) — a lone slice, or a slice plus plain numbers, passes. The walk's `.funcall` (`:28480–28501`) calls `.num` on each argument with `r10 = 1` (`func_param_type` is 0 for a foreign name), and `.num` defers a kosh slice to the door (`r134_holds_kosh` = 1 → return, no refusal) — and the foreign path never calls that door.
2. **The argument checks do not catch a slice.** In `r33_gen_foreign_funcall` (`src/r32_ffi.inc:666`), per argument (`r12 = [rbx+24+r13*8]`, `:685`): kinds are 0 = i64, 1 = f64, 2 = ptr (return kind 3 = void, checked at `:676`). For i64/f64 (`:690–701`): `AST_STR` → `.bad`; `AST_VAR` that `is_kosh_var` → `.bad`. For ptr (`:723–740`): a float → `.bad`; an `AST_VAR` that `is_kosh_var` gets an extra `mov rax,[rax]` deref (`:735–740`, "R127: a kosh passes its elements, not its descriptor"). **An `AST_SLICE` is neither `AST_STR` nor `AST_VAR`, so it passes every check in all three kinds** — the file's only `is_kosh_var` checks are at `:694` and `:723`, both `AST_VAR`-only, exactly as R148 found.
3. **The value produced is the descriptor address.** All three kinds fall through to `.gen` (`:761–763`): `mov rax, r12; call gen_expr`. In `gen_expr`, `AST_SLICE` dispatches to `r23_gen_slice` (`src/sutram_compiler.asm:21493`, ".ge_slice"). `r23_gen_slice` (`src/r23_capabilities.inc:570–697`) says it in its own comment: *"rax = the address of a two-qword descriptor (element pointer, length) in a frame slot of this site"* (`:570–572`). For a kosh base it reads the length from `[rax-16]` and the elements from `[rax]` (`:612–621`), computes the slice pointer `lea r8,[rax+rcx*8]` (`:663`), allocates 16 bytes of the current frame (`stack_dep += 16`, `:665–671`), writes `mov [rax],r8` (word 0 = element pointer) and `mov [rax+8],rdx` (word 1 = length) (`:679–680`), and returns with `rax` = that frame slot's address. **The descriptor address, not the elements address.**
4. **The passing.** Back in `r33_gen_foreign_funcall`, `.push` (`:765–767`) emits `push rax` (0x50) for every argument. `.args_done` (`:769`) then pops them last-first into registers: System V (`:771–824`) by position among integer args (`rdi, rsi, rdx, rcx, r8, r9`) and f64s to `xmm0+`; Microsoft x64 (`:825–868`) by position (`rcx, rdx, r8, r9`, f64s to `xmm<k>`, 5th/6th to the stack above the shadow space). In every ABI and every declared kind, the register (or stack slot) holds the descriptor address.
5. **The return leg (for completeness).** `.result` (`:870–885`): return kind 1 (f64) → `movq rax, xmm0`; i64/ptr → `rax` as-is; void → statement only. A foreign function returning the descriptor address as `ptr`/`i64` hands it back into a `vitti` — `r126_value_kind` of a foreign call is raw 5 (R148), so no door recognises it on the way back either.

### What the foreign side's first dereference reads

- Treating the argument as `int64_t*` (pointer to elements) and reading `p[0]`: it reads descriptor **word 0 = the element address** — a valid pointer value read as data. That is a **wrong value** (a ~1.4×10¹⁴ integer where an element was expected), **not a wild pointer**: the read itself succeeds, because the descriptor lives in the caller's live frame for the duration of the call.
- Reading `p[1]`: descriptor **word 1 = the length** (a small integer, e.g. 1) as if it were the second element. Also a wrong value.
- Treating the argument as an integer (i64 count): it receives the descriptor **address itself** as the count (~1.4×10¹⁴). Using that as a loop bound, allocation size, or index is what crashes — the ROUND-151 brief's "as a count, crashed" is the downstream use, not the first dereference.
- A wild pointer arises only second-hand: if the foreign side takes the misread word 0 (a valid element address) and uses it as something else, or indexes far past the two-word descriptor (`p[1000000]` walks off the frame slot into stack memory), or *writes* through the descriptor address (which corrupts the frame slot — word 0/word 1 — not the kosh elements).

### What this is not

It is **not a stale-read-after-growth defect**. The descriptor is built fresh at the call site and is alive throughout the call; its word 0 is the *current* element address, and the foreign function has no way to grow the kosh during the call. The defect is a **type confusion at the boundary** — the header address passed where the elements address was expected — in the same family as the R135/R136 laundering (a value whose kind the predicates cannot see), but with a different mechanism: no growth, no staleness, no lifetime involved. **Could not determine from source:** what any particular foreign function does with the descriptor address at runtime (that needs execution, which this round forbids) — the ROUND-151 brief's "C read the descriptor (it printed an address) and, as a count, crashed" is a v314-era measurement, consistent with this reading but not verified from v313 source here.

## Task 3 — the address-vs-value rule, for the method notes

A slice value is a pointer to a two-word descriptor `[element-address, length]` in the maker's frame (`src/r23_capabilities.inc:570–572` at v313; R135 diagnostic, `Muse-to-Sarvam/ROUND-135-INDIRECT-SLICE-AND-INTERRUPTED-INSTALL.md:139–146`). `likha` prints any qword as a decimal integer, with no type information. A printed number's *kind* is therefore determined by the expression that produced it, never by the number itself.

Points 1–4 are R148's, tightened; the arithmetic caveat (5) is promoted from a parenthetical in R148's point 5 to its own point; the descriptor-vs-element distinction (6) and the dasham-float case (7) are made explicit as their own points, grounded in the delivered probe outputs cited.

1. **Pre-declare the expected set before running.** Write down every value the probe itself writes (`kosh_kship` values, literals: 0, 1, 7, 10, 20, 30, 77, 99…). Any output outside that set is suspect, not a result. In R135 and R136 every genuine element was in the set; every address was outside it.
2. **Magnitude tripwire.** Every address observed on Linux x86-64 here is a 15-digit integer, ~1.3–1.4×10¹⁴: stack/descriptor pointers `140728493615824`, `140733170577648`, `140737185282080` (`0x7ffd…`); arena / heap element addresses `139932844687392` (`0x7f44…`), `131351504224288` (`0x7776…`), `139537424244064` / `139536700079456` (`0x7EEC…`). Genuine elements in these probes are ≤ 8,388,608 (7 digits). Rule of thumb: any bare integer > 2⁴⁰ (≈1.1×10¹²) — in practice anything with 12+ digits — is an address until proven otherwise. Magnitude alone is not proof (see 5).
3. **Hex-prefix check.** Convert the number: a top byte of `0x7f…` / `0x77…` / `0x7E…` is a user-space pointer on Linux x86-64.
4. **Deref-count check (source-level, the decisive one).** Count `[0]`s between the stored slice and `likha`: `likha(slice)` = descriptor pointer; `likha(t[0])` = element *address*; `likha(addr[0])` where `addr = t[0]` = element. A probe may only report a value printed after two dereferences from an untyped slice holder (or one `[0]` through a typed `vibhag` parameter), plus a direct `likha(k[i])` control printed alongside. One dereference too few is the entire R135→R136 difference: R135's `r135_ws1_return_launder.sm:14` does `likha(t[0])` and prints `131351504224288` (ROUND-135 report `:127–128`: "not an element — it is a pointer read as data"); R136's `r136_ws1_untyped_return.sm:11–12` does `vitti addr = t[0]` then `likha(addr[0])` and prints the genuine old value `7` (ROUND-136 report `:38`, `:51–53`).
5. **Arithmetic voids the magnitude check — promote it from a caveat to a rule.** A slice put through arithmetic is the descriptor address treated as an integer: `k[0:1] + 0` takes the descriptor address and adds zero (`Sarvam-to-Muse/ROUND-142.md:16`; repeated in `ROUND-144.md:27`, `ROUND-145.md:36–37`). A scaled address can land in a plausible range by accident — multiplied, divided, or masked into 7 digits or into the expected set — so once arithmetic has touched the value, magnitude (2) and the hex prefix (3) carry **no** weight at all, and only the deref-count (4) and the control comparison (8) may carry the verdict. Note the grounding limit, stated in R148 Task 3: the arithmetic probe behind `139537424244064` has **no `.sm` source file anywhere** — it is Sarvam's prose-only v308 measurement (`ROUND-142.md:10`, `:14`), not a delivered probe — so the arithmetic case is established by prose, not by a runnable program.
6. **Say which address: descriptor or element.** The two addresses are one dereference apart and must be labelled separately, not both called "an address". The diagnostic decomposition is the reference: `r135_ws1_return_launder_diag.sm` prints `t = 140728493615824` (`0x7ffde7df2ad0`, stack — the **descriptor** itself), `t[0] = 139932844687392` (`0x7f44a7800020`, arena — the **element address**), `t[1] = 1` (the length), `k[0] = 10` (ROUND-135 report `:133–136`, `:139–146`). The same distinction decides the FFI case (Task 2): the foreign function receives the **descriptor** address; its first dereference reads the **element** address. A report that says only "it printed an address" has not said which one, and the two have different consequences (a descriptor address used as an elements pointer misreads word 0 as an element; an element address used as a value is merely a wrong number).
7. **A dasham print ending `.000000` with a 15-digit integer part is an address passed through int→float conversion — report it as such, never as an element.** R136's `r136_ws2_dasham_diag.sm:2` prints the callee's `dasham` parameter as `140724879295072.000000` (ROUND-136 report `:79–85`): the descriptor pointer's *value* is preserved (exact at this magnitude) but its *bit pattern is destroyed* (the double encoding is `0x4270…`, not the pointer `0x7ffd…`), so indexing through it faults. Such a print can neither be dereferenced nor compared as an address — the bits are gone — and it must be labelled "address-as-float", not a value and not an address usable for further reasoning.
8. **Two cross-checks, always.** (a) **Control comparison** — always print `likha(k[0])` after growth + change next to the probed read: address vs `99`, stale `7` vs `99`, correct `99` vs `99` are three different verdicts. (b) **ASLR repeat** — run the identical probe twice: an address moves between runs (`131351504224288` vs `139932844687392` for the same slot; `140733170577648` vs `140737185282080` for `r136_ws1_cell_minimal.sm`, whose single `likha(box[0])` prints the descriptor pointer, ROUND-136 report `:34` — its sibling `r136_ws1_cell_write.sm` double-dereferences and prints the genuine `7`, `:35`); a value does not.
9. **Never report a bare `likha(slice)`, `likha(t)`, `likha(box[0])`, or `likha(d)` as an element value.** Those print the descriptor pointer itself. A probe whose verdict depends on such a print proves at most escape, never a stale (or correct) element read.
