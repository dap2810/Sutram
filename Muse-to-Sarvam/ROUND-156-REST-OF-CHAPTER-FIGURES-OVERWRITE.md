## Verdicts first

**Task 1 — the rest of the chapter: fourteen more claims a beginner could act on and be wrong.** The largest is the one the brief asked about directly: the chapter's §2 title ("a block whose memory is given back") and §7 ("memory comes back when a block ends") are unqualified, and a beginner reading them will expect that of a `kosh` made inside a block — and of a `mala`, which the chapter never mentions at all. The truth is three-way and the chapter states only two of the three: `nirmmita` written inside the block is given back; a `kosh` keeps its bytes for the whole program (only its *liveness* ends); a `mala` made inside a block is **never given back at all** — and its address can leave freely with no refusal, the opposite of the kosh rule the chapter does state. The other thirteen: the third `E_SCRATCH_ESCAPE` shape (store into memory) unmentioned while the blanket "may not leave" overstates the rule; `agrim` (continue) also rewinds, unmentioned; the budget counts **aligned** bytes (`parimita 1000` + one `nirmmita(1000)` is refused); N must be positive and `parimita = N` is silently no budget at all; "baait" is never defined; `parimana()` counts a mala too and a kosh made inside a block costs more; slice bounds **are** checked at runtime with a message naming "mala", and the chapter says nothing about bounds or about `k[lo:]`, `k[:hi]`, mala slices, slices of slices, or the kosh-dasham refusal; kosh **creation** failure has its own message, never shown; `nirmmita` failure returns **0** — no sentence, no stop — which undercuts §7's "not a crash"; `kshetra purnam` is named once, never explained, and the budget check fires before it; "you can see where memory is held" over-promises (there is no introspection); a whole mala can be passed to a `vibhag` parameter and a kosh dasham cannot, neither mentioned; writes are bounds-checked too, unmentioned. **Does the chapter imply a feature that does not exist? Yes, twice:** the title/§7 imply block reclamation applies to all memory made inside a block (it does not), and "you can see where memory is held" implies introspection that does not exist. A third implication by omission: §6–§7 imply every memory failure stops with a sentence (a `nirmmita` failure does not — it returns 0 and the program crashes on first use).

**Task 2 — no living document carries either wrong figure.** The reference already says "32-byte descriptor" (`docs/LANGUAGE-REFERENCE.md:1407`, `:1431`) and the books already carry 392 / 49,920 KB. Every hit is in the round folders — design proposals, brief premises stated as built fact, one wrong claim about the shipped layout (Muse ROUND-129), and corrections. The full file:line list is below, split into living docs (none) and historical records. Two related findings that belong in the same fix: the reference's §16 lists only **three** descriptor fields (`:964-967`) and never names the region size at d+8 — read literally, 3 × 8 = 24 bytes, which is plausibly where the figure survived; and `docs/decisions/MEMORY-DESIGN.md:17` says "The 16-byte header belongs to `kosh`" — true at v261, stale at v302+. **The R158 gate has seven checks and none of them would have caught either wrong number** — the memory check requires only the keywords `['mandapa', 'nirmmita', 'KB']`, and the examples check compares exit codes only, never printed output. The check that would is described in §3 of Task 2 below (check 8, `figures`): pin the descriptor size against a named source constant (which does not exist yet — the layout lives in the emitted bytes `r127_dk`, `src/sutram_compiler.asm:574`), pin the RSS figures and re-measure them within a ±10% band.

**Task 3 — the overwrite: confirmed, seven truncating opens, no identity check anywhere.** The compiler reads its input fully into memory first (`read_file`, `src/sutram_compiler.asm:6946`), then opens the output with `O_WRONLY|O_CREAT|O_TRUNC` — so the compile succeeds and the source file on disk is destroyed. The correct check is **file identity**, not path text: `stat()` the output and compare `(st_dev, st_ino)` with the input's (on Windows, the file ID from `GetFileInformationByHandle`) — that one primitive closes the symlink, relative-vs-absolute, case-insensitive-filesystem, hard-link and respelling cases. It goes in five places: (1) compiler early refusal in `_start` after `.args_ok`, gated on `r48_mode == 0` (the `--lang --check` path sets argv[2] = argv[1], so an ungated check false-positives); (2) compiler read-set check in `.r48_normal_write` (the output can name an imported `.smlib`, not just the main source); (3) linker after the read loop; (4) both converters; (5) the REPL's fixed scratch names, separately. No `stat`/`fstat` helper exists in the tree and `GetFileInformationByHandle` is not in the Windows import list — the fix must add both.

Context from the brief, noted not verified: the scope-rewind design is rejected (nothing in this round asks for it, and the chapter does not propose it); the `likh` finding — ChatGPT withdrew it as a review error, and the brief says Muse made the same mistake — was not a task here and I did not re-check it.

## Task 1 — chapter 19, line by line: every claim a beginner could act on and be wrong

R155 established: §1 "grows each time you add" is FALSE; the OOM message is quoted exactly and the kosh is unchanged; `parimana()`'s 1008/0/0/96 derive exactly; `E_PARIMITA` "pankti 2" is the `mandapa`'s line; "a block field that is full" is a real refusal but "field" is undefined; the Sanskrit chapter is the same chapter. The fourteen items below are what R155 did **not** check. The decisive ones were re-verified at this base by reading the code (spot-checks by me); the rest carry their file:line citations at `2aa15fe4`.

### 1. The mandapa scope — the title and §7 say "the block's memory"; the body says "`nirmmita`'s". The mala is never mentioned.

Chapter (§2 title): "mandapa: a block whose memory is given back". Chapter (§7): "no free for you to call (memory comes back when a block ends, or when the program ends — you never call anything to give memory back)". Chapter (§2 body): "everything made with nirmmita inside the block is given back, all at once, when the block ends". Chapter (§3): "A kosh keeps its bytes for the whole program, even one made inside a block, so its share of parimana() never falls."

**MISLEADING (title and §7) / INCOMPLETE (the mala).** The body is precise — only memory from `nirmmita` **written** inside the block is given back — and §3 states the kosh exception. But a beginner reading the title, or §7's unqualified "memory comes back when a block ends", will expect that of **any** memory made inside the block. The chapter never states the rule for the third kind of memory, a **mala** declared inside a block — and the rule is the opposite of what the title suggests.

Code: a mala declaration (`.gs_decl_array`, `src/sutram_compiler.asm:19389+`) allocates via `emit_nirmmita_from_rax` (`:26702`), which calls `r65_emit_nirm` — the **persistent** arena bump (verified: the call is at `:19422`; `emit_nirmmita_from_rax` at `:26702` jumps to `r65_emit_nirm`). There is no scratch path in it: the mandapa scratch redirect is lexical and applies only to `nirmmita` **written** inside the block (`BN_NIRM_SCRATCH`, `:246`). So a mala made inside a `mandapa` lives in the persistent arena and is **never given back**. And nothing stops its address leaving: `r73_taint` (`:12538-12610`) treats a value as tainted only if it is a `BN_NIRM_SCRATCH` call, a variable with a recorded taint, or an arithmetic/ternary combination of tainted values — a mala name is none of those, so it carries no taint and the escape check never refuses storing or returning it (verified: no mala/array handling in `r73_taint`). Contrast a kosh: `r107_note_kosh` (`:12611`) explicitly gives a kosh made in a block the block's depth as its taint.

**What a beginner would do wrong.** Declare a `mala` inside a `mandapa` expecting its memory to be reclaimed ("a block whose memory is given back"), and be wrong: it stays allocated for the whole program. Or, having read that "a kosh made inside a block cannot leave it", expect the same of a mala — and be wrong again: a mala's address can be stored in an outer variable or returned with no refusal at all. This is the direct answer to the brief's question: **the chapter does not say which memory comes back when the block closes — the title and §7 say "memory", the body says "`nirmmita`", §3 says "not a kosh", and a mala is never mentioned.**

### 2. E_SCRATCH_ESCAPE — the chapter names two refused shapes; the code refuses three. And the blanket "may not [leave]" overstates it.

Chapter (§2): "Numbers may leave a block. An address made inside it may not: putting one in a variable outside the block, or returning it, is refused at compile time (E_SCRATCH_ESCAPE)."

**INCOMPLETE (the third shape) / MISLEADING (the blanket).** The code refuses three shapes, all through `r73_fail_var` (`:12350`), `r73_fail_mem` (`:12356`), `r73_fail_ret` (`:12362`): a variable outside the block (`.assign`, `r73_check_stmt`, `:13153-13180`) — named; a return (`.return`, `:13200-13210`) — named; **a store into memory** (`.store_mem`, `:13190-13199` → `r73_fail_mem`; and `r73_check_call`, `:8702-8736`, which refuses a scratch address as an argument to the store builtins `kosh_push`, `likh8`, `likh8c`, `setchar`, `memset`) — **not named**. In the other direction: ordinary call arguments are **not** checked (only the store builtins are), so passing a scratch address to a `prakriya` that only reads it is allowed — the call happens while the block is live. A beginner reading "An address made inside it may not [leave]" as a blanket rule would wrongly avoid passing scratch to a helper, the one use the chapter never shows — and would be surprised by a refusal when storing into a mala cell, a kosh, a global, or a rachana field.

### 3. "However it ends" — the chapter lists three endings; there are four.

Chapter (§2): "everything made with nirmmita inside the block is given back, all at once, when the block ends — however it ends (its last line, nivartanam, krama)."

**INCOMPLETE.** The fourth ending is `agrim` (continue; `kw_uddeshya db "agrim"`, `src/sutram_compiler.asm:1340`). Both `krama` and `agrim` go through `r73_wrap_jump` (`:8437-8463`; call sites `:15609` for `krama`, `:15622` for `agrim`) — "leaving blocks inside the loop rewinds them". The rewind does happen for `agrim`; the chapter just doesn't name it. Minor, but "however it ends" is presented as exhaustive and is not.

### 4. The budget counts aligned bytes, not the bytes you asked for.

Chapter (§4): "Give a block a budget in bytes, and the allocation that would pass it is refused before it happens."

**INCOMPLETE, and wrong at the boundary.** The budget check (`r103_emit_budget_checks`, `src/sutram_compiler.asm:9011-9073`) tests `(mark − new end) > N`, where `new end` is computed **after** rounding the size up to a multiple of 16: `r73_gen_scratch_nirm` (`src/r65_arena.inc:420-445`) computes `rdx = align16(size)` and the new end **before** calling the budget check (verified: `r73_s2` aligns, the budget call follows at `:441`, the store of the new end after it). So `nirmmita(1000)` costs **1008** against the budget, and `parimita 1000` plus a single `nirmmita(1000)` is refused — the allocation that "would pass" a 1000-byte budget is refused because the budget counts rounded-up bytes. The chapter says "in bytes" and never says rounded up. (The same rounding is what makes §3's 1008, which the chapter does explain there — but §4 never connects the two.) Nested budgets are also unmentioned: the check iterates the whole inherited `r103_chain` (`:8930-8994`; "Nested budgets all hold (an inner block's nirmmita counts against every budgeted block around it)", `:8909-8910`), so an allocation inside a nested budgeted block counts against **every** budgeted block around it.

### 5. N must be positive — and `parimita = N` is not a budget at all.

Chapter (§4): "N must be a number written in the program."

**INCOMPLETE.** `r103_parse_budget` (`src/sutram_compiler.asm:8933-9006`) requires N to be a whole number **greater than 0** (`test rdx,rdx; jle .bad`); zero or negative is a compile error: `'mandapa parimita' dhanatmakam purnankam apekshate (baait)` (`:8920`) — in Sanskrit, unexplained. Worse: `mandapa parimita = 1000` (with `=`) is **not a budget at all** — the word is not reserved; a `TOK_OPERATOR` after `parimita` takes the `.out` path (no budget record), and `parimita = 1000` parses as an assignment statement inside the block. A beginner writing `=` by habit gets a silently unbudgeted block, with no error and no budget. (Likewise `parimita 500+500` is not an expression — only a bare number token is accepted.)

### 6. "baait" is never defined.

Chapter (§4, the quoted message): `Sutram truti [E_PARIMITA]: pankti 2 - mandape parimitat adhikam nirmmitam na sambhavati (parimitih 1000 baait)`.

**INCOMPLETE.** "baait" is the compiler's Sanskrit word for "bytes" (`msg_bytes db " baait sankalit"`, `src/sutram_compiler.asm:837`; `r103_txt_bad`, `:8920`), and it appears in the book only in the compile-success message (`Siddh: 97 baait sankalit`, `docs/sutram-book-english.html:105`) and in this error message. It is defined **nowhere** in the chapter and nowhere in the reference (grep: only the `E_PARIMITA` example at `docs/LANGUAGE-REFERENCE.md:1465`). The chapter's prose says "a budget in bytes", so a beginner can guess — but the chapter never says `baait` means bytes.

### 7. parimana() counts a mala too — and a kosh made inside a block costs more.

Chapter (§3): "parimana() returns the bytes your program's allocations hold right now."

**INCOMPLETE.** The formula — `(cur − base) + (sima − end) + 0parimana` (`.ge_call_parimana`, `src/sutram_compiler.asm:23892-23951`) — counts **everything** in the arena, including a mala: a mala declaration allocates `(length+1)×8` bytes persistently (`.gs_decl_array`, `:19389+`). The chapter never says a mala counts. Related: a kosh made inside a block costs **more** than one made outside (56-byte header with R82 on vs 32 — R155's `examples/318` note), so the chapter's "A kosh keeps its bytes for the whole program, even one made inside a block, so its share of parimana() never falls" is true, but the share's **size** depends on where the kosh was made, which the chapter never says. (The main `parimana()` findings are R155's and stand: logical bytes rounded to 16; kosh **capacity**, not length; 1008/0/0/96 derive exactly.)

### 8. Slice bounds are checked at runtime — with a message that names "mala". The chapter says nothing about bounds at all.

Chapter (§5): "k[1:3] is a slice: a view of elements 1 and 2 of k, without copying them." / "Read its elements with s[i] and its length with pankti_gan(s)."

**INCOMPLETE.** The chapter says nothing about whether slice endpoints are checked or what happens out of bounds. The code checks **both**, at runtime, at slice creation (`r23_gen_slice`, `src/r23_capabilities.inc:574-703`): `hi <= length` and `lo <= hi`, both via `emit_array_bounds_check` (verified: the routine's own comment at `:572` — "Checks 0 <= lo <= hi <= the base's length at run"). Element reads are checked too (`r23_index_slice`, `:704-720`; `.gs_ai_no_len`, `src/sutram_compiler.asm:19845`). The refusal message is `Sutram truti: mala ank seema atikram` (`msg_array_oob`, `:385`) — a message naming **"mala"** for a **kosh** slice. A beginner writing `k[0:99]` on a 4-element kosh gets a "mala" error for a kosh, and the chapter gives no warning that slices are bounds-checked at all. The chapter also never mentions the other slice forms the code supports: `k[lo:]` (open-ended, `hi` = the length — parser `:17576-17577`), `k[:hi]` (lo = 0, parser `:17555-17567`), slicing a **mala** (`.k_mala`), slicing a **slice** (`.k_slice`), or that a **kosh dasham** slice is refused at compile time (`.k_kosh` → `r23_slice_base_fail` — "a kosh dasham holds binary64: not this version"). (The `k[1:3]` endpoint semantics themselves are right: `hi` is exclusive, shown by the example — elements 1 and 2, sum 5.)

### 9. Kosh CREATION failure has a different message the chapter never shows.

Chapter (§6): "If kosh_kship needs more room and the machine has none to give, the program stops with this sentence and exit status 1: Sutram truti: kosh vardhayitum smritih na labdha - kosh yatha asit tatha eva."

**INCOMPLETE.** §6 covers only **growth** failure. Creation failure has its own message: `Sutram truti: kosh rachayitum smritih na labdha` (`r127_msg_make`, `src/sutram_compiler.asm:709` — verified), emitted by `r127_emit_make_check` (`:21349-21360`) on the kosh declaration path (`:19332` — verified). A declared capacity above `R128_MAXCAP` (2^40 elements = 8 TiB) stops with the **same** make message (`r128_emit_cap_check`, `:19308`). A beginner whose `kosh big[100000000]` creation fails sees a sentence the chapter never shows — and the chapter's "the kosh was not damaged / it still holds exactly what it held before the push that failed" does not apply, because there is no kosh yet. The section heading is "When memory runs out" but it covers only one of the failure shapes. (The grow message itself is quoted exactly and the kosh-is-unchanged claim holds — R155, re-verified the message string at `:708`.)

### 10. nirmmita failure returns 0 — no sentence, no stop. The chapter's "not a crash" framing does not cover it.

Chapter (§6 heading): "When memory runs out". Chapter (§7): "a kosh that cannot grow, a block over its budget, or a block field that is full each stops the program with a sentence that says which, not a crash."

**MISLEADING (by omission).** Persistent `nirmmita` failure does **not** stop with a sentence. `r65_emit_nirm` (`src/r65_arena.inc:245-290`) falls back to a per-call mmap (`r38_nirm_mmap`), and "nirmmita promises 0 on failure" (comment at `src/sutram_compiler.asm:26784-26785` — verified: "mmap reports failure as -errno (-4095..-1), and nirmmita promises 0 on failure. Map the error range to 0"). So `nirmmita(n)` with no memory to give returns a **NULL pointer and the program continues**; the first use (`b[0] = ...`) writes through address 0 — a crash, with no sentence. The chapter's §6 covers only kosh growth, and §7's closing sentence lists three stopping cases — a beginner who exhausts memory with `nirmmita` (for example in a loop outside a block) gets no sentence and a crash, the opposite of what "not a crash" suggests. Related silences: a **computed** negative size outside a block also returns 0 silently — `r75_gen_neg_check` is called **only** from the scratch path (`src/r65_arena.inc:425`); only a constant negative size is refused at compile time (`r75_check_nirm_size`, `:17810`) — and `nirmmita(0)` returns 0 (scratch `.zero` path; persistent `size == 0` → `.mmap` → `mmap(0)` fails → 0). The chapter's "nirmmita(n) gives you n bytes of fresh, zeroed memory" (R155: TRUE with the padding caveat) is silent on `n = 0` and on failure.

### 11. kshetra purnam — named once, never explained; and the budget check fires first.

Chapter (§7): "a kosh that cannot grow, a block over its budget, or a block field that is full each stops the program with a sentence that says which, not a crash."

**INCOMPLETE.** This is the chapter's only mention of the third refusal, and it never explains when it happens. It fires when a **scratch** `nirmmita` cannot fit in the remaining arena: the `.full` path in `r73_gen_scratch_nirm` (`src/r65_arena.inc:454-460`) — `end − align16(size)` underflows, or the new end would meet the persistent cursor — printing `Sutram truti: kshetra purnam - mandapa-smritih samapta` (`r73_msg_full`, `src/sutram_compiler.asm:728`), exit 1. A beginner whose `nirmmita(1000000000)` inside a block fails gets "kshetra purnam" with no chapter guidance on what it means, or that it is the scratch-side out-of-memory — as opposed to the budget refusal `E_PARIMITA`, which is a different thing. One ordering fact the chapter also omits: the budget check runs **before** the `.full` path in `r73_gen_scratch_nirm` (the budget call sits between the `.full` checks and the store of the new end — verified in the `r73_gen_scratch_nirm` listing), so a budgeted block reports `E_PARIMITA` even when the arena is also full. ("Field" is undefined — R155's finding, re-verified the message at `:728` and the `.full` path.)

### 12. "You can see where memory is held" — there is no way to see where.

Chapter (§7): "What you get instead is small and predictable: you can see where memory is held, ask how much (parimana()), cap it (parimita)."

**INCOMPLETE (soft).** `parimana()` tells you **how much**, not **where**; `parimita` caps how much a block may take. There is no way to ask where a given allocation lives — no introspection, no tool that reports an allocation's place. The only "where" is the code you wrote (in a kosh, in a block, in a mala). A beginner looking for a way to find *where* memory is held will find no such thing; what the language actually gives is the discipline of knowing from the code. The sentence over-promises the tooling by one verb. This is the second implied feature that does not exist.

### 13. A whole mala can be passed to a vibhag parameter; a kosh dasham cannot. Neither is mentioned.

Chapter (§5): "likha(yoga(k)) # 10: a whole kosh is passed as k[:]."

**TRUE for the kosh / INCOMPLETE for the rest.** The whole-kosh claim is verified: `.r23_gtca_slice` (`src/sutram_compiler.asm:27384-27400`) — "a vibhag parameter takes a slice, or a whole mala / integer kosh (passed as the slice [0:length]). Anything else is a compile error." A whole **mala** can also be passed to a `vibhag` parameter (same code path), and the chapter never says so; a **kosh dasham** passed to one is refused at compile time (`r23_gen_slice` `.k_kosh` → `r23_slice_base_fail`). Minor.

### 14. "Both are checked: reading dinah[3]" — writes are checked too, unmentioned.

Chapter (§1): "Both are checked: reading dinah[3] stops the program with Sutram truti: mala ank seema atikram (the index is past the end) instead of reading whatever lies beyond."

**TRUE for reads / INCOMPLETE.** The read check is verified (R155: `emit_array_bounds_check`, `src/sutram_compiler.asm:21130-21160`, on the index path in statement `:19845` and expression `:21942` codegen). The same check runs on **writes** (`.gs_ai_no_len`, `:19845`) — the chapter only mentions reading. A beginner might think writing `dinah[3] = 99` is unchecked. Minor.

### Checked and true (no finding)

- **"Try it" exercise:** `mandapa parimita 4096` around a loop calling `nirmmita(64)`. The arithmetic checks out: 64 × 64 = 4096 exactly, and the check is `(mark − new end) > N`, so exactly 4096 passes and the **65th** allocation (4160) is refused, on pass 65. Moving the `mandapa` inside the loop makes each pass fresh (64 bytes, rewound at block end), so it never refuses.
- **"Neither waits to see whether the kosh really grows" (§5):** TRUE — all refusals are compile-time (R155).
- **"A block gives back what nirmmita made inside it. It does not undo anything else the block did — what it printed, or wrote to a file" (§2):** TRUE — the rewind only moves the scratch cursor (`r73_gen_rewind`, `src/r65_arena.inc:404-412`); I/O is not undone.
- **"Numbers may leave a block" (§2):** TRUE — numbers are not tainted (`r73_taint`, `:12538-12610`).
- **The Sanskrit chapter:** the same claims, with the same gaps — read in full. Every item above applies identically to the Sanskrit chapter (same sections, programs, numbers, codes, and the same untranslated "baait" in the same quoted message). Nothing the English states is missing from the Sanskrit, and nothing the Sanskrit states is missing from the English.

### Does the chapter imply a feature that does not exist? (the brief's question, answered)

Yes, twice, and once by omission. (1) The §2 title and §7 imply that block reclamation applies to all memory made inside a block — it does not (a `kosh` keeps its bytes; a `mala` is never given back). (2) "You can see where memory is held" implies introspection that does not exist. (3) By omission, §6–§7 imply that every memory failure stops with a sentence — a `nirmmita` failure does not (it returns 0 and the program crashes on first use). What the chapter does **not** imply: it never implies a GC, a free, reuse inside a live block, or threads exist — R155 verified those four absences, and the line-by-line read found no sentence suggesting any of them.

### Two related findings that belong in the same fix (not the two brief figures)

## Task 3 — the compiler overwriting its own input: what the fix must check, and where it goes

### The defect, confirmed by reading

`sutram hello.sm hello.sm` replaces the program with a binary. The compiler reads its input fully into memory first (`read_file`, `src/sutram_compiler.asm:6946`), then opens the output with `O_WRONLY|O_CREAT|O_TRUNC` — so the compile itself succeeds and the user's source file on disk is destroyed. There is **no input-vs-output identity check anywhere in the tree** (grep for `overwrite|same file|same_file` over `src/`, `win/`, `linker/` returns no check; the only path comparison in the tree is a basename `strcmp` for a diagnostic message, §7 below, which is not a safety check and must not be copied as a pattern). Every truncating open in the tree (complete list — grep for `0x241` over `src/`, `win/`, `linker/`, verified):

| # | Site | Mode |
|---|---|---|
| 1 | `src/sutram_compiler.asm:32668` | ELF output (`write_elf`) |
| 2 | `src/sutram_compiler.asm:33485` | PE output (`write_pe`) |
| 3 | `src/r28_object.inc:125` | `--object` / `--separate` (`r28_write_object`) |
| 4 | `src/sutram_compiler.asm:2440` (Linux) / `:2409` (Windows) | REPL scratch file (`repl_write_program`) |
| 5 | `linker/sutram_link.asm:785` | linker output (`.write`) |
| 6 | `linker/sutram_coff2smo.asm:747` | COFF→SMO converter output |
| 7 | `linker/sutram_elf2smo.asm:635` | ELF→SMO converter output |

All other `os_open` call sites in the compiler are `O_RDONLY` (input, language files, module/`yoj` lookup, `.sffi` sidecar). No listing, map, or second output file exists anywhere: the seven sites above are the complete set of files the tools ever open for writing.

### Argument parsing — where the two names live

Entry is `_start` at `src/sutram_compiler.asm:2745`. Every mode normalises to the same two slots before `.args_ok` (`:3121`): normal / `--lang` (argv[1] = input, argv[2] = output, `:3081-3117`); `--object` / `--separate` (argv[2]/argv[3] shifted down, `:2955-2964`, `:2983-2994`); `--debug` (same shift, `:3038-3044`); `--fail-alloc N` (flag arguments dropped, `:2868-2876`); `--ffi <decls.sffi>` (flag arguments dropped, `:2899-2936`; the sidecar path is kept in `r32_ffi_path`). `.args_ok` then reads the input (`:3139-3140`) and only after lex/parse/codegen writes the output (`.r48_normal_write`, `:3218-3227`). `read_file` (`:6946-6969`) opens the input `O_RDONLY` (`:6951`), reads up to 64 KiB in a single `os_read` into `source_buf`, and closes. A missing input exits 1 with `Sutram truti: nivesh patra aprapt` (`:835`, `:6954-6960`). The input fd is closed long before the output is opened, so the fix cannot compare open file descriptors — it must compare file **identities**. The output format is decided from the output name before the input is read: `want_pe` (`:33457-33477`) returns 1 iff the name ends in `.exe` (case-sensitive `strcmp`); `target_pe` is set at `:2797-2810`. On a Windows build `target_pe` is forced to 1 (`:2797`).

**The trap:** in the `--lang <pack> --check <input>` path, argv[2] is set to the input path itself (`:3101-3102` — corrected from the working notes' `:3116`: `mov rax, R49_ARG(40)` = argv[4] = input; `mov R49_ARG(16), rax; mov R49_ARG(24), rax`, then `jmp .args_ok`). Harmless today because check mode never writes — but any check placed after `.args_ok` that compares argv[1] vs argv[2] unconditionally would false-positive on exactly this path. The fix's check must be gated on `r48_mode == 0`.

### The open sites, one by one

**ELF — `write_elf` (`:32660-32670`).** `write_elf` dispatches to `write_pe` if `target_pe != 0` (`:32663`); otherwise `mov rsi, 0x241; mov rdx, 0o755; call os_open` (`:32668-32670`; `os_open` on Linux is raw `sys_open`, `:33686-33689`). No check before it, and none between `.args_ok` (`:3121`) and this call. Do **not** put a separate check here — the single chokepoint in `_start` after `.args_ok` covers this path, because every mode funnels through `.r48_normal_write` → `write_elf`.

**PE — `write_pe` (`:33480-33489`).** Same flags, same absence of a check. Two differences: on the **Windows build**, `os_open` is `win/winrt.inc:181-210` — any nonzero flags → `GENERIC_WRITE` + `CREATE_ALWAYS` (`:202`), which truncates; `FILE_SHARE_READ` is passed unconditionally (`:192`), so the truncation happens even while another handle has the file open for reading. On the **Linux build**, a `.exe` output name selects this same writer (`want_pe`, `:33457`), so the PE path is reachable on Linux too — the fix must cover it on both builds, not only on Windows.

**`--object` / `--separate` — `r28_write_object` (`src/r28_object.inc:122-129`, called from `.r48_normal_write`, `:3223`).** `mov rsi, 0x241; mov rdx, 0o644; call os_open` (`:125-127`). Same hazard: `sutram_compiler --object hello.sm hello.sm` truncates the source. Note the open-failure path silently returns (`.done`, `:129`) — the compiler then prints success, which is a separate pre-existing wart, not this defect. The `_start` chokepoint covers it (the shift happens before `.args_ok`). In `--separate` mode the read-set additionally includes every module the `yoj` graph pulls in and the `r29_yoj_root` file itself (`:2983-2989`, used for path resolution at `:3955-3957`).

**Linker — `sutram-link` (`linker/sutram_link.asm:782-789`, `.write`).** Usage is `sutram-link <output> <input1.smo> [<input2.smo> ...]` — output is argv[1], inputs are argv[2..]; argc < 3 is a usage error (`:517-521`). All inputs are read fully into memory first (`.read` loop, `:522-542`, via `read_object` at `:291`), then the objects are ordered, laid out, and relocated — and only then the output is opened (`mov rdi, [rcx + 8]` = argv[1]; `mov esi, 0x241; mov edx, 0o755; call os_open`, `:783-787`). The linker's `os_open` (`:97-120`) is raw `sys_open` on Linux and `%include "win/winrt.inc"` on Windows — the same CREATE_ALWAYS truncation on Windows. The PE/ELF choice comes from the *inputs'* magic (`target_w`, set at `:337` from the first object), not from the output name — so the open site is single, and one check covers both output formats. The compiler never invokes the linker (no `execve` of `sutram-link` anywhere in `src/` or `win/` — only comments reference it), so the linker's check is independent of the compiler's; it must be added in the linker itself. **Build script note:** `tools/sutram_build.py:268` invokes `[linker, out] + objects`, where `out` and the object paths are constructed by the script itself under its work/cache directories (`:228`, `:251`). The script cannot name the output the same as an input — checked, no hazard in the script. The hazard lives in the tools it drives.

**Converters — `sutram-coff2smo`, `sutram-elf2smo`.** Both take `tool <input.obj> <output.smo>` (usage strings: `linker/sutram_coff2smo.asm:50`, `linker/sutram_elf2smo.asm:43`). Both read the whole input first (O_RDONLY), then open the output truncating: coff2smo input `:398` → output `:745-747` (`0x241`, `0o644`); elf2smo input `[rsp+16]` (argv[1], flags 0, raw `sys_open`), output `outpath` = `[rsp+24]` (argv[2]) at `:635-638` (`0x241`, `0o644`, raw `sys_open` — this tool has no `os_open` wrapper and no Windows build). No check in either.

### The other read inputs — the second stage the argv check does not cover

The `_start` chokepoint compares argv[1] vs argv[2]. But the compiler reads more files than argv[1], all before the output is opened, and the output could name any of them: the main source (`read_file`, O_RDONLY, `:6946-6969`); imported `.smlib` modules (`mg_read_file`, O_RDONLY, `:4473-4490`; lookup opens at `:3962-3978` also O_RDONLY; call sites `:3424`, `:5592`, `:6197`, `:13570`, `:13663`); the `.sffi` sidecar (`r32_load_sidecar`, read-only, `src/r32_ffi.inc:150-157`, called at `src/sutram_compiler.asm:13994`); the `--separate` root file (used for path resolution only, not read, `:3955-3957`, `:11892` — but it is a user file the compile depends on). All of these are read-only opens, so none of them can clobber anything — the hazard is only the **output** naming one of them. A fix that checks only argv[1] vs argv[2] leaves `sutram_compiler lib.smlib lib.smlib`'s cousins open: e.g. `sutram_compiler main.sm lib/foo.smlib` where `main.sm` imports `foo` destroys `lib/foo.smlib` (already read into memory, so the compile succeeds and the library is gone).

### `--check` mode, the REPL, and other outputs

**`--check` mode: no hazard.** No output file is ever created (`.r48_generate`, `:3200-3215`). Caveat, recorded above: the `--lang --check` path sets argv[2] = argv[1] (`:3101-3102`), so any fix placed after `.args_ok` must be gated on `r48_mode == 0`.

**REPL (`sutram -i` / `--shell`): a different hazard, same family.** The REPL takes no user filename — its commands are exit/help/`sarvam`, or a line appended to the session (`shell_main`, `:2269-2400`). But it writes to **fixed scratch names**: Linux `str_repl_in` = `/tmp/.sutram_repl.sm`, `str_repl_out` = `/tmp/.sutram_repl.bin` (`:810-811`); Windows `str_repl_in` = `.sutram_repl.sm`, `str_repl_out` = `.sutram_repl.exe` in the **current directory** (`:802-803`; the comment says the CWD placement is deliberate on Windows and the `.exe` suffix intentionally selects the PE backend for the child compilation). `repl_write_program` (`:2402`) truncates the scratch input on every run — Linux `:2440-2442` (`0x241`), Windows `:2409-2416` (`CreateFileA`, `CREATE_ALWAYS`). The child compile (`repl_compile_and_run`, `:2555-2640`, fork+execve of the compiler itself with argv `[self, in, out]`) then truncates the scratch output. The compiler's own argv check would **not** catch this: the REPL's input and output names differ from each other. The collision is with a **user's own file** that happens to share the fixed name — on Windows, any file named `.sutram_repl.sm` or `.sutram_repl.exe` in the directory the REPL is started from is destroyed on the first run command.

**No second output file exists.** There is no listing, map, or debug file: the complete truncating-open inventory is the seven sites in the table above. `--debug` (R45) only adds traps to the generated code and uses the ordinary write path. `parikshita`/`--analysis-steps` write nothing.

**Closest existing precedent — do not copy it.** At `:11892-11910` the compiler compares a file's basename against the program's own file's basename with `strcmp`, to print which file a division is in. That is a diagnostic message, not a safety check, and it is exactly the string-comparison pattern the brief says is insufficient. It is cited here so the fix does not reuse it.

### The correct check (consolidated)

**The primitive is file identity, not path text.** On Linux, `stat()` the output path (following symlinks) and compare `(st_dev, st_ino)` with the input's `(st_dev, st_ino)`; on Windows, compare the file ID (`dwVolumeSerialNumber`, `nFileIndexHigh`, `nFileIndexLow` from `GetFileInformationByHandle`). No new helper for this exists in the tree — there is no `stat`/`fstat` wrapper in the compiler, the linker, or `win/winrt.inc`, and `GetFileInformationByHandle` is not in the Windows import list (`win/winrt.inc:501-516` imports only `LdrLoadDll`, `GetStdHandle`, `WriteFile`, `ReadFile`, `CreateFileA`, `CloseHandle`, `VirtualAlloc`, `ExitProcess`, `GetCommandLineA`). The fix must add both the helper and, on Windows, the import. `os_readlink` exists (Linux `sys_readlink`, `src/sutram_compiler.asm:33698`; used once, for `/proc/self/exe` at `:1804`) but resolves only one symlink level and is a stub on Windows (`win/winrt.inc:345-346`) — it is not a substitute.

How the one primitive closes each case:

| Case | Why a string comparison misses it | Why identity catches it |
|---|---|---|
| Symlink (output is a symlink to the input, or vice versa) | the two spellings differ | `stat()` follows symlinks; both resolve to the same `(dev,ino)` |
| Relative vs absolute (`hello.sm` vs `./hello.sm` vs `/home/<you>/hello.sm`) | the strings differ | `stat()` resolves both against the same CWD to the same file |
| Case-insensitive filesystem (`HELLO.SM` vs `hello.sm` on Windows) | byte comparison differs | the file ID is assigned by the filesystem, independent of the spelling used to open it |
| Hard link (two names, one file) | the strings differ | hard links share `(dev,ino)` / the same file index by definition |
| Different spelling (`dir/../hello.sm`, `//hello.sm`) | the strings differ | the kernel resolves the path before `stat()` returns |
| Output names a file that does not exist yet | — | `stat()` fails with `ENOENT`: proceed. A failed `stat` must mean "not the input", never "refuse" |
| Output is a directory | — | its `(dev,ino)` cannot equal a regular-file input's; the following open fails with `EISDIR` as today |

**What the fix must check, in order:**

1. **Compiler, early refusal** — in `_start`, immediately after `.args_ok` (`src/sutram_compiler.asm:3121`), before `read_file` (`:3140`): if `r48_mode == 0`, `stat()` argv[2] and compare with argv[1]'s identity (stat argv[1] too, or capture it from the `read_file` open — `fstat` on the input fd while it is open is the cleanest capture point, inside `read_file` at `:6946`). If equal, print a Sanskrit refusal (see below) and exit 1. This one site covers ELF, PE, `--object`, `--separate`, `--debug`, `--fail-alloc`, and `--lang`, because all of them normalise argv[1]/argv[2] before `.args_ok`. It must be skipped in `--check` mode (`r48_mode != 0`), where argv[2] may legitimately equal argv[1] (`:3101-3102`).
2. **Compiler, read-set check** — in `.r48_normal_write` (`:3218`), before the mode dispatch to `r28_write_object` / `write_elf`: `stat()` argv[2] and compare against the recorded identity of **every** file read during the compile (main source, each `.smlib` import, the `.sffi` sidecar, the `yoj` root). Recording goes in `read_file` (`:6946`) and `mg_read_file` (`:4473`) plus the sidecar load (`src/r32_ffi.inc:150`). This is the check that closes the output-naming-an-import hole, which step 1 cannot see.
3. **Linker** — in `linker/sutram_link.asm`, after `.read_done` (after the `.read` loop at `:522-542`) and before `.write` (`:782`): compare argv[1] against **each** argv[2..] by identity; refuse before the open at `:785-787`.
4. **Converters** — in each tool, after the input is read and before the output open: `sutram-coff2smo` before `:745`, `sutram-elf2smo` before `:635`; compare argv[1] vs argv[2] by identity.
5. **REPL** — make the scratch names unique per process (PID suffix, or `O_EXCL` create with retry) in `shell_main` (`:2269`) / at the `str_repl_in`/`str_repl_out` definitions (`:802-812`); or refuse to start if either scratch path already exists. This is a separate fix from steps 1–4 and must not be folded into the compiler's argv check.

**Refusal convention.** Print a Sanskrit-only message and exit 1, following the existing missing-input path (`Sutram truti: nivesh patra aprapt`, `src/sutram_compiler.asm:835`, exit 1 at `:6958-6960`). Do not route the refusal through `.usage`, which exits **0**. New diagnostics stay Sanskrit-only strings outside the per-pack `sandesh` table (R52 precedent; `LANGUAGE-PRIORITY.md`: Sanskrit only until v1.0). The message should name both the input and the output as given, so the user sees which spelling collided.

**TOCTOU residual (not a blocker).** A `stat()`-then-`open()` check closes the reported defect (a user naming the same file twice) but leaves a narrow window: a concurrent rename swapping the output path for the input between the check and the open would still truncate. Closing that needs `O_NOFOLLOW` plus `fstat` on the opened fd — which does not help for hard links, since the open itself truncates — so the fully race-free Linux form is `stat()` before open plus `O_EXCL` semantics that the normal case (overwriting a *different* existing output) forbids. Recorded as a residual: the threat model here is a typo, not a concurrent attacker.
