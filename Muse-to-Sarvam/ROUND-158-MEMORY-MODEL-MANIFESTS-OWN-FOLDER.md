### Q1 — The descriptor: size and layout

**What the code says.** A `kosh` value is a descriptor that never moves, **four qwords / 32 bytes** — length, capacity, elements pointer, region size — **56 bytes with the liveness metadata** (three more qwords). The header allocation adds 4 qwords, or 7 when the per-program flag is set; the flag is set at parse time if a program makes a `kosh` inside a `mandapa`, so *every* `kosh` in such a program gets the 56-byte header. **What the document says** (line 7): "its length, capacity and the address of its elements." It names only **three** fields — the fourth (region size) is never mentioned, and the document gives **no byte size at all** (no size wording anywhere in the file). Line 43 gives the correct offsets for length and capacity but again no fourth field and no size. **Verdict: WRONG.** "Never moves" holds; the field list is incomplete in exactly the way that yields 24 bytes by arithmetic (3 × 8). The document does not repeat the old wrong figure, but a reader counting its fields gets 24, not 32.

### Q2 — What a block reclaims: the three-way split

**What the code says, leg by leg.** (1) **`nirmmita` inside a block IS given back at block end.** The redirect is lexical: `nirmmita` written inside a `mandapa` takes the scratch side, and the rewind restores the scratch cursor to the block's mark on every exit path (fall-off, return, and the two loop-control exits). Only the scratch cursor moves; the persistent cursor is untouched. (2) **A `kosh` keeps its bytes for the whole program; only its LIVENESS ends.** A `kosh` declared in an open block is only remembered, so the outlives rule can refuse to give it to a procedure that keeps it. Its allocation goes through the ordinary persistent path and its growth through the growth emitter; what ends at the block is liveness, enforced by the refusal. (3) **A `mala` made inside a block is NEVER given back, and its address can leave freely with no refusal.** A mala declaration allocates via the ordinary persistent path — a declaration is not a `nirmmita` call in the source text, so the lexical redirect never applies. No rewind touches mala storage, and no escape refusal exists for a mala: the only mala-specific checks are the operator refusals. A mala pointer is a persistent-side pointer, so neither the scratch-escape refusal nor the kosh-block refusal applies to it.

**What the document says.** Only leg 1, and overstated. Line 5: "A `mandapa` block gives back what it allocated when it ends — the arena's scratch side falls (R102)." "Gives back what it allocated" without qualification implies all block allocations; a `kosh` and a `mala` are both allocated in a block's text and neither is given back. The kosh-storage half is never stated (line 8 says only "A `kosh` made in a block cannot leave it", a refusal, not a storage claim). The mala half is entirely absent — the word appears **once** in the whole document (line 110, about bounds errors on particular indexing paths). Two further defects in line 5: the round citation is wrong — the rewind is the R73 work, and the cited round was a reference census with no scratch/rewind content; and "Pages are reused, not returned to the kernel" holds for the arena (one mapping, never unmapped) but is stated as if it covered everything the block allocated. **Verdict: WRONG** (line 5 as stated). The scratch-side mechanism it names is real; the sentence's scope is not.

### Q3 — What `parimana()` counts

**What the code says.** The number is **logical bytes held, rounded to 16** (arena cursors are aligned to 16), and it counts **kosh CAPACITY, not length**: the region counter is incremented by new capacity bytes at allocation/growth and decremented by old capacity on region release. It is NOT reserved address space (the 1 GiB arena and 64 MiB regions are never counted) and NOT committed pages (only the bytes the cursors say are held). In detail: the persistent side is bytes bumped, including abandoned arena buffers left by small growth and all descriptor bytes; the scratch side is live bytes only; a mala counts too (its bytes are ordinary allocation bytes); a kosh's region reservation counts only through the capacity counter. Corroborated by the golden test: a `kosh` of 1000 counts 8,288 — 64 + 8,224, where 8,224 = 32-byte header + capacity 1024 × 8 (not length 1000 × 8). **What the document says** (line 9): "`parimana()` reports the bytes the program's `nirmmita` and `kosh` hold now (R107)." True in outline and silent on every material qualifier: it does not say capacity (not length), logical (not committed, not reserved), or that a region counts through a separate counter. A reader cannot tell from it whether a `kosh` of 1000 counts 8000, 8192, or 8224. **Verdict: IMPRECISE.**

### After a manifest is regenerated, what does it still prove? — and was that what it was for?

**What it still proves:** exactly what the brief says — the listed files' bytes are the ones the manifest was generated from. A regenerated manifest proves the tree is consistent with itself at generation time. It proves nothing about history: the old hashes describe pre-normalisation bytes, and regeneration replaces them with new ones. A regenerated manifest is consistent with *any* bytes, including bytes altered after publication for any reason at all — the check cannot distinguish "bytes changed by the privacy normalisation" from "bytes changed by anything else, at any time".

**Was that what it was for?** In part — and the part it would lose is the point. The run folders' stated purpose is evidence integrity: a later reader verifying that the published evidence is the evidence observed then. That purpose has two halves: (1) **self-consistency** — "these files, as they stand now, match this list" (regeneration preserves this half; a fresh check would pass); (2) **historical anchoring** — "these are the files published in November 2026, with the bytes they had then" (regeneration *empties* this half — the new manifest's hashes are the post-normalisation bytes; nothing in it ties them to the publication event). For evidence folders, the second half **is** the purpose. A manifest that only proves self-consistency is a checksum of the present, not evidence of the past — and these folders exist to be evidence of the past. Regenerating the seven in place would trade the historical claim for a clean check, and the clean check would then be vacuous (it would pass for any content whatsoever, since the manifest was generated from that content).

**What would preserve it:** keep the original manifest alongside as a historical record, with the old hashes labelled pre-normalisation — do not overwrite it. The preservation already exists in two places, and both should be cited, not assumed: the normalisation record (before/after digests for all 806 changed files) and history itself (the old base reproduces the pre-normalisation bytes exactly; history is not rewritten). What neither does on its own is keep the *manifest* readable as a record: a reader running the check in a run folder still fails, and must know to consult the record and the base commit. The honest repair is therefore three parts: (a) keep the original checksum files untouched as historical records; (b) if a current-tree check is wanted, generate a *separate* manifest under a different name, so the two are never confused; (c) put the pointer in the run folder (a line in the results or commands file: the original manifest covers the bytes as published; the record and the base commit give the before/after digests). The other agent's R222 and R223 say the same, independently: "Preserve original manifests as historical records and supply an explicit restoration/mapping workflow rather than saying no evidence dependency broke" and "A hash alone does not recover evidence. An accessible immutable historical object can; keeping evidence in the working tree avoids recovery friction. No history rewrite is needed." One more consequence of regenerating in place, specific to the 57 missing screenshots: regeneration would *drop them from the list* (a regenerated manifest can only list files that exist). The original manifest is then the only record that those 57 screenshots were part of the evidence set at all. Deleting the originals would erase the fact of their inclusion, not just their hashes.
