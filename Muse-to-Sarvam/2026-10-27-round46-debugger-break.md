# ROUND-46 — try to break the debugger

**Base:** `origin/main` at `7ef38a2f` (v370; round written against
v369), compiler **v252**. The debugger under test is Claude's
`--debug` in `src/r45_debug.inc`: a trap before every statement,
built as ordinary Sutram statements (`likha` calls generated by
`gen_stmt`), printing `[shodhan] pankti N` and every scalar in
scope. All tests below were run twice: once normally, once with
`--debug`, and the trap values compared against the real program
output. PASS / FAIL / NOT-RUN separately.
**No code changes made. No files added or modified in the tree.**

## WS1 — the six hard cases, with exact output

### 1. Register vs stack — PASS

Program: 5 register locals (`r1`–`r5` = 10–50), 3 stack locals
(`s6`–`s8` = 60–80), a parameter (`a = 0` in `add7`), and
`total = r1+…+s8+add7(0)`.

Trap output (abridged, full in the transcript below):
```
[shodhan] pankti 13
    r1 = 10
    r2 = 20
    r3 = 30
    r4 = 40
    r5 = 50
    s6 = 60
    s7 = 70
    s8 = 80
[shodhan] pankti 2
    a = 0
[shodhan] pankti 14
    ...
    total = 367
367
```
Every register and stack value matches the real computation, and
the normal run also prints `367`. The trap fires inside the called
function too (pankti 2, `a = 0`), correctly interleaved between the
caller's traps. A trap before a statement shows only variables
declared before that statement — `total` is absent at pankti 13
and present at pankti 14, which is correct, not missing.

### 2. Dasham precision — VALUE PASS, PRECISION FAIL (limitation, not a lie)

```
dasham pi = 3.141592653589793
dasham third = 1.0 / 3.0
dasham sum = 0.1 + 0.2
```
Trap and normal output agree exactly:
```
pi = 3.141593
third = 0.333333
sum = 0.300000
```
But the agreement is only to **6 decimal places, because the trap
prints through `likha`, and `likha` prints 6 decimal places**.
`0.1 + 0.2` is `0.30000000000000004` in binary, and the trap shows
`0.300000` — the floating-point error is invisible. A wrong answer
that differs only beyond the 6th decimal place cannot be seen
through this debugger. The values are not wrong; the precision is
insufficient for the brief's question ("enough precision to see a
wrong answer?" — no, not past 6 places). Fixing this means fixing
`likha`'s float format, not the trap.

### 3. Mala / kosh element — CONTAINER NOT PRINTED (by design), ELEMENT PASS

```
mala a[3]; a[1] = 22; vitti elem = a[1]
kosh dasham k[4]; kosh_push(k, 2.5); dasham ke = k[1]
```
Trap output shows **no `a` and no `k` at any statement** — the
container variables are deliberately left out (the source says
`likha` would print an address). What it does show is correct:
```
[shodhan] pankti 7
    elem = 22
22
[shodhan] pankti 12
    elem = 22
    ke = 2.500000
2.500000
```
So: the container itself is not printed at all, and an element is
only visible after it has been assigned to a scalar. A user
debugging "why is `a[1]` wrong?" gets no help from the trap
directly — they must add the scalar assignment themselves. That is
a documented design limit, not a wrong value, but it is the
debugger's largest blind spot after strings (below).

### 4. Shadowed variable — PASS, with two honest qualifications

(a) **Nested redeclare does not exist in this language.** My first
shadow test (`vitti x = 2` inside a block where `x` already
exists) is a **compile error**, not a runtime shadow:
```
shadow.sm:5:15: Sutram Error [E_DUPLICATE_NAME]: punah ghoshana 'x'
Sanket: 'x' purvam eva ghoshitam; navinam manam datum: x = ...
```
So the "inner scope shadow" form cannot occur for `vitti`.

(b) **Redeclare after a block closes — PASS.** Inside the block
the trap shows `x = 1`; after the block, the trap shows `x = 2`
(the new declaration), never the stale `1`:
```
[shodhan] pankti 4
    x = 1
1
[shodhan] pankti 7
    x = 2
2
```

(c) **Parameter shadowing a global — PASS, and the global never
prints.** Inside `show(x)` the trap shows `x = 5` (the parameter),
not the global `100`. After the call, the trap at the `likha(x)`
statement shows **no variables at all** — module-level `vitti` is
not in `var_table` and is never shown — and then the program
prints `100`. So: the outer value does not leak into the inner
trap (correct), but a global is invisible to the debugger
everywhere (by design, and a real blind spot for global-dependent
bugs).

### 5. Devanagari identifier — PASS

Compiled with `--debug --lang sanskrit`:
```
[shodhan] pankti 2
[shodhan] pankti 3
    योग = 42
42
```
The Devanagari name prints correctly. (The trap header itself
stays in Latin script, `[shodhan] pankti N` — that is the debug
format, not a defect.)

### 6. Program that crashes — PASS, both kinds

**Clean error (array out of bounds):**
```
[shodhan] pankti 4
10
[shodhan] pankti 5
Sutram Error: mala ank seema atikram
```
Exit 1, `999` never printed. The trace stops exactly at the
failing statement, with its trap printed before the error.

**Hard crash (integer division by zero):**
```
[shodhan] pankti 3
    a = 10
[shodhan] pankti 4
    a = 10
    b = 0
```
Then the process dies with SIGFPE (exit 136, shell reports
"Floating point exception"), no trap after the crash, no garbage,
no trap loop. The last trap shows the state *before* the crashing
statement (`a = 10, b = 0`) — which is exactly what you want from
a crash trace. The debugger itself prints no "crashed" message;
the OS reports the signal. That is clean enough, but if a
"program crashed at pankti N" line is wanted, it is not there
today.

### Extra finding 1 — THE WRONG VALUE: string variables print as addresses — FAIL

This is the case the brief called most valuable, and it is real.
```
vitti s = "hello"
shabda(s)        ; the correct way to print a string
```
Normal run: `hello`. Debug trap:
```
[shodhan] pankti 3
    s = 4194504
hello
```
The trap prints `s = 4194504` — a memory address, presented
exactly as if it were an integer. Two problems: (i) a user reads
it as "s is a number, 4194504", which is false — s is "hello";
(ii) the address shifts between builds (the normal binary's own
`likha(s)` printed `4194454`, the debug binary's `4194504`),
so the trap value cannot even be compared across runs. Cause: the
trap prints through `likha`, and `likha` on a string variable
prints its address — strings are printed with `shabda`, not
`likha`. Unlike mala/kosh, strings are **not** excluded from the
trap, so they appear as fake integers instead of being omitted.
Fix: either exclude string variables like mala/kosh, or print
them through `shabda`. As it stands, **every string variable in
a `--debug` trace is a misleading value**.

### Extra finding 2 — very long names are silently omitted — LIMITATION

A 120-character variable name compiles and runs correctly
(normal and debug both print `42`), but the debug trap at its
statement shows **no variable at all** — the source skips names
longer than 112 characters (`R45_LABEL_CAP - 8`) with no marker
that anything was skipped. A user seeing an empty trap at that
statement would conclude "no variables in scope", which is
false. A one-line marker ("name too long, omitted") would fix
the silence.

### Did `--debug` change program behaviour? — NO, in these tests

Excluding trap lines, every program's own output and exit code
were identical with and without `--debug` (367; 3.141593 /
0.333333 / 0.300000; 22 / 2.500000; 1 / 2; 5 / 100; 42; OOB exit 1;
SIGFPE exit 136). The only differing value is the string address
above, which is address layout, not program logic.
