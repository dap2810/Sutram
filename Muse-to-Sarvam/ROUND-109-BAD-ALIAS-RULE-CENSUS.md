sankhya_bindu — the one bad alias.

File: `src/sutram_compiler.asm`, handler `.ge_call_vecdot` (old name `sankhya_dot`, builtin id 21). New name `sankhya_bindu`. What the body does: it reads 16 bytes (4 × 32-bit floats) from each argument pointer with `movups`, multiplies them with `mulps`, reduces with two `haddps`, and returns the result as float BITS in `eax` — which `likha` then prints as an integer. Why the name misleads: `bindu` (dot/point) promises a dot product, and a user trusting the name gets a silent wrong answer, not a refusal. No Sutram value holds 4 contiguous 32-bit floats: a `kosh` argument gives its header (dots to 0), a `mala` gives 8-byte slots (dots to garbage, 2 for [5,6,7]). And even a correct dot would print as bits via `likha`, not as the value. So the name is right for the intent and the body cannot deliver it for any constructible input — that is the defect, and it outranks the rest of this round because it is a defect in a function we just renamed. It is a BODY defect, not a name defect: `bindu` passes the name rule below (it is a complete noun), and the fix is a double-based redesign returning a `dasham`, not a rename. That redesign is Claude's/Sarvam's, not Muse's; this round does not implement it.

## WS2 — the root-versus-noun rule, one answer, applied

**The rule (two tiers, from R108, unchanged).** (1) Concepts and keywords must be COMPLETE words. (2) Function names use the SHORTEST RECOGNIZABLE FORM (root, stem, or noun) that unambiguously names the action. Existing roots are grandfathered, not regularised. Meaning errors are fixed regardless of form.

**The honest answer to "is the tree inconsistent?"** No — not under this rule. The apparent inconsistency (roots mixed with nouns) dissolves once the tiers are separated: functions use short forms, concepts use complete words, and no concept keyword is a bare root except `yoj` (the include keyword, grandfathered — renaming it would break every include unless aliased, which is churn for no behavior gain, so it stays). Regularising the tree would therefore NOT break every program if done with aliases (it would churn them), and is unnecessary because the tree is already consistent under the two-tier rule. Do not regularise.
