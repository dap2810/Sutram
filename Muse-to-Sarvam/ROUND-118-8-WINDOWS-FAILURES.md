## WS1 — the eight, one by one (expected, actual, exit, classification)

**1. 220_hindi_parse_error — HARNESS (missing flag, not a compiler failure).** Expected (exit 1): "भाषा पैक मिला: hindi" then the Hindi parse error (व्याकरण दोष, पंक्ति 7:1, शब्द 'फ़ाइल का अंत' + Hindi hint). Actual (exit 1, same exit): NO "भाषा पैक मिला" line, and the error in Romanized Sanskrit ("vyakaran dosh, pankti 7:1, shabd 'patra-ant'" + Romanized hint). The exit matches; only the pack differs. Cause (proven by the JSON's `compile_command`, which has NO `--lang` flag, vs the Linux runner `tests/run_tests.py:45,83`, which passes `--lang hindi` for this case): the Windows runner did not pass `--lang hindi`, so the compiler used the default (Sanskrit) pack. The Windows compiler itself is not shown to be broken here — whether it finds `lang/hindi.lang` when given `--lang hindi` is a follow-up that needs a Windows run with the flag, but the current failure is the missing flag. **Fix: the runner, not the compiler.**

**2. 288_r86_kosh_alias_moves — COMPILER LIMITATION, DOCUMENTED AND PRE-EXISTING (not a regression, not this week's work).** Expected (exit 0): "a[0]=99 k[0]=99" then "a[0]=7 k[0]=7" (a is a second name for the same kosh, so writes through either name show through the other). Actual (exit 0): "a[0]=41 k[0]=99" then "a[0]=7 k[0]=99". The program's own comment says it: "Windows still moves (reference section 16)". On Linux, R101A regions (v284) give every kosh its own 64 MB region and grow it in place, so aliases stay one. On PE, regions were never built (R101A is Linux-only), so koshes still use the old relocating path: when `kosh_kship(k, 42)` grows k from capacity 1 to 2, k MOVES to a new buffer, but `a` (the alias) stays on the old buffer — hence a[0] reads the stale 41 (the first push) and k[0] reads the stale 99 after a[0]=7. This is the R101A-on-PE gap, documented in the reference, not a new bug. **Fix: bring regions (or an equivalent) to PE — a larger piece of work, not a one-line fix.**

**3. 29_nishkriya — HARNESS (should be SKIP, not FAIL).** Expected exit 42; actual exit 0, with stdout IDENTICAL (the full "Yantra: Inline Assembly ... Exiting with code 42..." text). The program uses `yantra` with raw x86-64 bytes for a LINUX syscall (`mov eax,60 / mov edi,42 / syscall` = Linux exit(42)). There is no Linux syscall 60 on Windows, so the bytes cannot exit 42 there — the program prints the text and exits 0 (the normal exit). The JSON already has a `SKIP_SIDE_EFFECT_OR_INLINE_ASM` category (3 cases: 217, 245, 270) — 29 is an inline-asm test and belongs in it, but the runner's skip list missed it. **Fix: the runner's skip list, not the compiler (no compiler change can make a Linux syscall exit 42 on Windows).**

**4. 303_r103_parimita_refuses — COMPILER GAP (PE does not enforce the budget).** Expected (exit 1): "Sutram truti [E_PARIMITA]: pankti 6 - mandape parimitat adhikam nirmmitam na sambhavati (parimitih 1048576 baait)". Actual (exit 0): "not reached 499999500000" — the program ran all 1,000,000 iterations (the sum 0..999999 = 499999500000 confirms it) and reached the line after the mandapa block. The `mandapa parimita 1048576` budget check did not fire on PE. **Fix: the PE nirmmita must check the block budget (see grouping — this shares a root cause with 317/318).**

**5. 317_r107_parimana — COMPILER GAP (parimana unimplemented on PE).** Expected (exit 0): "start 0 / after nirmmita(64) 64 / in a block, nirmmita(1000) 1072 / after the block 64 / a kosh of 1000 8272". Actual (exit 0): ALL ZEROS ("start 0 / after nirmmita(64) 0 / in a block, nirmmita(1000) 0 / after the block 0 / a kosh of 1000 0"). `parimana()` returns 0 on Windows, always. **Fix: implement parimana on PE (see grouping).**

**6. 318_r108_parimana_moves — COMPILER GAP (same as 317).** Expected (exit 0): "start 0 / a kosh of 1 48 / grown to capacity 4 72 / a block's nirmmita(100) 184 / and a kosh of 8 in it 288 / after the block 176". Actual (exit 0): ALL ZEROS. Same cause as 317: `parimana()` returns 0 on PE.

**7. 322_r111_new_names — COMPILER FAILURE (PE string crash, NOT a names issue).** Expected (exit 0): full output ending "laghu 97 guru 65 / B42 / abcd". Actual (exit 3221225477 = 0xC0000005, Windows ACCESS_VIOLATION): "...laghu 97 guru 65 / �42 /" then crash — NO "abcd". The crash point is in the string steps after the laghu/guru line: `shabda(anka_akshar(66))` printed � (a bad byte) instead of 'B', then `likha_santat(42)` + newline printed "42", then `vartani_sandhi("ab","cd")` → `shabda(s)` crashed (access violation) before "abcd". So two PE string builtins are broken at that point (anka_akshar's result has a bad first byte; vartani_sandhi's result crashes on print). **Crucially, 323 (the same program with OLD names) crashes identically (same �, same exit, same point) — so the names are NOT the cause. Fix: the PE string builtins, not the vocabulary.**

**8. 323_r111_old_names — COMPILER FAILURE (same as 322).** Expected (exit 0): same full output as 322 ("B42" + "abcd"). Actual (exit 3221225477, same ACCESS_VIOLATION): same "�42" then crash, same point. The old-name warnings DID print correctly at compile time (all 15 warnings, correct new names), so the alias mechanism works — the crash is downstream, in the string steps, identical to 322. ## WS2 — Linux v297 (all eight pass) + parimana numbers

Linux v297, run directly (220 with `--lang hindi`, the rest plain): 220 → Hindi pack line + Hindi diagnostic, compile exit 1 ✓; 288 → "a[0]=99 k[0]=99 / a[0]=7 k[0]=7", exit 0 ✓; 29 → exit 42 ✓; 303 → E_PARIMITA, exit 1 ✓; 317 → 0, 64, 1072, 64, 8272, exit 0 ✓; 318 → 0, 48, 72, 184, 288, 176, exit 0 ✓; 322/323 → full output ending "B42 / abcd", exit 0 ✓. So the goldens are correct on Linux; the Windows failures are all Windows-side.

**Parimana, specifically (the brief's question): Linux gives 64, 1072, 64, 8272 (317) and 48, 72, 184, 288, 176 (318). What would Windows plausibly give?** The Linux numbers are 16-byte-ALIGNED requested bytes, not page counts: nirmmita(64) → 64 (exact); nirmmita(1000) in a block → 1072 = 64 + 1008 (1000 rounded up to 1008, 16-aligned). The alignment (16) is a compiler-level constant, not a page size — so IF parimana were implemented on PE counting the same way (aligned requested bytes), it WOULD match the Linux goldens, and the golden would NOT need changing. The current Windows result (0) is not a different number — it is absence (unimplemented). So 317/318 are compiler gaps, NOT harness failures (the golden does not assert a page-dependent number). Caveat for after implementation: IF Windows' allocator rounds differently (e.g. to 8 bytes, or adds a header), a Windows parimana WOULD give different numbers, and the golden would then need a platform variant — but that is a follow-up question for after implementation, not the current bug (0 vs 64 is not a rounding difference).

## WS3 — the grouping (the most useful thing)

**Eight failures = four fixes, not eight bugs — and the five "this week's work" do NOT share one cause (they split 3 + 2):**

- **Group 1 — PE allocator tracking missing (one root cause, 3 tests: 303, 317, 318).** All three are "the PE backend doesn't track allocations the way the ELF backend does": parimita cannot enforce a budget without tracking (303 runs to completion), and parimana cannot report without tracking (317/318 return 0). One fix (PE allocation tracking: cursors + block budgets + reporting) covers all three.
- **Group 2 — PE string builtins broken (one cause, 2 tests: 322, 323).** Identical crash at the identical string step (anka_akshar bad byte, vartani_sandhi access violation), in both the new-name and old-name programs — so it is one string bug, not two vocabulary bugs, and not a names issue at all.
- **Group 3 — PE kosh regions missing, documented (1 test: 288).** The R101A gap on PE (regions are Linux-only); reference §16 already documents "Windows still moves". Related to Group 1 (both are "PE backend behind ELF") but a distinct mechanism — fixing allocation tracking does not fix kosh relocation, and vice versa — so it stays its own group.
- **Group 4 — harness (2 tests: 220, 29).** 220: pass `--lang hindi` (the Linux runner does; the Windows runner doesn't). 29: add to the SKIP_SIDE_EFFECT_OR_INLINE_ASM list (the category already exists; 29 was missed).

So: **three compiler gaps (allocator tracking, string builtins, kosh regions) + one harness fix (two small runner changes) = the eight.** The single most valuable next step is Group 1 (three tests, one root cause, and the mechanism — allocation tracking — is the same one Group 3's regions will need on PE anyway).
